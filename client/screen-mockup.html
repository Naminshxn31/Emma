ทุกข้อด้านล่างมาจากไฟล์จริงในรีโปหรือจากการคำนวณขนาดจอ ไม่ได้มาจากความชอบ ถ้าข้อไหนขัดกับที่เจ้าของต้องการ ให้แก้ข้อนั้นก่อนแล้วค่อยลงโค้ด

1. ขนาดตัวอักษรมาจากระยะยืน ไม่ใช่จากความสวย

จอ 18.5" 16:9 ติดตั้งแนวตั้ง = กว้าง 230 มม. × สูง 409 มม. วาง 1080 px บน 230 มม. ได้ 4.69 px/มม. (~119 dpi)

เกณฑ์ที่ใช้กันคือความสูงตัวอักษรพิมพ์ใหญ่ต้องไม่ต่ำกว่า ระยะ ÷ 200 จึงจะอ่านออก และ ÷ 150 จึงจะอ่านสบาย

ระยะยืนcap height ต่ำสุด= font-size ประมาณ
1.0 ม.5.0 มม.34 px
1.5 ม.7.5 มม.50 px
2.0 ม.10.0 มม.67 px

ข้อที่ต้องรู้: หน้าแอปตอนนี้ (html.app-shell .reply-text) ตั้งไว้ clamp(1rem, 2.8vw, 1.32rem) ซึ่งบนจอกว้าง 1080 px คือ 21 px — ขนาดนั้นอ่านออกที่ประมาณ 0.6 เมตร คือระยะถือมือถือ ไม่ใช่ระยะยืนคุยกับหุ่น แบบร่างนี้จึงตั้งตัวพื้นที่ 56 px คำทักที่ 116 px และตัวเล็กสุดที่ 30 px สำหรับข้อความที่ยอมให้อ่านไม่ออกจากระยะไกล (ที่มา/เวลาอัปเดต)

2. ห้ามเอาคำที่ลูกค้าพูดขึ้นจอนี้

กฎเดิมของ /display?chat=1 ใน CLAUDE.md ใช้กับจอนี้ทั้งข้อ — เหตุผลเดียวกันเป๊ะ: ถอดเสียงผิดบ่อยพอที่จะทำให้หุ่นที่ทำงานถูกดูเหมือนพัง และ prompt สั่งให้เอ็มม่า ทวนเบอร์โทรกลับ = เบอร์คนแปลกหน้าขึ้นจอกลางห้องขายให้คนเดินผ่านอ่าน

แบบร่างนี้จึงไม่มีช่อง transcript เลย มีแต่ตัวชี้วัด “กำลังฟัง…” ปุ่ม “ข้อความ” ที่มีอยู่ในแอปตอนนี้ต้องไม่ติดมาที่จอหุ่น (จอโน้ตบุ๊กพนักงานยังมีได้ นั่นคนละพื้นผิว)

3. ชื่อคนใช้ได้แค่ประโยคทัก แล้วหายไป

ตรงกับ greeting_for ในเซิร์ฟเวอร์: หลังทักแล้วโมเดลไม่มี speaker ID จึงไม่รู้ว่าเสียงถัดไปเป็นใคร ปล่อยชื่อค้างบนจอทั้งสาย = จอยืนยันสิ่งที่ระบบไม่รู้ จอที่ 3 จึงมีชื่ออยู่จอเดียว จอที่ 4-6 ไม่มีชื่อเลย

และชื่อขึ้นได้เฉพาะเมื่อเงื่อนไขครบตามที่โค้ดมีอยู่แล้ว: ผ่านเกณฑ์ + ยืนยันหลายเฟรม + margin อันดับ 1-2 + หน้าเดียวในเฟรม + consent ไม่ถูกเพิกถอน ไม่ครบข้อไหนก็ตกไปที่จอที่ 2 ซึ่งไม่มีวันผิด

4. โหมดว่างต้องไม่ใช่นาฬิกาเรือนที่สอง

บั๊กที่โปรเจกต์นี้จ่ายมาแล้วหลายรอบคือกลไกใหม่ที่มีนาฬิกาของตัวเอง (Canva กับจอเว็บ, ตัวกระตุ้นทัวร์กับคิวเสียง) โหมดว่างจึงต้องเป็น state เดียวกับที่หน้าเว็บมีอยู่แล้ว (data-emma-state="idle") ไม่ใช่ timer แยกที่ตัดสินเองว่าเมื่อไหร่ควรกลับไปวนภาพ ไม่งั้นจะได้อาการ “หุ่นกลับไปโชว์ภาพโครงการกลางประโยคที่กำลังตอบลูกค้า”

5. จอสลับเองตามสถานการณ์ ไม่ใช่มีปุ่มให้คนสลับ

  • ว่าง → โหมดดึงดูด (จอ 1)
  • กล้องเห็นคน → ทัก (จอ 2 หรือ 3 ตามเงื่อนไขข้อ 3)
  • คุยกันอยู่ → Emma นำ (จอ 4)
  • เครื่องมือคืนของที่มีภาพ → Emma หดไปบน + การ์ด (จอ 5)
  • ผัง/สไลด์/เว็บ → เนื้อหาเต็มจอ Emma เหลือหัวเล็ก (จอ 6)
  • ปิดของ / จบสาย → กลับจอ 1

จอ 5 กับ 6 ต่างกันตรง “ของชิ้นนี้ต้องมองนานแค่ไหน” การ์ดห้องอ่าน 5 วินาทีจบ ผังชั้นกับสไลด์ต้องกวาดตา จึงยอมให้กิน Emma ได้

6. ช่องว่างติดป้ายว่าขาดอะไร ไม่ซ่อน

“ภาพห้อง — รอจากฝ่ายขาย” และ “ราคา — สอบถามฝ่ายขาย” อยู่ในแบบร่างโดยตั้งใจ ตามกฎเดิมของการ์ดห้อง ช่องว่างที่บอกว่าต้องเติมอะไรทวงตารางยูนิตได้ดีกว่าอีเมล และ UNITS_SHOW_PRICE=false ยังเป็นค่าเริ่มต้นตามคำสั่งเจ้าของ

สิ่งที่แบบร่างนี้ยังไม่ตอบ

  • ภาพที่จะวนในโหมดว่าง — ตอนนี้ดึงสไลด์มาใช้ชั่วคราว ของจริงควรเป็นชุดภาพที่เลือกไว้เพื่อการนี้
  • เสียง/แอนิเมชันตอนเปลี่ยนจอ — ยังไม่ออกแบบ ต้องดูของจริงบนหุ่นก่อน
  • จอเวลาเน็ตหลุด / เซิร์ฟเวอร์ดับ — ต้องมี แต่ยังไม่ได้ร่าง
  • 4 จอที่ยังไม่ได้พอร์ต (calc / unitlist / promotions / unittypes) — เจ้าของเลือกไม่เอารอบนี้
