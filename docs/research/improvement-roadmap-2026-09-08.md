# แนวทางพัฒนา condo-voice หลังรีวิวโค้ด

วันที่ค้นคว้าและตรวจโค้ด: 8 กันยายน 2026

ข้อเสนอหลักคือพัฒนา **การวัดคุณภาพเสียงจริง ความน่าเชื่อถือของข้อมูล และความพร้อมของเครื่องที่ใช้งาน** ก่อน แล้วใช้ผลวัดเลือกการปรับ VAD, retrieval และ transport ต่อไป ผลตอบแทนที่คาดหวังคือหุ่นตอบถูกขึ้น คุยสะดุดน้อยลง และเจ้าหน้าที่เห็นสาเหตุเมื่อระบบทำงานไม่ได้

รายงานนี้เทียบเอกสารทางการและงานวิจัยกับ working tree หลังแก้รีวิว 8 ข้อแล้ว เป็นข้อเสนอสำหรับงานถัดไป ยังไม่ได้เปิดฟีเจอร์ เปลี่ยนโมเดล หรือติดตั้งแพ็กเกจตามข้อเสนอ ผลลัพธ์และระยะเวลาข้างล่างเป็นเกณฑ์/ประมาณการที่เสนอ ไม่ใช่ผล benchmark ที่วัดได้แล้ว

## ลำดับงานที่แนะนำ

P1 = ควรเริ่มในรอบถัดไป, P2 = ทำหลังมีฐานวัดผล, ทดลอง = เปลี่ยนค่าเริ่มต้นเมื่อผลเปรียบเทียบผ่านเท่านั้น เวลาเป็นวันทำงานของนักพัฒนา 1 คนโดยประมาณ ไม่รวมรอฝ่ายขาย/อุปกรณ์/สิทธิ์ระบบ และแต่ละงานมีส่วนที่ทำร่วมกันได้

| ลำดับ | งาน | ประโยชน์ที่คาดหวัง | ระดับ | ประมาณการ |
|---|---|---|---|---|
| 1 | วัด latency และ usage รายเทิร์น | รู้ว่าช้าตรงไหนและต้นทุนเปลี่ยนเพราะอะไร | P1 | 2–3 วัน |
| 2 | ชุดประเมินเสียงไทยและคำตอบอ้างอิง | เลือกการปรับที่ช่วยผู้ใช้จริงและจับ regression | P1 | 3–5 วัน + เก็บเสียง |
| 3 | ขั้นตอนอนุมัติ/อายุ/ที่มาของข้อมูล | ตอบจากข้อมูลที่เจ้าของรับรองและยังใช้ได้ | P1 ห้องขาย | 3–5 วัน + เจ้าของข้อมูล |
| 4 | ปรับ VAD/AEC จากการทดลอง | ลดตัดคำ พูดแทรกผิด และช่วงเงียบ | P2/ทดลอง | 2–4 วัน + เครื่องจริง |
| 5 | ปรับ retrieval และ reranker จากชุดสอบ | หาสไลด์ถูกโดยรักษาเวลาตอบ | P2 | 2–3 วัน |
| 6 | ทดสอบสายหลุดและคุยต่อเนื่อง | เปิดใช้งานได้นานและฟื้นตัวอย่างมีขอบเขต | P1 | 2–3 วัน + soak test |
| 7 | Command ID, ACK และ confirmation ที่บังคับจริง | ลดคำสั่งซ้ำและการรายงานผลเกินหลักฐาน | P1 ก่อนเดินจริง | 3–5 วัน + Android |
| 8 | ล็อก dependency และทดสอบติดตั้งใหม่ | ย้ายเครื่อง/ย้อนรุ่นได้สม่ำเสมอ | P1 | 1–2 วัน |
| 9 | หน้าสถานะพร้อมใช้งานและควบคุม WebSocket | เจ้าหน้าที่แก้ปัญหาได้และจำกัดผู้เข้าถึง | P1 เมื่อใช้ LAN | 2–3 วัน |
| 10 | สรุปความต้องการเพื่อส่งต่อฝ่ายขาย | เจ้าหน้าที่รับช่วงต่อได้โดยถามซ้ำน้อยลง | P2 ห้องขาย | 2–4 วัน |

## 1. วัด latency และ usage รายเทิร์น

**สิ่งที่พบ:** [turnlog.py](../../app/turnlog.py) มี session ID และบันทึกบทสนทนาแล้ว แต่ยังไม่มี timeline ที่เชื่อมช่วงจบเสียงผู้ใช้ → provider → tool → เสียงเริ่มเล่นจริง ฝั่ง OpenAI จัดการ `response.done` โดยยังไม่ได้รวบรวม usage; ฝั่ง Gemini ยังไม่พบการจัดการ `usage_metadata` ใน provider

**ข้อเสนอ:** เพิ่ม `turn_id` ต่อจาก session ID ที่ใช้ติดตามงาน และ timestamp จาก monotonic clock ในแต่ละฝั่ง เก็บเวลาจบเสียง, provider speech-end, first output audio, tool start/end, client playback-start และ interruption-stop แยก p50/p95 ตาม provider, VAD, อุปกรณ์ และชนิดงาน วัดช่วงเวลาภายใน browser/server ของแต่ละฝั่งให้ถูกต้อง ห้ามลบ timestamp จากคนละนาฬิกาโดยไม่เทียบเวลา และใช้เสียง loopback ภายนอกตรวจว่าการรายงานเริ่มเล่นใกล้กับเสียงที่ได้ยินจริงเพียงใด

แนวทางแยก end-of-turn, inference และเสียงตอบมีตัวอย่างจาก [LiveKit: Data hooks](https://docs.livekit.io/deploy/observability/data/) ซึ่งใช้เป็นแนวคิดการวัดได้โดยไม่จำเป็นต้องย้าย framework สำหรับ speech-to-speech ควรใช้ชื่อ metric ที่ตรงกับ event ที่สังเกตได้ ไม่สร้างค่า STT/TTS แยกขึ้นเองเมื่อ provider ไม่เปิดเผย

เก็บ usage ตาม event ที่ SDK/โมเดลที่ติดตั้งรองรับ พร้อมระบุหน่วยและป้องกันนับ event ซ้ำ แสดง token usage ก่อน แล้วค่อยคำนวณค่าใช้จ่ายจากตารางราคาที่ระบุวันที่และประเภทบัญชี Google อธิบายว่าประวัติที่คงอยู่ใน context มีผลต่อการคิดค่าใช้จ่ายแต่ละเทิร์น จึงไม่ควรประมาณต้นทุนจากนาทีเสียงอย่างเดียว หรือถือว่าเปิด Gemini แล้วฟรีเสมอ ดู [Live API best practices](https://ai.google.dev/gemini-api/docs/live-api/best-practices)

**เกณฑ์รับงานที่เสนอ:** ทุกเทิร์นทดสอบมี timeline ครบหรือระบุ metric ที่หาไม่ได้; สรุป p50/p95 และ usage แยก provider ได้; trace ไม่ใส่ credential/เนื้อหาส่วนตัวเป็น metric label; ไม่ใช้ session ID ที่เป็น credential มาปะปนกับ ID ติดตามงาน

## 2. ขยาย eval จากข้อความค้นหาเป็นประสบการณ์เสียงจริง

**สิ่งที่พบ:** ชุดปัจจุบันมีทั้งไทยและหลายภาษาแล้ว แต่ประเมินผลค้นหาอันดับแรกและใช้ข้อมูลชุดเดียวกันเสนอ threshold ยังไม่ได้แยกชุดสอบที่กันไว้จากการปรับค่าอย่างชัดเจน

**ข้อเสนอ:** เริ่มจากเสียงที่ทีมยินยอมบันทึก 100–200 utterances ครอบคลุมภาษาไทย/อังกฤษ/จีนตามสัดส่วนผู้ใช้จริง: เลขห้อง ราคา ทศนิยม ประโยคค้าง “เอ่อ…”, พูดแก้ตัวเลข, พูดแทรกหุ่น, เสียงทีวี, คำถามที่ไม่มีข้อมูล และเปลี่ยนภาษากลางประโยค แบ่งตามผู้พูด/กลุ่มความหมายเป็นชุดปรับค่าและชุดสอบ ไม่ให้ paraphrase ของคำถามเดียวกันหลุดไปอยู่คนละฝั่งจนคะแนนสูงเกินจริง

ให้คะแนนแยก 4 ส่วน: เข้าใจคำและตัวเลขสำคัญ, เลือก tool/ข้อมูลถูก, คำตอบมีแหล่งรองรับ, และการผลัดกันพูด ใช้เจ้าหน้าที่ตรวจตัวเลขกับแหล่งข้อมูลจริง; ใช้ model judge ช่วยจัดกลุ่ม/ให้คะแนนได้เมื่อเทียบความเห็นกับคนแล้ว [OpenAI: Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices) สนับสนุน eval ตามงานจริง การกันชุดสอบ และการใช้มนุษย์ตรวจความหมายของคะแนน

**ข้อสังเกตโค้ดที่ควรแก้พร้อมงานนี้:** ใน `scripts/eval_search.py` สาขา `if not hits` เพิ่มค่าลง positives/negatives แต่ไม่เพิ่ม `wrong` เมื่อเป็นคำถามที่ควรค้นเจอ ทำให้กรณีนั้นถูกนับเป็น correct ในสูตรท้ายไฟล์ได้ นอกจากนี้ commercial ที่ปฏิเสธก่อนค้นไม่ได้รวมใน denominator เดียวกัน ควรเปลี่ยนเป็นผลรายกรณีที่มี `pass/fail/skipped` แล้วรวมจากรายการเดียว ข้อนี้พบจากการอ่าน control flow ยังไม่ได้รันจำลองในรอบ research

**เกณฑ์รับงานที่เสนอ:** ผลทุกครั้งระบุ dataset version, model/config, จำนวนกรณีจริงและ skipped; กรณีควรเจอแต่ไม่เจอต้อง fail; เก็บคะแนนรายภาษา/สภาพเสียง; การกล่าวราคาหรือสถานะห้องผิดถือเป็นข้อผิดพลาดสำคัญแยกจากการเปิดภาพผิด

## 3. ทำให้ความรู้มีเจ้าของ รุ่น และวันสิ้นสุดการใช้

**สิ่งที่พบ:** การแก้รีวิวทำให้ `_entry()` แยก draft/approved แล้ว ข้อมูลราคา live มี source/updated_at และโปรฯ ใช้ flag `active` อยู่ แต่เนื้อหาในสไลด์ คลังเว็บ และบทบรรยายยังไม่ได้มีสัญญา metadata ร่วมกันครบวงจร จำนวน 64 scripts ที่ยังไม่มี flag อนุมัติคือรายการรอตรวจ ไม่ใช่สิทธิ์ให้ตั้ง approved อัตโนมัติ

**ข้อเสนอเชิงออกแบบจากโค้ด:** ให้เนื้อหาสำหรับลูกค้าใช้ `source_id`, `source_version`, `approved_by`, `approved_at`, `effective_from`, `effective_until` ตามความเหมาะสม แยกข้อความจากเอกสารต้นทางออกจากคำบรรยายที่ AI สร้าง หน้าตรวจเนื้อหาแสดงต้นฉบับ/ร่าง/diff และเผยแพร่เป็นรุ่นที่ย้อนกลับได้ ตรวจ fingerprint เพื่อให้แก้ข้อความหลังอนุมัติแล้วกลับเข้าคิวตรวจ

ข้อมูลราคาและสถานะห้องยังอ่านจากระบบขายที่เป็นเจ้าของข้อมูล; เพิ่มเวลาที่ดึงมาและพฤติกรรมเมื่อระบบขายเข้าไม่ถึง วันหมดอายุของโปรฯ ต้องเพิ่มร่วมกับ schema ของระบบขาย ไม่อนุมานจาก `updated_at` ซึ่งหมายถึงเวลาแก้ไข ไม่ใช่วันหมดอายุ แสดงแหล่งอ้างอิงที่อ่านง่ายบนจอ เช่น “ระบบขาย ณ เวลา…” หรือ “เอกสารฉบับ…”

**เกณฑ์รับงานที่เสนอ:** เนื้อหาหมดอายุ/ถอนอนุมัติไม่ถูกนำมาอ้างเป็นข้อมูลปัจจุบัน; เนื้อหาแก้หลังอนุมัติต้องตรวจใหม่; เมื่อราคาเข้าไม่ถึงต้องบอกว่าไม่ทราบราคาปัจจุบัน; สามารถย้อนรุ่นเนื้อหาได้โดยไม่แตะข้อมูลขายจริง แนวทางนี้เป็นข้อเสนอของรายงาน ไม่ใช่ข้อกำหนดสำเร็จรูปจาก provider

## 4. ทดลอง Hybrid VAD และปรับเสียงบนฮาร์ดแวร์

Google ระบุรูปแบบ Hybrid VAD: เปิด automatic VAD ไว้ให้ server จับต้นเสียง แล้ว client ใช้ VAD ส่ง `audio_stream_end` เมื่อจบเสียง เพื่อให้ finalize ได้เร็วขึ้น โดยยังมี server VAD เป็น fallback หาก client ไม่ส่งสัญญาณ และเตือนว่า threshold ที่แรงเกินไปอาจตัดคำ ดู [Live API capabilities — Hybrid VAD](https://ai.google.dev/gemini-api/docs/live-api/capabilities)

**ช่องว่าง/วิธีทดลอง:** โค้ดมี Gemini automatic และ local manual VAD แล้ว จึงเพิ่ม hybrid เป็นทางเลือกภายใต้ feature flag และเปรียบเทียบทั้ง 3 แบบด้วยเสียงเดียวกัน ก่อนทำต้องตรวจ SDK/โมเดลที่ติดตั้งรองรับพฤติกรรมตามเอกสารปัจจุบัน ใน manual mode ให้คง `activity_start/activity_end` ตามสัญญาเดิม; ห้ามส่ง `audio_stream_end` ปะปนกับ manual mode ที่ปิด automatic VAD

ฝั่ง browser ขอ AEC อยู่แล้ว แต่การตั้ง `echoCancellation: true` ไม่ใช่หลักฐานว่าหุ่นจริงตัดเสียงสะท้อนได้ดี ต้องตรวจเส้นทางเสียงบน Android ตาม [robot-integration.md](../robot-integration.md): เล่นเสียงจากหุ่นและให้คนพูดทับที่ระยะ 1, 2, 4 เมตร วัด false interruption, ต้นคำหาย, ปลายคำหาย และเวลาเสียงหุ่นหยุด อย่าลดช่วง silence เพียงเพื่อให้ค่า latency ดูดี

**เกณฑ์รับงานที่เสนอ:** เริ่มตั้งเป้าให้ p95 เวลารอหลังพูดจบดีขึ้นอย่างน้อย 15% จาก baseline โดยอัตราตัดคำ/ตัวเลขผิดไม่แย่ลง; รายงานจำนวนตัวอย่างและการกระจายคะแนนเพื่อเห็นความไม่แน่นอน เป้าหมายนี้เป็นเกณฑ์เริ่มคุยที่เสนอ ยังไม่ใช่ผลที่รับรองว่าจะได้

## 5. ปรับ retrieval โดยรักษาความเร็ว

โครงสร้างปัจจุบันสอดคล้องกับแนวทาง [Anthropic: Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval) ซึ่งรวมบริบทของ chunk, BM25 และ embeddings และ [Sentence Transformers: Retrieve & Re-Rank](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html) ซึ่งใช้ CrossEncoder เรียง candidate อีกขั้น ผลของบทความไม่ได้รับรองว่าจะเพิ่มคะแนนในเด็คนี้เท่ากัน

**ข้อเสนอ:** ใช้ชุดสอบข้อ 2 เทียบ lexical, hybrid และ hybrid+reranker แยกเวลาครั้งแรก/หลัง warm-up วัด Recall@5, ความถูกต้องของอันดับแรก, อัตรายอมรับคำถามที่ไม่มีข้อมูล และเวลาค้น p95 ตรวจแยกภาษาไทย/อังกฤษ/จีน เลือกโมเดลที่รองรับภาษางานจริงก่อนทดลอง; ยังไม่มีหลักฐานพอให้ฟันธงเลือก reranker ตัวใด

เพิ่มผลตอบกลับเมื่ออันดับต้นสูสีกัน: ถามแยกความหมายสั้น ๆ เช่น “ฟิตเนสหลักหรือ Bungee Gym คะ” แทนการเดาสไลด์ ตรวจ `source_version` ก่อนใช้ embeddings/cache หลังแก้เด็ค และต่อยอด contextualization เฉพาะ chunk ที่ปัญหาเกิดจากขาดบริบท

**เกณฑ์รับงานที่เสนอ:** คะแนนบนชุดสอบดีขึ้นโดย p95 อยู่ในงบเวลาที่กำหนดจากข้อ 1; การค้นไม่เจอไม่ถูกกลบด้วย fallback ที่รายงานว่า semantic ทำงาน; จะเปิด reranker เป็นค่าเริ่มต้นเมื่อผลทั้งความแม่นยำและเวลาผ่าน

## 6. ทดสอบคุยนานและสายหลุดหลายรูปแบบ

Google อธิบายขีดจำกัดของอายุ connection และแนะนำ compression/resumption/GoAway สำหรับการต่อเนื่องข้าม connection ใน [Live API session management](https://ai.google.dev/gemini-api/docs/live-api/session-management) โปรเจคมีส่วนเหล่านี้แล้ว สิ่งที่ควรเพิ่มคือหลักฐานว่าพฤติกรรมต่อเนื่องถูกต้องภายใต้ความล้มเหลวจริง

**ข้อเสนอ:** เพิ่ม fault injection สำหรับ GoAway ขณะกำลังพูด, socket หลุดก่อน/หลัง tool result, resumption handle ใช้ไม่ได้, rate limit, provider ตอบช้า และ browser reconnect ระหว่างเปลี่ยนสไลด์ ทดสอบ bounded retry/backoff ตามชนิด error; ไม่ retry คำสั่งพิมพ์/เดินซ้ำเพียงเพราะหลุดก่อนทราบผล และไม่ส่งต่อความจำส่วนตัวข้าม provider/session เมื่อ fallback

**เกณฑ์รับงานที่เสนอ:** ผ่าน soak test 2 ชั่วโมงบนเครื่องทดสอบ มีการ reconnect หลายครั้ง, ไม่เกิดเสียงซ้อน/งานค้างสะสม/คำสั่งผลข้างเคียงซ้ำ; ระบบแสดงสถานะกำลังเชื่อมต่อใหม่และจบการพยายามได้เมื่อเกินขอบเขต ส่วนการสลับ provider อัตโนมัติควรทำภายหลังเมื่อกำหนดการรักษาบริบทและสิทธิ์ได้ชัดเจน

## 7. ยืนยันคำสั่งและผลจากหุ่นยนต์

**สิ่งที่พบ:** `robot_link.send()` รู้ว่าส่งผ่าน WebSocket ได้ แต่การส่งสำเร็จยังไม่ยืนยันว่า Android รับหรือ SDK เริ่มทำงาน แม้จะมี arrival callback/timeout แล้ว ก็ยังไม่มี command ID ที่เชื่อมทุกช่วงของคำสั่ง การกันงานซ้ำใน registry ช่วยขณะงานค้าง แต่ยังไม่ใช่การ deduplicate ข้าม reconnect/restart ส่วน `Tool.confirm` ระบุในโค้ดว่า informational

**ข้อเสนอ:** ออกแบบข้อความ `command_id`, `session_id`, deadline และ payload ที่ผ่าน validation โดยแยกสถานะ `sent`, `accepted`, `running`, `succeeded`, `failed`, `unknown` ให้ Android ACK การรับคำสั่งและรายงานผล SDK ภายใต้ ID เดิม เก็บ dedupe window และปฏิเสธ ID เดิมที่เปลี่ยน args; ทดสอบ heartbeat และสถานะไม่ทราบเมื่อขาดการติดต่อ การหยุดจริงเมื่อการสื่อสารขาดต้องอาศัยนโยบายฝั่งอุปกรณ์และทดสอบจริง

แนวคิด request ID และการ retry ที่ไม่สร้างผลซ้ำอ้างอิง [Amazon Builders’ Library: Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/) นี่เป็น pattern สำหรับ bridge ที่เราควบคุม ไม่ได้อ้างว่า Aobo SDK มีระบบ idempotency นี้ให้แล้ว

confirmation สำหรับงานที่ต้องยืนยันควรผูกกับคำสั่งและ args ที่ผู้ใช้เห็น มีอายุ และใช้ได้ครั้งเดียว ถ้าผู้ใช้สั่งงานนั้นไว้อย่างชัดเจนและครบแล้วให้ใช้เป็นหลักฐานตามนโยบาย ไม่บังคับถามซ้ำทุก tool; หาก args เปลี่ยนจึงให้ตรวจใหม่ คำสั่งหยุดฉุกเฉินต้องไม่ติดขั้นตอนยืนยัน

**เกณฑ์รับงานที่เสนอ:** ส่งคำสั่ง ID เดิมซ้ำ 10 ครั้งแล้วอุปกรณ์เริ่มงานครั้งเดียวในช่วง dedupe ที่ระบุ; ACK หายไม่ทำให้รายงานว่าจบแล้ว; arrival เก่าปิดงานใหม่ไม่ได้; ไม่มี ACK ต้องไม่กล่าวว่าหุ่นหยุดหรือถึงปลายทางแน่นอน ต้องทำร่วมกับ Android และทดสอบบนอุปกรณ์

## 8. ทำให้ติดตั้งและย้อนรุ่นได้เหมือนเดิม

**สิ่งที่พบ:** [requirements.txt](../../requirements.txt) ใช้ lower bound `>=` และรวม runtime/test/optional หลายกลุ่ม ยังไม่พบ lockfile หรือ `.github` workflow ใน working tree ส่วน local embeddings และ reranker import `sentence_transformers` แต่แพ็กเกจนี้ไม่อยู่ใน requirements

**ข้อเสนอ:** แยก base, dev, local-search, face, browser และ hardware dependencies ให้สอดคล้องกับ feature สร้าง lock จากสภาพแวดล้อมที่ทดสอบแล้วและระบุ Python version ใช้ `uv` หรือ workflow lock ที่เทียบเท่าได้ หากเลือก uv ให้ตรวจ lock กับ metadata และติดตั้งตาม lock ใน environment ใหม่ก่อนแทนที่เครื่องใช้งาน เอกสาร [uv: Locking and syncing](https://docs.astral.sh/uv/concepts/projects/sync/) อธิบาย `--locked` ซึ่งตรวจความสอดคล้อง และการ sync ที่จัด environment ตาม lock

เพิ่ม Windows CI สำหรับ tests หลัก, Python/JS syntax และ clean-install smoke ของ feature ที่เลือก แยก job ที่ต้องดาวน์โหลดโมเดล/เรียก provider/hardware ออกจาก fake tests เพื่อให้เห็นว่าอะไรได้ทดสอบจริง บันทึกรุ่น/แฮชของ wake, face, embeddings model และ rollback recipe คู่กับรุ่นแอป

**เกณฑ์รับงานที่เสนอ:** เครื่อง Windows ใหม่ติดตั้งตามกลุ่มที่เลือกแล้ว boot ได้; local-search ใช้ encoder ได้จริงเมื่อเลือก extra; ไม่มีการตกไป lexical โดยไม่แจ้ง; รุ่นแอปและ asset/model manifest เดิมกู้กลับได้

## 9. หน้าความพร้อมใช้งานและ WebSocket ที่เหมาะกับ LAN

**สิ่งที่พบ:** `/health` คืน `ok: true` พร้อมข้อมูล config และสถานะบางส่วน; มี `units.live_probe()` ตรวจ inventory ตอนเริ่มระบบอยู่แล้ว แต่ยังไม่มีภาพรวมความพร้อมล่าสุดของทุกส่วน ตัวตรวจ WebSocket ตรวจ token แล้ว แต่ยังไม่พบ explicit Origin allowlist ใน handshake; CORS middleware สำหรับ HTTP ไม่ทดแทนการตรวจ WebSocket Origin

**ข้อเสนอ:** คง endpoint เดิมเพื่อความเข้ากันได้ เพิ่ม readiness ที่แยก provider configured/last success, inventory, slides, optional models และ robot โดยตรวจตาม feature ที่เปิดจริง มี timestamp/TTL และ cached probe ที่จำกัดเวลา หน้าเจ้าหน้าที่แสดง “พร้อม/ใช้งานบางส่วน/ต้องแก้การตั้งค่า” พร้อมขั้นตอนแก้ตรงสาเหตุ ไม่เรียก paid model ทุกครั้งที่เปิด health และไม่แสดงรายละเอียดภายในแก่ผู้ไม่ได้รับสิทธิ์

เพิ่ม Origin allowlist สำหรับ browser, นโยบาย native Android ที่อาจไม่มี Origin พร้อม device credential, จำกัดขนาด/อัตราของ JSON และ audio แยกตามชนิดข้อความ, schema validation และลดอายุ credential ที่ใช้เข้าระบบเมื่อขยายไปหลายเครื่อง token ใน URL ควรมีทางแลกเป็น session ที่จำกัดสิทธิ์และไม่ถูกเขียนลง access log แนวทางตรงกับ [OWASP: WebSocket Security](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html) โดยต้องออกแบบเพดานให้รองรับเสียงปกติ ไม่คัดลอกอัตราข้อความของแชตมาใช้กับ PCM

**เกณฑ์รับงานที่เสนอ:** จำลอง API/DB/โมเดลหายแล้ว readiness แสดงสาเหตุ; feature ที่ปิดไม่ทำให้เครื่องทั้งเครื่องขึ้น failed; browser จาก origin ที่ไม่ได้อนุญาตเข้าไม่ได้แม้เปิด CORS กว้าง; client ปกติส่ง audio 20 ms ต่อเนื่องได้โดยไม่ถูกตัดจาก rate limit

## 10. สรุปความต้องการและส่งต่อให้ฝ่ายขาย

**ข้อเสนอเชิงผลิตภัณฑ์จากการเทียบโค้ด:** ต่อยอด inventory/compare/quotation ที่มีอยู่เป็นการ์ดสรุป: ห้องที่สนใจ, งบที่ผู้ใช้บอก, เงื่อนไขที่ยืนยันแล้ว, คำถามที่ยังไม่มีคำตอบ และลิงก์ข้อมูลต้นทาง ให้เจ้าหน้าที่กดรับช่วงต่อได้ในจอเดิม เริ่มจาก draft ที่ตรวจแก้ได้ก่อนเชื่อม CRM หรือช่องทางส่งจริง

อย่าให้โมเดลสร้างราคาใหม่ในสรุป ให้ใส่ reference ไปยัง quotation/ข้อมูลขายที่ตรวจสอบได้ แยกข้อมูลที่ผู้ใช้พูดกับข้อสรุปของผู้ช่วย เก็บเฉพาะข้อมูลที่จำเป็นและผู้ใช้ตกลงให้ส่ง พร้อม clear หน้าจอเมื่อจบสายตามนโยบายเดิม

**เกณฑ์รับงานที่เสนอ:** เจ้าหน้าที่เปิดสรุปแล้วเห็นแหล่งที่มาของตัวเลขทุกจุด; สิ่งที่ไม่ยืนยันมีป้ายชัด; ไม่มีการส่งออกโดยไม่มีการอนุญาต; วัดเวลารับช่วงต่อและจำนวนคำถามซ้ำก่อน/หลังทดลองกับทีมขาย ข้อนี้ยังเป็นสมมติฐานเรื่องประโยชน์ทางธุรกิจ ต้องทดลองกับผู้ใช้งานจริง

## การทดลองที่น่าสนใจ แต่ควรมี baseline ก่อน

**OpenAI WebRTC + server sideband:** OpenAI แนะนำ WebRTC สำหรับ client browser/mobile เพื่อประสิทธิภาพที่สม่ำเสมอ และมี sideband ให้ server คงการควบคุม tools/business logic ดู [Realtime WebRTC](https://developers.openai.com/api/docs/guides/realtime-webrtc) และ [Server-side controls](https://developers.openai.com/api/docs/guides/realtime-server-controls) เหมาะเป็น prototype ฝั่ง OpenAI โดยเฉพาะเมื่อมี browser หลายเครื่อง/เครือข่ายแปรปรวน ต้องวัด barge-in, latency, reconnect และตรวจสิทธิ์ tools ครบก่อนใช้จริง ไม่ได้เป็นทางเปลี่ยน Gemini transport โดยตรง ประมาณ prototype 3–5 วัน ไม่รวม production hardening

**Thai semantic end-of-turn:** พบงาน [Thai Semantic End-of-Turn Detection for Real-Time Voice Agents](https://arxiv.org/abs/2510.04016) ที่ศึกษาการตัดสินจบเทิร์นจากข้อความไทย โดยใช้ subtitle transcripts และลักษณะภาษาไทย งานนี้เป็นเหตุผลให้สร้างชุดทดสอบไทยเฉพาะทางได้ แต่ยังไม่ใช่หลักฐานว่าโมเดลพร้อมใช้กับเสียงห้องขาย/หุ่นตัวนี้ ต้องตรวจโมเดลที่นำมาใช้ได้ การปล่อย artifact/license และผลบนเสียงจริงก่อน อาจพิจารณาหลัง hybrid VAD หากยังพบปัญหาหยุดกลางประโยค

## แผนเริ่มต้นที่คุ้มที่สุด

1. **ชุดแรกประมาณ 5–8 วัน:** metric ขั้นต่ำ + แก้โครงผล eval/แยกชุดสอบ + dependency lock และ clean-install smoke ได้ฐานเปรียบเทียบที่ใช้ซ้ำได้ ทุกชุดแก้บันทึกใน CHANGELOG พร้อมผลตรวจจริง
2. **ทำคู่กับเจ้าของข้อมูล:** ให้ฝ่ายขายตรวจ 64 บทบรรยายและข้อมูลที่ยังรอการรับรอง แล้ววาง workflow metadata/expiry ตามข้อ 3; การตรวจอาจไม่จบทั้งหมดในรอบเดียว
3. **รอบถัดไปตามผลวัด:** เปรียบเทียบ VAD และ retrieval, ทำ fault injection/soak test แล้วเลือกเฉพาะการปรับที่ผ่านเกณฑ์
4. **ก่อนให้หุ่นเดินจริง:** ทำ command ACK/idempotency กับ Android และตรวจการหยุด/ขาดการติดต่อบนพื้นที่ทดสอบตามเอกสาร integration
5. **เมื่อความแม่นยำและการใช้งานนิ่ง:** ทดลองสรุปส่งต่อฝ่ายขาย; ถ้าเน้น Emma ส่วนตัว ให้ยกงานนี้ออกและจัดลำดับ confirmation/ความพร้อมอุปกรณ์แทน

การเพิ่ม multi-agent orchestration, ย้าย vector database หรือ fine-tune โมเดลยังควรรอให้ผล eval ชี้ปัญหาที่วิธีเหล่านั้นแก้ได้ก่อน ส่วนการเปลี่ยนโมเดลเสียงควรเปรียบเทียบภาษาไทย/การเรียก tools/ต้นทุนกับ baseline เดียวกัน

## ขอบเขตการตรวจครั้งนี้

- อ่านโค้ด/เอกสารใน working tree และนับ metadata แบบไม่แสดงข้อมูลส่วนตัว ตรวจเอกสารเว็บที่ลิงก์ไว้ในแต่ละข้อ โดยข้อมูลเว็บเป็น snapshot ณ วันที่ค้นคว้า
- แยกข้อเท็จจริงจากโค้ด, ความสามารถตามเอกสาร provider และข้อเสนอ/เป้าหมายของผู้เขียน ไม่อ้างผล benchmark ของแหล่งอื่นเป็นผลของโปรเจค
- ไม่ได้รัน paid API, inventory จริง, browser audio, กล้อง, เครื่องพิมพ์ หรือหุ่นยนต์; ยังไม่มีตัวเลข latency/cost/accuracy ใหม่จาก production
- ไม่รัน `eval_search.py` ในรอบนี้ เนื่องจาก workflow มีการเขียน query cache และอาจเรียก embeddings ตาม configuration; ตรวจตรรกะจาก source โดยตรง
- รอบ research เพิ่มเอกสารนี้และบันทึกประวัติเท่านั้น; ผล tests 1,093 passed เป็นผลรอบแก้โค้ดก่อนหน้า รายละเอียดดู [CHANGELOG.md](../../CHANGELOG.md)
