# ผลทดสอบข้อมูลรับจากบอร์ดแขนจริง

ผลต่อเนื่อง: [ทดสอบด้านหน้าช่อง 7/8/11](robot-front-camera-test-2026-09-11.md) พบภาพหัวหันจากช่อง 7 และหัวก้มจากช่อง 8 ส่วนช่อง 11 ยังไม่เห็นขยับ

> **แก้ข้อสรุปจากการตรวจต่อเวลา 13:03–13:06 น.: บอร์ดตอบจริง** usbmon พบ `#STOP+OK...\r\n` ครั้งละ 13 ไบต์ ตัวอ่านก่อนหน้านี้พลาดข้อมูล แก้ด้วย `timeout --foreground` และ `adb exec-out` แล้วรับครบ 26 ไบต์ต่อ stop สองครั้ง ดังนั้นตัวเลข 0 ไบต์ในประวัติด้านล่างเป็นผลของตัวอ่านเดิม ไม่ใช่หลักฐานว่าบอร์ดไม่ตอบ รอบ up ช่อง 1 รับ `#CC\r\n` เพิ่มด้วย แต่ผู้ใช้ยังไม่เห็นการเคลื่อนไหว

วันที่ 11 กันยายน 2026 เวลาเริ่มรอบที่เก็บข้อมูลครบ 12:51:23 น. (Asia/Bangkok)

ผู้ใช้อนุญาตให้ทดลองจริงและแจ้งว่าอยู่ใกล้หุ่น รอบแรกส่งเฉพาะคำสั่งหยุด ต่อมาทดลอง centre และ up ช่อง 1 หลังยืนยันว่าเข้าถึงสวิตช์หลัก ไม่ส่งกลุ่มท่าหรือ home

## วิธีตรวจ

- อ่านอุปกรณ์สด พบ `/dev/ttyUSB10` ผูกกับ USB `9-1.4` โดย VID/PID `1a86:7523` (CH340)
- ไม่พบ PID ของ `com.aobo.robot.ai3` ในการตรวจก่อนทดสอบ ไม่เปิดแอปขึ้นมา
- อ่าน stty: 115200 baud, CS8, parity ปิด, 1 stop bit, raw input/output และ echo ปิด มี `hupcl` เปิดอยู่ ไม่เปลี่ยนค่า baud หรือ DTR/RTS ในสคริปต์นี้ อย่างไรก็ตามการเปิด/ปิด tty มีผลตาม line configuration ของไดรเวอร์ จึงไม่อ้างว่าไม่มีผลทางไฟฟ้า
- เปิด read descriptor ให้พร้อมก่อนเรียก `/arm/command` ด้วย action `stop` ซึ่งระบบเดิมเขียน `#STOP` สองครั้งห่างกันประมาณ 60 ms และล็อกการส่งต่อ
- เก็บ stdout เป็นไบต์ด้วย reader จำกัดเวลา 5 วินาที พร้อมเก็บ stderr และ exit status; ไม่เรียก query ที่เดา schema

## ผลที่ได้

| รายการ | ผล |
|---|---|
| API ตอบ | `ok=true`, `stop_write_ok=true` |
| จำนวนข้อมูลที่อ่านได้ในรอบที่เก็บครบ | **0 ไบต์** |
| พบ `#STOP+OK` | ไม่พบ |
| ตัวอ่านจบ | exit 137 ตาม `timeout -s KILL 5` ที่กำหนด |
| timeout ฝั่งคอม | false |
| stderr ตัวอ่าน | ว่าง |
| สถานะส่งแขนหลังทดสอบ | `armed=false` |
| ค่าตำแหน่งที่วัดจริง | ยังไม่มี |
| ยืนยันการหยุดแขนจากการเห็นจริง | ยังไม่มี |

รอบแรกใช้ SIGTERM และรอข้อมูลด้วย communicate แล้วติด timeout ฝั่งคอม จึงไม่มี RX ที่เก็บครบและไม่ใช้รอบนั้นอ้างว่าไม่มี ACK ส่วนคำสั่ง stop ของรอบแรกถูกเรียกไปแล้ว แก้การอ่านเป็นเก็บข้อมูลระหว่างทางและ timeout ด้วย SIGKILL ก่อนทำรอบที่รายงานข้างต้น ไม่พบ process cat/timeout ค้างในการตรวจหลังรอบแรก

หลักฐานดิบเก็บในไฟล์ ignored `data/robot-inspection/console-ui-20260911/stop-rx-probe.json` และสคริปต์ทำซ้ำอยู่ที่ [probe_robot_arm_stop.py](../scripts/probe_robot_arm_stop.py) ต้องระบุ `--send-stop` ชัดเจน

## ขอบเขตข้อสรุป

ยืนยันได้ว่า **ตัวอ่านนี้ไม่ได้รับไบต์ในช่วงทดสอบ** ไม่ใช่ข้อพิสูจน์ว่าบอร์ดไม่รองรับ feedback, เซอร์โวไม่มีไฟ, สาย RX เสีย หรือแขนหยุดแล้ว การเขียนสำเร็จยังเป็นรายงานของเชลล์และ API ไม่ใช่เซนเซอร์วัดข้อต่อ

การวัดการเคลื่อนไหวจริงต้องมีค่าตำแหน่งจากเซนเซอร์ที่ตรวจสอบได้ หรือภาพ/ผู้สังเกตข้างหุ่น หากใช้ผู้สังเกต ผลต้องติดป้ายว่าเป็นการสังเกตของผู้ใช้ ไม่แปลงค่า PWM เป็นองศาจริงโดยไม่มีการสอบเทียบ

ขณะจบรอบ stop ยังไม่ทดสอบขยับช่อง 1 เพราะรอยืนยันการเข้าถึงสวิตช์หลัก ต่อมาผู้ใช้ตอบว่า “ปิดได้” จึงทดสอบตามรายการด้านล่าง

## ทดสอบคำสั่งช่อง 1 หลังผู้ใช้ยืนยันปิดไฟได้

เริ่มเวลา 12:54:21 น. ตรวจซ้ำก่อนทดสอบว่าไม่พบ PID แอปผู้ขายและพอร์ตยังอยู่บน CH340

1. เรียก action `arm` เพื่อปลดล็อกเฉพาะระบบส่งเดิม
2. เรียก `centre` ช่อง 1 เพียงครั้งเดียว ระบบใช้ `#1P1500T9999` ตามค่าปัจจุบันใน `app/robot_arm.py` (9999 ms ไม่ใช่การสอบเทียบมุมจริง)
3. หลัง API ตอบสำเร็จ รอ 2 วินาทีแล้วเรียก `stop` ใน finally ส่งสองครั้งและล็อกกลับ
4. เก็บ RX ตลอดหน้าต่าง 5 วินาทีที่เริ่มก่อนคำสั่ง

ผล: motion API ตอบ `ok=true, at=1500`; stop API ตอบ `stop_write_ok=true`; RX **0 ไบต์**; ไม่พบ `#STOP+OK`; reader exit 137 ตามการจำกัดเวลา ไม่มี local timeout หรือ stderr; สถานะท้ายรอบ `armed=false`

นี่คือ **ทดลองส่งคำสั่งกับบอร์ดจริงแล้ว** แต่ยังไม่ใช่หลักฐานว่าข้อต่อขยับหรือหยุดใน 2 วินาที ส่งคำถามให้ผู้ใช้ซึ่งอยู่ใกล้หุ่นรายงานว่าส่วนไหนขยับและหยุดเมื่อใด รอคำตอบก่อนสั่งต่อ ไม่ทดสอบช่องอื่นหรือกลุ่มท่าอัตโนมัติ

หลักฐานดิบ `data/robot-inspection/console-ui-20260911/channel1-live-probe.json` ไม่มีข้อมูลตำแหน่งจริง การทดลองใช้ flag เพิ่ม `--centre-channel-1` ซึ่งต้องมีคนดูหุ่นและเข้าถึงสวิตช์หลัก; หากไม่ระบุ flag นี้ สคริปต์จะส่ง stop อย่างเดียว

## พบ ACK ที่ USB และแก้ตัวอ่าน

เวลา 13:03:13 น. ใช้ usbmon ที่เครื่องเปิดไว้แล้ว กรองเฉพาะ `9:006` (CH340 ที่ตรวจจาก sysfs) ก่อนข้อมูลออกจากหุ่น ไม่เก็บ traffic ของกล้องหรือไมค์ พบ:

```text
TX 7 bytes: 23 53 54 4f 50 0d 0a                 #STOP CRLF
RX 13 bytes: 23 53 54 4f 50 2b 4f 4b 2e 2e 2e 0d 0a   #STOP+OK... CRLF
```

พบ TX และ RX อย่างละสองครั้ง bulk completion status เป็น 0; ตัวอ่าน tty รุ่นเดิมยังรายงาน 0 ไบต์ในรอบเดียวกัน จึงยืนยันว่ารุ่นเดิมพลาดข้อมูล

ตาม [เอกสาร Linux usbmon](https://docs.kernel.org/usb/usbmon.html) ข้อมูลนี้เป็นเหตุการณ์ระหว่างไดรเวอร์กับ host controller ไม่ใช่การวัดแรงดันบนสายเซอร์โวหรือเซนเซอร์ข้อต่อ โดยจับคู่ URB submission/callback ผ่าน tag และแปลข้อมูล hex ตาม data length

แก้ `timeout --foreground` แล้วตัวอ่านเริ่มรับ ACK ได้ (28 ไบต์ เนื่องจากชั้น adb shell เพิ่ม CR); เปลี่ยนเป็น `adb exec-out` แล้วได้ raw **26 ไบต์** ตรงกับ USB: `#STOP+OK...\r\n` สองชุด การแยก process group ของ timeout เกี่ยวข้องกับปัญหาตัวอ่าน แต่ไม่ได้เก็บ signal trace จึงยังไม่อ้างว่าพิสูจน์ SIGTTIN โดยตรง

หลักฐานใน `data/robot-inspection/console-ui-20260911/usb-stop/`, `stop-rx-foreground.json`, `stop-rx-exec-out.json` ค่า DTR/RTS มี control transfers ตอนเปิด/ปิดตามไดรเวอร์ ไม่พบหลักฐานว่าทำให้ MCU รีเซ็ตในรอบนี้

## ทดสอบ +40 และสิ่งที่ผู้ใช้เห็น

เวลา 13:06:08 น. หลังยืนยัน last-commanded ช่อง 1 เท่ากับ 1500 เรียก up เพียงครั้งเดียว → API ตอบ at=1540 (โค้ดใช้ `#1P1540T800`) จากนั้นรอ 2 วินาทีแล้ว stop/ล็อกกลับ

รับ raw **31 ไบต์**:

```text
#CC\r\n
#STOP+OK...\r\n
#STOP+OK...\r\n
```

ตรวจ `SerialToothManagerCH340.handleCompletePacket`: parser เช็ก `#CC` และผลรวมไบต์แรกสามตัวเทียบ `ARM_ONE_ACTION_END`; ค่าใน `SerialdataService.<clinit>` คือ 169 ตรงกับ 35+67+67 ชื่อค่าคงที่สื่อถึงจบ action หนึ่งรายการ **ไม่ใช่ encoder และไม่มีเลขตำแหน่งหรือมุมอยู่ใน packet นี้** ตัวแปร isArmStartAction ที่ parser ปรับยังขึ้นกับ robotSendResetCmd จึงไม่ใช้เป็นคำยืนยันทางกล

ผู้ใช้ตอบว่า “ไม่เห็น” ในรอบ centre และ “ไม่เห็รอะไรเลย” ในรอบ up จึงบันทึกว่า **ผู้ใช้ไม่เห็นการเคลื่อนไหว** ไม่ใช่ผลกล้องพิสูจน์ว่าเคลื่อนที่เป็นศูนย์ และยังระบุผังข้อต่อไม่ได้ ผู้ใช้ตรวจว่าปุ่มแดงเด้งขึ้นแล้ว แต่ยังไม่ได้วัดแรงดันไฟเลี้ยงเซอร์โว

หลังรอบนี้ `armed=false`, last-commanded ช่อง 1=1540 ไม่มีคำสั่งช่องอื่น กลุ่มท่า หรือเพิ่มระยะอัตโนมัติ หลักฐาน `channel1-step-live.json`
