# CP2102: ปุ่มแดง IO7 และการตรวจรีเลย์แขน

## ข้อสรุปจากเครื่องจริง

อ่าน CP2102 ที่ USB `9-1.2`, VID/PID `10c4:ea60` ได้จริง โดยผูกไดรเวอร์ cp210x ชั่วคราว พบ `/dev/ttyUSB11` และเก็บข้อมูลที่บอร์ดส่งออกเอง ไม่ต้องส่ง handshake หรือคำขอเซนเซอร์ในการทดลองรับข้อมูลนี้ เปิดที่ 115200 8N1/raw แล้วคืนค่า stty และ unbind ทุกครั้ง

**ยืนยันปุ่มแดงเข้าบิต IO7 ได้แล้ว** ด้วยลำดับก่อนกด → กดค้าง → ปล่อย:

| รอบ | เวลา UTC | เฟรม IO ที่ checksum ผ่าน | ค่า IO | IO7 |
|---|---|---:|---:|---|
| ก่อนกด | 07:10:18 | 196 | 0 | false |
| ผู้ใช้ยืนยันกดค้าง | 07:12:11 | 197 | 64 / 0x40 | true |
| ผู้ใช้ยืนยันปล่อย | 07:13:33 | 197 | 0 | false |

เวลาประเทศไทยคือ UTC+7 ทุกตัวอย่าง IO ในแต่ละรอบตรงกัน ไม่มี candidate checksum เสีย พบแพ็กเก็ตขนาด 27 และ 14 ไบต์ร่วมด้วย โค้ดผู้ขาย dispatch ข้อมูลเหล่านี้ไปส่วนเซนเซอร์/อุปกรณ์อื่น แต่รายงานนี้ไม่ตีความว่าเป็นแรงดันเซอร์โวหรือค่าตำแหน่งแขน

หลักฐาน: `data/robot-inspection/console-ui-20260911/cp210-passive-status.json`, `cp210-estop-pressed.json`, `cp210-estop-released.json` และไฟล์ `*-decoded.json` ทั้งหมด ignored การอ่านรอบแรกมี 2520 transport bytes แต่เป็น serial frames ที่ตรวจสอบได้ 2488 bytes ส่วนต่างเป็นข้อความสถานะที่ remote stderr ถูก ADB exec-out รวมเข้ามา ห้ามเรียก transport ทุกไบต์ว่าข้อมูลบอร์ด

## แก้สาขาโค้ดที่เคยโยงผิด

`SerialdataService.sendCmdtowhichUart` ที่ CODE_OFFSET=4340076:

- route 60000: `if-eq` offset `0x16`, jump `+0x22` code units → `0x5a` → `sendCmd(byte[])`
- `sendCmd` ส่ง broadcast `send.usbserial.cmd` ซึ่งเป็นเส้นทาง CP2102 / `SerialToothManager`
- route 8963 เป็นอีกสาขาไป `sendCmdPL232` / `send.usbserial.cmd.pl232`

ดังนั้นข้อความเดิมที่โยงรีเลย์ route 60000 ไป PL232 ผิด และนำข้อกำหนด handshake/RESET ของ PL232 มาใช้กับ CP2102 ไม่ได้ `SerialToothManager.usbInit` ของ CP2102 เปิดพอร์ต ตั้ง 115200 8N1 และรายงานการเชื่อมต่อ ไม่พบการเขียน RESET ในเมธอดนี้ การรับข้อมูลจริงโดยไม่ส่งคำขอเป็นหลักฐานเพิ่มเติมเฉพาะการรับสถานะ ไม่ได้พิสูจน์ว่าทุกคำสั่งควบคุมได้รับอนุญาตโดย firmware เสมอ

`heartBeatCheck` ของ CP2102 อ้าง `DataConstants.COMM_GET_SENOR`; ถอด fill-array-data ที่ `0x80 + 2*0x41a = 0x8b4` ได้ `FF 10 29 29 29 29 B4 FE` เก็บเป็นหลักฐานโค้ด ไม่ได้ส่ง query นี้ เพราะบอร์ดส่งข้อมูลเองอยู่แล้ว

## รูปแบบข้อมูลที่ใช้ตรวจ

จาก `SerialToothManager.processBufferedData`, `verifyCheckCode`, `handleTouchAndRemotePacket` และ `AllTouchSignalEvent`:

- header เริ่ม A5, payload length เป็น little-endian ที่ byte 3–4, ขนาดเฟรม = length+8
- ผลรวมทุกไบต์ modulo 256 ต้องเป็นศูนย์
- frame ขนาด 12: byte 8 เป็น remote raw; byte 9 เป็น IO; IO7 คือ mask 0x40
- byte 10 ยังเก็บเป็น raw ไม่มีหลักฐานให้เรียกว่า relay state หรือ servo power

`scripts/decode_robot_cp210.py` ตรวจรูปแบบนี้แบบ offline พร้อมแยกข้อความนำหน้า แพ็กเก็ตขาด และ checksum เสีย ไม่แปลง IO=0 เป็นการรับรองว่าพื้นที่ปลอดภัยหรือไฟเซอร์โวอยู่ในสถานะใด

## ค่าตั้งและการทดลองรีเลย์

อ่าน `armSetting.xml` ล่าสุดผ่าน XML parser: พบ `key_voicearmisuse=false` แต่ไม่มี `armcontrolmethodtype` จึงเข้าค่า default 0 ใน `setRelayPower` ของแอป ซึ่งเป็นโหมดรีเลย์ ค่านี้บอกเส้นทางที่แอปเลือก ไม่พิสูจน์ว่ามีรีเลย์ต่อกับแขนจริง

`BoardBuildDataUtil.buildRelayControlPacket` สร้างแพ็กเก็ต 10 ไบต์:

| ความหมายในโค้ด | เฟรม |
|---|---|
| จ่ายไฟ | `A5 01 2A 02 00 00 00 08 00 26` |
| ตัดไฟ | `A5 01 2A 02 00 00 00 08 01 25` |

หลังผู้ใช้ยืนยันปล่อยปุ่ม ตรวจภาพด้านหน้าและอ่าน IO ใหม่ 197 ตัวอย่างทั้งหมด IO7=false จากนั้นทดสอบจ่ายไฟ **หนึ่งวินาที** แล้วสั่งตัดสองครั้ง โดยไม่ส่งคำสั่งข้อต่อหรือกลุ่มท่าเพิ่ม กล้องเก็บ 91 เฟรม เชลล์จบ 0 และรายงานว่าเขียน ON/OFF แล้ว ภาพก่อน/ระหว่าง/หลังยังไม่เห็นหัวหรือแขนเปลี่ยนตำแหน่งจากมุมนี้

หลักฐานอยู่ใน `relay-power-one-second/`: `relay.json`, `relay-preflight.json`, `frames.json`, ภาพดิบ และ [ภาพเปรียบเทียบ](../data/robot-inspection/console-ui-20260911/relay-power-one-second/review.png) ใต้โฟลเดอร์หลักฐานเดียวกัน เวลาในภาพอ้างอิงจุดเริ่ม subprocess ซึ่งรวมเวลาตรวจ IO ก่อนจ่ายไฟ ไม่ใช่เวลาที่หน้าสัมผัสรีเลย์ทำงาน

**ยังไม่ได้วัดแรงดัน ไม่มี ACK เฉพาะรีเลย์ และไม่ได้วัดกระแส** การไม่มีแขนขยับจาก power pulse ที่ไม่มีคำสั่งตำแหน่งใหม่ ไม่พิสูจน์ว่ารีเลย์เสีย ไม่มีมอเตอร์ หรือสายหลุด สถานะจบรอบคือ *สั่ง OFF* ไม่ใช่ยืนยันไฟดับหรือคืนสถานะไฟเดิม เพราะไม่รู้สถานะจริงก่อนทดสอบ

## สิ่งที่ยังต้องดูจากฮาร์ดแวร์

ยืนยันการเคลื่อนหัวได้จาก [ผลกล้องช่อง 7/8](robot-front-camera-test-2026-09-11.md) แต่ยังไม่มีตารางสายของช่อง 1/11 หรืออีก 16 ช่องในข้อมูลที่ตรวจ ไม่พบค่าที่อ่านแรงดันรางเซอร์โวโดยตรง ขั้นถัดไปที่แยกสมมติฐานได้คือภาพบอร์ดควบคุม ป้ายรุ่น และปลั๊กสายของแขนภายในช่องบริการ โดยปิดไฟหลักก่อนและไม่ถอดสาย ไม่ควรสรุปว่าหุ่นติดตั้งมอเตอร์นิ้วครบตามคู่มือสินค้าจากการที่บอร์ดรองรับ 20 ช่อง

ตรวจท้ายรอบ: CP2102 กลับเป็น unbound, CH340 ยังพบพอร์ต, API แขน `armed=false` ไม่มีการแก้ `.env` หรือติดตั้งแอปในชุดนี้ เทสต์ offline ของ parser, preflight relay และตัวบันทึกรวม 13 ตัวผ่าน ไม่ใช่การทดสอบวงจรหยุดทางกายภาพ
