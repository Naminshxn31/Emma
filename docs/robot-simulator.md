# ซ้อมสั่งหุ่น Astronaut / Aobo ก่อนเครื่องมาถึง

ตัวจำลองนี้เรียกเครื่องมือ `go_to_place`, `stop_moving`, `return_to_base` และ
`get_robot_status` ชุดเดียวกับโปรเจกต์จริง แล้วส่งต่อไปยัง backend จำลองผ่าน
context เฉพาะคำขอ จึงซ้อมผ่านปุ่ม/ข้อความได้โดยไม่ต้องมีหุ่นหรือ API key เสียง
เพิ่มการสั่งด้วยเสียง Emma ที่ `/voice` แล้ว โดยโหมดเสียงใช้ provider/voice/API key
ที่ตั้งไว้เดิมในเครื่อง และใช้โควตาหรือค่าใช้จ่าย API ตามบัญชีของผู้ใช้

**ยังไม่ใช่ Android APK และไม่ได้รัน `SdkMode.MOCK` ของผู้ผลิต** เพราะมีคู่มือ
แต่ยังไม่มี `aoborobotsdk-v2.0.aar`, demo project หรือ Android toolchain ในเครื่องนี้
แผนที่ ตำแหน่ง เวลา แบตเตอรี่ และการชาร์จทั้งหมดเป็นข้อมูลสมมติ ไม่ใช่ผังโครงการ
หรือผลวัดจากหุ่นจริง ไม่มี SLAM, physics, การชน หรือการวางเส้นทางหลบสิ่งกีดขวาง

## เปิดใช้

บนเครื่องนี้ดับเบิลคลิก `start-robot-simulator.cmd` แล้วเปิด
**http://127.0.0.1:8010** ในเบราว์เซอร์ ปิดด้วย Ctrl+C ในหน้าต่างเซิร์ฟเวอร์
ตัวเปิดใช้เลือก `.venv-smoke` ถ้ามี ไม่เช่นนั้นใช้ `.venv` และไม่ติดตั้ง dependency เอง
หากตัวจำลองเปิดอยู่แล้ว ดับเบิลคลิกไฟล์เดิมจะเปิดหน้า Emma World ในเบราว์เซอร์
แทนการเริ่มเซิร์ฟเวอร์ซ้ำ หากพบ WinError 10048 จากการรันคำสั่งเอง ให้ลองเปิดลิงก์ด้านบนก่อน
หากพอร์ตถูกใช้โดยโปรแกรมอื่น ให้ใช้ `--port 8011` ตามตัวอย่างด้านล่าง

รันด้วยคำสั่งได้เช่นกัน:

```powershell
.venv-smoke\Scripts\python.exe -m app.robot_simulator
# เปลี่ยนพอร์ตเมื่อ 8010 ถูกใช้งานอยู่
.venv-smoke\Scripts\python.exe -m app.robot_simulator --port 8011
```

เครื่องใหม่ใช้ Python 3.14 และ environment ตาม `docs/measurement-and-installation.md`
ตัวจำลองผ่านปุ่มใช้ dependency หลักเดิม ไม่ต้องติดตั้ง extras ของเสียง/กล้อง/หุ่น
โหมดเสียงใช้ dependency ของ provider/VAD แบบเดียวกับ Emma เดิม
แยกโปรเซสจาก `app.main` ไม่แก้ `.env` ไม่ต้องเปิด `ROBOT_ENABLED` ไม่รีสตาร์ทระบบหลัก
และไม่ได้เปิด port ให้คอมพิวเตอร์อื่นหรือหุ่นจริงเชื่อมต่อ

หากเปิดสายแล้วพบ `Could not open a Gemini Live session: [WinError 5] Access is denied`
ให้ตรวจว่าเซิร์ฟเวอร์ถูกรันในสภาพแวดล้อมที่จำกัดเครือข่ายหรือไม่ กรณีที่พบในเครื่องนี้
เป็นโปรเซสที่เปิดจาก sandbox: เปิดเว็บ localhost ได้ แต่เชื่อมต่อ Gemini ไม่ได้
หยุดโปรเซสนั้นแล้วเปิด `start-robot-simulator.cmd` จาก Windows ตามปกติ
ไม่ต้องปิด firewall หรือเปลี่ยน API key จากข้อความนี้เพียงอย่างเดียว
หลังรีสตาร์ทให้กด Ctrl+F5 ที่หน้าเสียงเพื่อรับ cookie ใหม่

## แผนที่แบบเกม Emma World

ฉาก 3D มีห้องตัวอย่าง โต๊ะเซลส์ ฟิตเนส สระว่ายน้ำ และฐานชาร์จ
พร้อมเฟอร์นิเจอร์ แสงเงา หุ่น astronaut ที่หันตามทางเดิน แผนที่ย่อ และความคืบหน้าการเดินทาง
ตำแหน่งและเส้นทางมาจาก engine เดียวกับคำสั่งเสียง Emma ภาพขยับตามสถานะที่เซิร์ฟเวอร์ส่งมา

ผัง 3D ขยายความกว้างและความลึกเป็น 1.5 เท่าของรุ่นแรก (พื้นที่รวม 2.25 เท่า)
กลุ่มเฟอร์นิเจอร์ ตัวคน และหุ่นคงขนาดเดิม ทำให้ช่องเดินกว้างขึ้น กล้องด้านหลังเริ่มที่ระยะ 2.8 หน่วย
พิกัดใน engine/JSON ยังเป็นหน่วยผังเดิม; renderer แปลงตำแหน่ง เส้นทาง และ minimap ให้ตรงกัน
ขนาดนี้เป็นการจัดฉากจำลอง ไม่ใช่ระยะวัดจากสถานที่จริง

ค่าเริ่มต้นเป็น **Third person ของผู้เยี่ยมชม**: ตัวละครคนคือตัวคุณ แยกจากหุ่น Emma
คลิกฉากแล้วใช้ WASD/ลูกศรเดิน, Shift เดินเร็ว, ลากเมาส์ซ้ายเพื่อมองรอบตัว และล้อเมาส์ปรับระยะกล้อง
มือถือใช้ปุ่มลูกศรค้างเพื่อเดินและลากฉากเพื่อมอง; ออกจาก focus หรือปล่อยปุ่มแล้วหยุดเดิน
กด **V / เดินสำรวจ** เพื่อสลับกับภาพรวม; **F** เปลี่ยนไปตามหุ่น และ **◎ / 0** ดูทั้งฉาก
การเดินของคนเป็น state เฉพาะ browser ไม่ได้ส่งคำสั่งเดินให้หุ่น
มีการชนแบบ circle/AABB กับเฟอร์นิเจอร์ ผนัง สระ และขอบฉาก รวมถึงปรับระยะกล้องเมื่อมีสิ่งบัง
เป็นการชนสำหรับเดินสำรวจเท่านั้น ไม่ใช่ระบบหลบคนของหุ่นหรือการจำลองแรง/มวล

การใช้กล้อง **ในโหมดภาพรวม**:

- คลิก/แตะป้ายหรือจุดในฉากเพื่อเลือก แล้วกด **เริ่มเดินทาง**; เมาส์ดับเบิลคลิกเพื่อสั่งเดินทางได้ทันที
- ลากเมาส์ซ้ายเพื่อหมุนรอบฉาก ลากเมาส์ขวาเพื่อเลื่อนกล้อง หมุนล้อเมาส์หรือกด +/− เพื่อซูม
- กดปุ่ม **F (กล้องตามหุ่น)** เพื่อดูหุ่นระยะใกล้และติดตาม และ **◎ (ดูทั้งฉาก)** เพื่อคืนมุมมองเริ่มต้น; การลากหรือซูมด้วยเมาส์จะออกจากโหมดตามหุ่น
- กดปุ่มเต็มจอเพื่อขยายฉาก; กดอีกครั้งหรือ Esc เพื่อออก
- เมื่อโฟกัสอยู่บนแผนที่: Space หยุด, F เปิด/ปิดติดตาม, 0 คืนกล้อง และ +/− ซูม
- มือถือใช้แตะเลือกจุด ลากหนึ่งนิ้วเพื่อหมุน สองนิ้วเพื่อซูม/เลื่อน; ผู้ที่ไม่ใช้เมาส์เลือกจุดจากรายการในแผงคำสั่งได้

ใช้ [Three.js WebGLRenderer](https://threejs.org/docs/pages/WebGLRenderer.html) ซึ่งต้องมี WebGL 2
และ [OrbitControls](https://threejs.org/docs/pages/OrbitControls.html) สำหรับกล้อง โดยเก็บรุ่น 0.180.0
และ MIT LICENSE ภายใน `client/vendor/three/` พร้อม SHA-256 ใน manifest ไม่โหลด CDN ขณะเปิดฉาก
ถ้าเปิด 3D ไม่สำเร็จจะกลับเป็นฉาก Canvas 2.5D พร้อมข้อความแจ้ง; หากกราฟิกขาดการเชื่อมต่อ
ระบบเสียงและปุ่มยังใช้งานต่อได้ ระหว่างรอกราฟิกคืนมา จำกัด render ประมาณ 30 fps และลดงานเมื่อซ่อนแท็บ

เส้นทางสมมติผ่านทางเดินกลางและทางเข้าจุดหมาย ไม่ใช่เส้นตรงทแยงผ่านห้อง
ผังและเฟอร์นิเจอร์เป็นภาพประกอบ ไม่ใช่แผนที่จริงหรือข้อมูล collision/SLAM ของหุ่น
ระบบยังไม่คำนวณหลบสิ่งกีดขวางหรือระยะเบรกของหุ่นจริง
หากเปิดหน้าเก่าค้างไว้ ให้กด Ctrl+F5 เพื่อโหลดฉากใหม่

## Smart home ในฉาก

สั่งผ่านเสียง Emma หรือแผงควบคุมใต้ฉาก ทั้งสองทางใช้ validation/สถานะจากเซิร์ฟเวอร์ชุดเดียวกัน:

| ตัวอย่างคำสั่ง | ผลที่เห็น/ค่าที่รองรับ |
| --- | --- |
| “เอ็มม่า ปิดไฟ” / “เปิดไฟ” | โคมไฟและความสว่างทั้งฉากเปลี่ยน |
| “หรี่ไฟเหลือ 30 เปอร์เซ็นต์” | 0..100%; เปิดหลังหรี่เป็น 0 จะคืน 85% |
| “เปิดแอร์ ปรับ 23 องศา” | สถานะเปิด/ปิดและอุณหภูมิ 16..30°C, LED/ช่องลมในฉาก |
| “ปิดม่าน” / “เปิดม่านครึ่งหนึ่ง” | ม่านเคลื่อนไป 0..100% และปรับแสงธรรมชาติ |
| “เปิดทีวี” | หน้าจอทีวีมีภาพจำลอง ไม่มีเสียงทับ Emma |

ไฟยังควบคุมทั้งฉาก ไม่มีการเลือกโซน อุณหภูมิเป็นค่าที่ตั้ง ไม่ได้จำลองการถ่ายเทความร้อน
ไม่เชื่อม Broadlink, Home Assistant หรืออุปกรณ์จริง ทั้ง 4 อุปกรณ์เป็น virtual state
tools `set_simulated_device` และ `get_simulated_home` เปิดเฉพาะ context ตัวจำลอง
`/api/home` รับ JSON แบบ strict และตรวจ origin เช่นเดียวกับ API จำลองเดิม
ผลอยู่ใน journal/JSON export และ reset กลับค่าเริ่มต้นเมื่อเริ่มรอบใหม่
ฉากใช้วัสดุ [MeshStandardMaterial](https://threejs.org/docs/pages/MeshStandardMaterial.html),
texture วาดในเครื่อง เพดาน ช่องประตู และแสงโคม แต่ยังเป็นโมเดลสร้างขึ้นเพื่อซ้อม
ไม่ใช่ภาพถ่ายหรือ digital twin ที่วัดจากสถานที่จริง

## สั่งด้วยเสียง Emma

1. เปิด `http://127.0.0.1:8010` จะเห็นแผนที่และแผง **คุยกับ Emma** ในหน้าเดียว
   ใช้ voice client เดิมในแผงนี้; `/voice` ยังเปิดแยกได้ แต่ควรใช้หน้าเสียงเพียงหน้าหนึ่ง
2. อนุญาตไมค์ในเบราว์เซอร์ เมื่อขึ้นข้อความรอฟังชื่อ ให้เรียก **Emma / เอ็มม่า** ได้เลย
   ตัวจำลองใช้ `WAKE_ENABLED` และโมเดล wake เดิม; หากไม่มีโมเดลหรือปิดไว้ ยังใช้ปุ่ม **เริ่มคุย** ได้
   เบราว์เซอร์ที่ระงับเสียงอัตโนมัติอาจต้องคลิกหน้าเว็บหนึ่งครั้งเพื่อเปิดระบบเสียง
3. ลองพูด “เอ็มม่า พาไปห้องตัวอย่าง”, “หยุดก่อน”, “กลับฐาน” หรือ “ตอนนี้อยู่ไหน”
4. ดูหุ่นเคลื่อนที่ในแท็บแผนที่ เมื่อสำเร็จ/ล้มเหลว Emma จะได้รับเหตุการณ์เพื่อแจ้งเป็นเสียง
5. กด End เพื่อจบเสียง งานเคลื่อนที่จำลองที่ค้างจะถูกยกเลิก

หน้านี้ใช้ audio client, AudioWorklet, provider และเสียงที่ตั้งไว้ของ Emma เดิม
แต่ prompt เป็นโหมดซ้อม และเปิด robot tools 4 ตัวพร้อม virtual-home tools 2 ตัว
ไม่เปิดคำสั่งคอมพิวเตอร์ อุปกรณ์บ้านจริง การค้นเอกสาร ความจำส่วนตัว หรือการค้นเว็บจาก provider
หน้า `/voice` เปิดไมค์รอฟังชื่อเมื่อได้รับสิทธิ์และ wake พร้อม โดยใช้ detector ในเครื่อง
เปิดสายไป provider เมื่อได้ยินชื่อหรือกดเริ่มคุยเท่านั้น; หน้าแผนที่มีแผงเสียงที่รอฟังชื่อด้วย
มี audio owner เพียงตัวเดียวต่อ origin เมื่อเปิดหลายแท็บด้วย browser ที่รองรับ Web Locks
แท็บที่ไม่ได้ถือสิทธิ์จะแจ้งว่ามีอีกแท็บใช้ไมค์ ปิดแท็บเดิมแล้วกดเริ่มคุยเพื่อรับช่วง
Web Locks ไม่ครอบคลุมคนละพอร์ต/hostname/browser จึงควรใช้ URL `127.0.0.1:8010` เดียวกัน
หลังจบสายจะกลับไปรอฟังชื่ออีกครั้ง ปิดแท็บเสียงเมื่อต้องการหยุดฟังทั้งหมด
ไม่บันทึกคลิป debug/enrollment ของตัวจำลอง และไม่รับการปลุกจาก reminder/camera ของระบบหลัก
รองรับผู้พูดหนึ่งเซสชันต่อตัวจำลอง; หลังอัปเดต/รีสตาร์ทให้รีเฟรช `/voice` เพื่อรับ cookie ใหม่
การฟังแทรกใช้ `HALF_DUPLEX` ตามค่าเดิม ถ้าเปิดอยู่ต้องรอ Emma พูดจบ
หรือกดปุ่มหยุดบนแผนที่ระหว่างที่ Emma พูด

API key อยู่บนเซิร์ฟเวอร์ ไม่ส่งให้หน้าเว็บ การเชื่อมต่อเสียงของเซิร์ฟเวอร์จำลอง
ตรวจ origin ตรงกันและ cookie แบบ HttpOnly/SameSite Strict ที่ได้จาก `/voice`
ไม่ได้ใช้หรือเปลี่ยน token/endpoint ของบริการ Emma หลัก
ไม่ส่ง transcript จำลองเข้าบันทึกผู้ใช้งานจริง; ผลเครื่องมือยังอยู่ใน journal/export
เซสชันเสียงจริงต้องมี API key และเครือข่ายไป provider ตามระบบเดิม

## สถานะเสียงและผลซ้อม

แผงเสียงแยกสถานะไมค์ ข้อมูลเข้า ระบบเล่นเสียง wake และ provider คำว่า “เสียงออกพร้อม”
หมายถึง AudioContext ทำงาน ไม่ยืนยันว่าลำโพงดังจริง ใช้ **ทดสอบลำโพง** เล่นเสียงสั้นในเครื่อง
โดยไม่เปิดไมค์หรือสาย AI เพิ่ม ส่วนปุ่มเริ่มคุยเป็นการเชื่อม provider จริงและใช้โควตาตามบัญชี

ผลซ้อมเสียงด้านล่างแสดงสถานะ provider ที่ server เห็นจริงและ latency p50/p95
จากสัญญาณจบเสียงถึงข้อมูลเสียงตอบ หากยังไม่มีสัญญาณเวลาที่ต้องใช้จะแสดง “ยังไม่มีข้อมูล”
ไม่แทนด้วยศูนย์ และไม่ถือเป็นการวัด acoustic latency จากลำโพง

metrics ใช้ sink เฉพาะตัวจำลอง จำกัด 800 เหตุการณ์ และไม่เก็บ transcript/ไฟล์เสียง
แยกจาก visitor log; session/turn/command ช่วยเชื่อมเหตุการณ์ Browser observations เป็นข้อมูล
ที่ client รายงาน ส่วน provider ready/error มาจาก server ไม่ให้ client เปลี่ยนแทนได้
**บันทึกผล JSON** รูปแบบ v2 รวมสถานะหุ่นและ `voice_diagnostics` ของรอบเดียวกัน
ข้อมูลอยู่ใน RAM ให้ส่งออกก่อนปิดโปรแกรม/เริ่มรอบใหม่ และจบสายก่อนกดเริ่มรอบใหม่
journal คำสั่งเดิมยังอาจมีชื่อจุดหรือข้อความที่กรอกทดสอบ จึงควรใช้ข้อมูลสมมติ

## ลองอะไรได้บ้าง

เปิดแผงพับ **คำสั่งและสถานการณ์ทดสอบ** เพื่อใช้ปุ่ม/ช่องกรอกต่อไปนี้

1. เลือกจุดหมายแล้วกด **เริ่มเดินทาง**: รับ ACK ก่อน หุ่นจำลองเคลื่อนที่ แล้วมี
   `robot_arrived` เมื่อครบเวลาเท่านั้น ผล tool ต้องกลับทันทีโดยไม่รอถึง
2. ช่องข้อความส่งตรงเข้า `go_to_place` เช่น “พาไปห้องตัวอย่าง” เพื่อทดสอบตัวจับชื่อจุด
   ช่องนี้ไม่ใช่ตัวแปลเจตนาหรือระบบรู้จำเสียง คำสั่งหยุดใช้ปุ่มหยุด
3. **หยุดการจำลอง** ระหว่างเดิน: ยกเลิกงานเดิม ไม่เกิด arrival สำเร็จภายหลัง
4. **กลับฐาน**: สถานะชาร์จเป็นจริงเฉพาะหลังถึงฐานจำลอง
5. เลือกเหตุการณ์แล้วกด **ใช้กับคำสั่งถัดไป** ก่อนส่งคำสั่งเดินทางใหม่
   สิ่งกีดขวางจะค้างที่ 45% ของระยะทางตามเส้นทางจน timeout; ไม่ได้จำลองการหลบจริง
6. **จำลองหลุดการเชื่อมต่อ**: รายงานการเคลื่อนที่ “ไม่ทราบ” ภาพหยุดอัปเดต;
   เชื่อมต่อใหม่ซิงก์เป็น idle ในโลกสมมติ ไม่ส่งคำสั่งค้างซ้ำ
7. **ส่งคำสั่งเดิมซ้ำ**: ใช้ command ID เดิม ระบบไม่เริ่มเดินอีกครั้ง
8. **บันทึกผล JSON**: ดาวน์โหลดสถานะ คำสั่ง และเหตุการณ์เพื่อเก็บผลซ้อมก่อนเริ่มรอบใหม่

สถานการณ์ `ack_lost` จำลองกรณีคำสั่งอาจทำงานแล้วแต่ผู้สั่งไม่ได้รับ ACK:
tool ส่งกลับ failed และการเคลื่อนที่เป็น unknown แม้ภาพจำลองยังเคลื่อน
เมื่อ timeout หยุดเฉพาะโลกจำลอง การหมดเวลาไม่ใช่หลักฐานว่ามอเตอร์จริงหยุด
`no_arrival` จะไปถึงตำแหน่งในภาพแต่ไม่แจ้งสำเร็จ แล้วจบด้วย timeout เช่นกัน
การตั้งค่าใหม่ไม่เปลี่ยนคำสั่งที่กำลังทำงาน; คำสั่งไปจุดอื่นขณะเดินถูกปฏิเสธว่า busy
ให้หยุดงานเดิมก่อน

ประวัติใน RAM เก็บ 500 เหตุการณ์ล่าสุดและ 256 คำสั่งล่าสุด รวมงานที่กำลังทำอยู่
การป้องกันคำสั่งซ้ำครอบคลุมเฉพาะคำสั่งที่ยังอยู่ในหน้าต่างนี้
Reset/ปิดโปรแกรมล้างประวัติ ไม่ใช่ durable exactly-once delivery ของฮาร์ดแวร์
ไฟล์ export มีข้อความทดสอบที่กรอก จึงควรใช้ข้อมูลสมมติสำหรับซ้อม

## โครงสร้างและขอบเขตการย้ายไปหุ่น

```text
ปุ่ม/ข้อความทดสอบ → /api/tool → app/tools/robot.py (โค้ดเดียวกับ voice tools)
                                      ↓
                            app/tools/robot_link.py
                                      ↓ context เฉพาะตัวจำลอง
                            SimulatedRobot → ACK / arrival / failure

ระบบจริงปัจจุบัน: AI voice tools → robot_link → /ws เดิม → Android bridge [ยังต้องสร้าง]
                                                               ↓
                                                    Aobo SDK MOCK → REAL
```

แนวทางเริ่มต้นคือ Python รันบนคอมพิวเตอร์เดิม แล้วหุ่น Android เป็น client
ผ่าน Wi-Fi; หุ่นทำหน้าที่รับเสียง/เล่นเสียง/แสดงผลและเรียก native SDK
ถ้าต้องการรันทั้งหมดบนหุ่น ต้องพิสูจน์ Python runtime/dependency ที่ใช้จริงบน Android
พร้อมทรัพยากรและการเปิดบริการหลังบูตเพิ่มเติม ไม่สามารถคัดลอก Windows virtualenv
ลง Android แล้วรันได้ทันที

ไฟล์หลัก:

| ไฟล์ | หน้าที่ |
|---|---|
| `app/robot_backend.py` | interface และ context ของตัวจำลอง แยกจากสถานะหุ่นจริง |
| `app/robot_simulation.py` | engine รับคำสั่ง บันทึก ACK และผลเดินทาง; ไม่มี network/SDK |
| `app/robot_simulator.py` | localhost API/วงรอบอัปเดต และ voice/wake endpoint ใช้ detector เดิม |
| `app/robot_voice.py` | ส่งผลเดินทางให้ Emma หลังรอจบคำพูด และตัดผลที่ล้าสมัย |
| `client/robot-simulator.*` | หน้าจอและส่งออกผลทดสอบ |
| `tests/test_robot_simulation.py` | lifecycle, isolation, API และ regression หุ่นจริง |
| `tests/test_robot_voice.py` | PCM/WebSocket/tool/arrival, schema isolation, auth และ log isolation ด้วย upstream fake |

## Contract และ mapping จากคู่มือ

คำสั่งใช้ action/args เดียวกับ `/ws` เดิม ตัวจำลองเพิ่ม `command_id`:

```json
{"type":"robot","action":"move_to_point","args":{"place":"ห้องตัวอย่าง"},"command_id":"example-1"}
```

| คำสั่ง/ผล | Aobo SDK ตามคู่มือภาษาไทย |
|---|---|
| เตรียม SDK | `AoboRobotManager.init(context, SdkMode.MOCK)` หรือ `REAL` หน้า 5 |
| เชื่อม chassis | `quickConnect()` ค่าเริ่มต้น `192.168.11.1:1445` หน้า 6 |
| โหลดจุดจริง | `manager.getPoints()` คืน `List<PointOfInterest>` หน้า 14 |
| `move_to_point` | resolve POI จากรายการจริงแล้ว `manager.moveToPoint(poi)` หน้า 8 |
| `cancel_navigation` | `manager.cancelNavigation()` หน้า 8 |
| `go_home` | `manager.goHome()` หน้า 8; ต้องตั้งฐานชาร์จบนหุ่นจริงก่อน |
| การเชื่อมต่อ | `onConnected`, `onConnectionFailed`, `onConnectionLost` หน้า 27 |
| สถานะ | `onStatusUpdate(StatusUpdateEvent)` หน้า 27–28 |
| เดินทาง | `onNavigationUpdate`, `onReachedTarget`, `onNavigationFailed` หน้า 29–30 |

ACK ในตัวจำลองหมายถึง adapter ยอมรับคำสั่ง ไม่ใช่ถึงที่หมาย และไม่ใช่หลักฐานจากมอเตอร์
event `robot_ack`/`command_id` เป็น **contract ที่เราสร้างเพื่อซ้อมและเสนอให้ bridge ใช้**
คู่มือไม่ได้ยืนยันว่าตัว SDK รองรับ command ID หรือ idempotency เหล่านี้
ต้องอ่านโครงสร้าง event จริงจาก AAR ก่อนเขียน Android adapter

ตัวอย่างผลจำลอง:

```json
{"type":"robot_ack","command_id":"example-1","accepted":true,"hardware":"simulated"}
{"type":"robot_arrived","command_id":"example-1","place":"ห้องตัวอย่าง","ok":true,"hardware":"simulated"}
```

`/ws` ของ production ปัจจุบันยังรับเพียง `robot_ready`/`robot_arrived` ที่ผูกกับ
robot token และส่งคำสั่งแบบไม่รอ ACK ไม่มี handler ของ ACK/command ID แบบใหม่นี้
จึงยังห้ามนำตัวจำลองไปอ้างว่าทดสอบ protocol บนหุ่นจริงครบแล้ว
ชุดนี้เพิ่ม guard กัน arrival คนละจุดหมาย แต่ callback เก่าจากการไปจุดเดิมสองครั้ง
ยังต้องใช้ command ID ใน bridge และ session จริงแก้ให้ครบก่อนทดสอบ REAL
ต้องทดสอบแยกการยกเลิกแบบ software กับปุ่ม emergency stop ของเครื่องด้วย

## สิ่งที่ต้องได้ก่อนทำ APK และเปิด REAL

| รายการ | ทำตอนนี้/รออะไร |
|---|---|
| Command behavior และหน้า test bench | ทำแล้วในตัวจำลองนี้ |
| SDK `.aar`, Android demo, package names และ dependencies | ขอชุดพัฒนาที่ตรงรุ่น/firmware จากผู้ขาย |
| ABI / `minSdk` / native `.so` / permission / callback fields | ตรวจใน AAR และอุปกรณ์จริง ไม่เดาจากชื่อรุ่น |
| Android bridge และ APK ที่ build ได้ | ทำหลังได้ AAR/demo และติดตั้ง JDK/Android SDK; เริ่ม SDK MOCK |
| ติดตั้งและ auto-start/kiosk | ยืนยันสิทธิ์ติดตั้ง วิธี `adb`/MDM และ policy ของผู้ขาย |
| Map/POI/ฐานชาร์จ/เขตห้ามเข้า | สร้างและทดสอบในพื้นที่จริง |
| ไมค์/ลำโพง/AEC/barge-in | ยืนยัน channel/sample rate และทดสอบเสียงจริง |
| Wi-Fi/auth/reconnect/ACK/late callback | ทดสอบ bridge ทั้ง MOCK และ REAL ก่อนส่งมอบ |
| การหยุดและระยะเบรก | ทดสอบในพื้นที่ควบคุมและยืนยัน emergency stop ก่อนพาลูกค้าเดิน |

หากทำ bridge ผ่าน Android WebView ให้จำกัด origin ของเนื้อหาที่เรียก native API,
ตรวจความสามารถ runtime และไม่เปิด bridge ให้เว็บทั่วไปเรียกการเคลื่อนที่ได้
อ้างอิง [Android: native API access via JS bridge](https://developer.android.com/develop/ui/views/layout/webapps/native-api-access-jsbridge)
และ [WebView native bridge security](https://developer.android.com/privacy-and-security/risks/insecure-webview-native-bridges)
(ตรวจ 2026-09-08) ทั้งนี้ยังไม่มี WebView bridge ถูกเพิ่มในชุดนี้
