## วงเน็ต: หุ่นกับ PC เคยอยู่คนละวง (10 ก.ย. ~15:40)

อาการคือเปิด `https://192.168.0.3:8001/health` บน Chromium ของหุ่นแล้วหมุนค้างจนหมดเวลา
**ไม่ใช่ certificate ไม่ใช่ firewall** — ไม่มี error ให้เห็นเลย มีแต่ "ช้า" ซึ่งเป็นหน้าตาของ
แพ็กเก็ตที่ออกไปทาง gateway แล้วไม่มีใครตอบ

- หุ่น (Settings → About tablet → IP address): **192.168.1.23** เกาะ Wi-Fi
- PC: **192.168.0.3** ผ่านสาย Ethernet (gateway 192.168.0.1) และ Wi-Fi ปิดอยู่
- prefix /24 ทั้งคู่ = คนละซับเน็ต ไม่มีเส้นทางถึงกัน

แก้โดยเปิด Wi-Fi ของ PC เข้า SSID `Embassy` (มีโปรไฟล์บันทึกไว้อยู่แล้ว) ได้ **192.168.1.43**
วัดหลังแก้: ping หุ่น 2-3 ms · `GET https://192.168.1.43:8001/health` ตอบ 200 ใน 9 ms ·
`certs/lan-cert.pem` มี 192.168.1.43 ใน SAN อยู่แล้ว ไม่ต้องออกใบใหม่ · firewall rule
"Condo Voice LAN 8001" เป็น Private,Public และวง Wi-Fi ถูกจัดเป็น Public จึงผ่าน ·
Ethernet ยังเป็น default route (interface metric 35 < 60) อินเทอร์เน็ตของ PC ไม่สะดุด

**URL ที่หุ่นต้องเปิด:** `https://192.168.1.43:8001/?kiosk=1&token=<WS_TOKEN ใน .env>`
ใช้ `?kiosk=1` ไม่ใช่ `/display` เพราะหุ่นมีไมค์ของตัวเอง มันคือ client ไม่ใช่จอแสดงผล

**ยังค้าง:** ติดตั้ง `certs/rootCA-android.crt` บนหุ่น (Settings → Security →
Encryption & credentials → Install a certificate → CA certificate) ถ้าไม่ติดตั้ง
Chromium จะขึ้นหน้าเตือนใบรับรองทุกครั้ง และสิทธิ์ไมค์บน origin ที่ใบรับรองมีปัญหาไม่แน่นอน

**เจอเพิ่มระหว่างสแกน:** SSID `SLAMWARE-AB340E` (open, สัญญาณ 60%) คือบอร์ดนำทางของหุ่นเอง
ที่กระจาย AP ของมันออกมา ตรงกับที่คู่มือบอกว่า `quickConnect()` วิ่งไป 192.168.11.1:1445 —
ถ้าจะคุยกับบอร์ดตรงๆ ต้องเกาะ AP ตัวนี้ ซึ่งจะหลุดจากวง Embassy ทันที
(การ์ด Wi-Fi ใบเดียวเกาะได้วงเดียว) จึงไม่ใช่ทางที่ใช้พร้อมกับการเป็นเซิร์ฟเวอร์ได้

**ไม่ต้องลง Google Play Store** หุ่นมี Chromium เป็นเบราว์เซอร์หลักอยู่แล้ว (Default apps →
Browser app: Chromium) ทุกอย่างที่ระบบนี้ต้องใช้รันในนั้นได้ ส่วน APK ที่โหลดจากเว็บมิเรอร์
ลงไม่สำเร็จเพราะ Play Store ต้องมาคู่กับ Play Services ใน system image ที่ลายเซ็นตรงกัน

## แขนและจอบนหัว: ตัดเบาะแสที่ตันออกแล้ว (10 ก.ย. กลางคืน)

ต่อจาก [ผลตรวจแขนและจอบนหัว](../data/robot-inspection/analysis-arm-head-20260910/ผลตรวจแขนและจอบนหัว.md)
ซึ่งระบุไว้ถูกแล้วว่าอะไรเห็นชื่อกับอะไรพิสูจน์แล้ว บันทึกเพิ่มสองอย่าง

### ตารางเลขท่าไม่ได้อยู่บนแท็บเล็ต เลิกค้นในไฟล์ได้

ตรวจแล้วตัดออกทีละอัน:

| ที่ที่ค้น | ผล |
|---|---|
| `aobocenter/chatcode.txt` | มุกตลกจีน 21 รายการ index 0-20 ไม่เกี่ยวกับท่า |
| `voice_config/base_actions.json` | กติกาจับข้อความ (`QUIT`, `OPEN_APP`, `VOICE_NAVI_SETTING`, `MAPU_CONTROL` พร้อมชนิดการแมตช์) ไม่มีมอเตอร์ |
| layout ของหน้า ARM ใน APK | มีแค่ปุ่ม `selectactiongroup` กับ spinner เลือกหมายเลขเซอร์โว — แอปส่ง**เลข** ไม่ได้ถือตาราง |

รูปแบบนี้คือบอร์ดเซอร์โวที่เก็บกลุ่มท่าที่บันทึกไว้ในหน่วยความจำของบอร์ดเอง
แล้วสั่งด้วยหมายเลข ความหมายของเลขจึงอยู่ที่บอร์ด ไม่ได้อยู่ในไฟล์ใดบนเครื่อง
**เหลือทางเดียวคือขอรายการจากผู้ขาย หรือให้ช่างไล่ทีละเลขบนหน้า ARM ของแอปเองแล้วจดว่าเลขไหนทำอะไร**

ข้อควรระวังถ้าจะไล่: `loopCount=0` แปลว่าวนไม่สิ้นสุด ห้ามใช้เป็นค่าทดสอบ ·
เลข 0-255 ที่ไม่รู้จักอาจดันข้อต่อไปสุดระยะ ต้องให้แขนโล่ง ไม่มีคนหรือของในระยะเอื้อม
และเตรียม `stopArmAll` ไว้ · **ห้ามไล่เลขจากเครื่องมือที่โมเดลเรียกได้** งานนี้อยู่ที่แอปผู้ขาย
หรือเครื่องมือหน้าโต๊ะ ไม่ใช่สิ่งที่ Emma ควรมีสิทธิ์เรียก

### จอบนหัว: มีสมมติฐานที่ทดสอบได้ด้วยสวิตช์เดียว

`double_screen.xml` มี `SurfaceAnimView` ชื่อ `robotface` และในหน้าตั้งค่ามี
`switch_doublescreen` — ชวนให้เชื่อว่าหน้าตาถูกวาดเป็น surface ของ Android
บนจอที่สองที่**โผล่มาเฉพาะตอนเปิดโหมดสองจอ** ส่วน dump ที่เห็นจอเดียวนั้นเก็บตอนสวิตช์ปิดอยู่

**การทดสอบ:** เปิดสวิตช์โหมดสองจอในแอปผู้ขาย แล้ว dump จอใหม่
เจอจอจริงตัวที่สอง = จอบนหัวเป็นจอ Android เอาหน้าเว็บขึ้นได้แบบเดียวกับจอหน้าอก ·
ไม่เจอ = ขับด้วยตัวควบคุมแยกผ่านพอร์ตอนุกรม ตระกูลเดียวกับแขน และต้องพึ่งผู้ขาย

### สิ่งที่ต้องขอผู้ขายเหลือสามข้อ ไม่ใช่รายการยาว

1. ตารางกลุ่มท่าของแขนสำหรับรุ่นนี้ (เลขไหนคือยกมือ จับมือ)
2. จอบนหัวขับด้วยอะไร และส่งภาพไปยังไง
3. ช่องไหนของชุดไมค์คือช่องที่ผ่านการตัดเสียงสะท้อนแล้ว

ล้อไม่อยู่ในรายการนี้แล้ว เพราะสั่งได้เองผ่าน REST ของ SLAMTEC ตั้งแต่บ่ายวันนี้

## เบรกของแชสซี — ผู้ต้องสงสัยอันดับหนึ่งที่ยังไม่ได้ทดสอบ (10 ก.ย. ~18:20)

ดึงไฟล์สเปกของบอร์ดเอง `http://<board>:1448/js/spec.js` (160 KB, เป็น OpenAPI)
แล้วอ่านคำอธิบายของ `PUT /api/core/system/v1/parameter` ได้ความว่า

| พารามิเตอร์ | ความหมาย (แปลจากคำอธิบายจีนในสเปก) |
|---|---|
| `base.max_moving_speed` | ความเร็วเชิงเส้นสูงสุด m/s (อ่านได้ ตอนนี้ 0.4) |
| `base.max_angular_speed` | ความเร็วเชิงมุมสูงสุด rad/s (อ่านได้ ตอนนี้ 1.0) |
| `base.emergency_stop` | `on` = สั่งหยุดฉุกเฉิน · `off` = ปลดการหยุดฉุกเฉิน |
| `base.brake_release` | `on` = **ปลดเบรก** · `off` = คืนเบรกสู่สภาพปกติ |

**สองตัวหลังเขียนได้อย่างเดียว อ่านไม่ได้** — `GET ?param=base.brake_release` ตอบ
`"invalid arguments"` เพราะ enum ของ GET มีแค่สามตัวแรก จึงไม่มีทางรู้จาก REST
ว่าตอนนี้เบรกอยู่สถานะไหน

**ทำไมถึงเป็นผู้ต้องสงสัยอันดับหนึ่ง** โหมดปลดเบรกมีไว้ให้**เข็นหุ่นด้วยมือ**
มอเตอร์ถูกปลดกำลัง ล้อหมุนอิสระ และหุ่นขับตัวเองไม่ได้ ซึ่งอธิบายอาการที่วัดได้
ทุกข้อพอดี: บอร์ดรับคำสั่ง สร้าง action สำเร็จ รายงานว่า `status: 1` กำลังทำงาน
แต่ `stage` ว่างเปล่า ไม่มี error ไม่มี `reason` และตำแหน่งไม่ขยับเลยสักมิลลิเมตร
และวันนี้มีการ**เข็นหุ่นด้วยมือ**จริง (ออกจากแท่นชาร์จ) ซึ่งเป็นเหตุให้ใครสักคน
ปลดเบรกไว้ได้

**ยังไม่ได้ทดสอบ** คำสั่งที่ต้องรัน (ปลอดภัยทั้งสองทาง: ถ้าเบรกปกติอยู่แล้วจะไม่มีอะไรเปลี่ยน
และสเปกระบุว่าค่าที่ตั้งมีผลเฉพาะรอบการทำงานนี้ รีบูตแล้วกลับค่าเดิม)

```powershell
curl.exe -X PUT -H "Content-Type: application/json" `
  -d '{"param":"base.brake_release","value":"off"}' `
  http://127.0.0.1:11448/api/core/system/v1/parameter
```

**ลำดับที่ควรทำ** คืนเบรก → เข็นหุ่นออกที่โล่ง (ตอนนี้รอบตัวแคบ 0.43 ม. สามด้าน) →
เสียบชาร์จ → กดหมุนอยู่กับที่บนหน้า `/robot` ถ้าหมุนได้ แปลว่าเบรกคือคำตอบ
ถ้ายังไม่หมุนทั้งที่มีที่ว่าง ให้กลับไปดูฝั่งแผนที่และคุณภาพการระบุตำแหน่ง (ตอนนี้ 44)

## ทดสอบสั่งด้วยมือครั้งแรก: คุมได้ แต่หุ่นเดินไม่ออก (10 ก.ย. ~17:10)

**เส้นทางคำสั่งพิสูจน์แล้วว่าครบ** หน้าเว็บ → เซิร์ฟเวอร์ → บอร์ดนำทาง
22 คำสั่งจากหน้า `/robot` ไปถึงบอร์ดทุกคำสั่ง บอร์ดตอบ 200 และสร้าง action ให้ทุกครั้ง
(นับจาก access log 22 ครั้ง และ `robot_manual_command` ใน turn log 22 รายการ)

**แต่หุ่นไม่ขยับแม้แต่มิลลิเมตรเดียว** วัดจากตำแหน่งที่บอร์ดรายงานเอง 8 ครั้งห่างกัน 1.5 วินาที
ได้ค่าเดิมเป๊ะทุกครั้ง `+0.027, +0.205, +0.050` เคลื่อนที่ 0.0 ซม. หมุน 0.0 องศา

**เอกสาร action ที่บอร์ดคืนมาคือเบาะแส** (เพิ่ม log ไว้ที่ `move_to()` และ `_tick()` เพื่อจับตัวนี้):

```
{'action_id': 26, 'action_name': 'slamtec.agent.actions.MoveToAction',
 'stage': '', 'state': {'reason': '', 'result': 0, 'status': 1}}
```

`status: 1` คือกำลังทำงาน แต่ `stage` **ว่างเปล่า** และค้างแบบนั้นเป็นนาที
งานที่เดินจริงต้องมี stage บอกว่าอยู่ขั้นไหน ว่างเปล่าแปลว่าตัววางแผนการเคลื่อนที่ไม่เคยเริ่ม

**สาเหตุที่น่าจะเป็น: หุ่นถูกล้อมจนออกไม่ได้** ไลดาร์ทำงานปกติ (1,572 จุดใช้ได้จาก 1,586)
และรายงานว่ารอบตัวหุ่นแคบมาก

| ทิศ | ระยะถึงสิ่งกีดขวางที่ใกล้ที่สุด |
|---|---|
| ซ้าย (+45..+90°) | 0.43 ม. |
| ซ้ายหลัง (+90..+135°) | 0.43 ม. |
| หลังขวา (-135..-90°) | 0.48 ม. |
| ขวา (-90..-45°) | 0.48 ม. |
| หน้า (0..+45°) | 0.68 ม. |
| หน้าขวา (-45..0°) | 0.88 ม. |

สามด้านมีของอยู่ใกล้กว่าครึ่งเมตร แชสซีที่ต้องเผื่อรัศมีตัวเองบวกระยะปลอดภัย
จะถือว่าออกไม่ได้และไม่ขยับ โดยไม่บอกเหตุผลผ่าน REST

**ที่ตัดทิ้งไปแล้ว:** ไม่ใช่ปัญหาโค้ด (คำสั่งถึงบอร์ดครบ) · ไม่ใช่ไลดาร์ (จุดใช้ได้ 99%) ·
ไม่ใช่ปุ่มหยุดฉุกเฉินหรือ error ของฐาน (`robot/health` สะอาดทุกฟิลด์) ·
ไม่ใช่ล็อกซอฟต์แวร์ (`ROBOT_CHASSIS_MOTION_ENABLED=true` แล้ว)

**ข้อควรระวังที่เจอ:** action ที่ค้างสถานะ "กำลังทำงาน" ไม่หายไปเอง ยกเลิกด้วย
`DELETE /api/core/motion/v1/actions/:current` (ปุ่มหยุดบนหน้า `/robot` ทำอันนี้)
ไม่งั้นคำสั่งถัดไปจะไปทับงานที่ค้างอยู่

**ขั้นต่อไป** เข็นหุ่นออกมาที่โล่ง ให้มีที่ว่างรอบตัวอย่างน้อย 1 เมตร แล้วลองหมุนอยู่กับที่ก่อน
และเสียบชาร์จ แบตเหลือ 15% ระหว่างทดสอบทั้งบ่ายไม่เคยได้ชาร์จเลย

## หน้าสั่งหุ่นด้วยมือ (`/robot`)

เปิด `https://<เซิร์ฟเวอร์>:8001/robot?token=<WS_TOKEN>` — ต้องมี token เพราะทุกปุ่มบนนั้นขยับของจริง
มีไว้ตอบคำถามเดียว: หุ่นตอบเราไหม ไม่ใช่หน้าใช้งานประจำวัน

- ปุ่ม **หยุด** อยู่บนสุดติดจอตลอดและใช้ได้แม้ตอนการเคลื่อนที่ถูกล็อก
- เดินหน้า/ถอยหลังครั้งละ 30 ซม. หมุนซ้าย/ขวาครั้งละ 15° — **ระยะกำหนดที่เซิร์ฟเวอร์**
  หน้าเว็บส่งได้แค่ชื่อคำสั่ง เปลี่ยนตัวเลขไม่ได้
- กลับแท่นชาร์จ และไปจุดหมายในแผนที่ (ตอนนี้แผนที่ยังว่าง ปุ่มจึงยังไม่มี)
- สถานะสดทุก 1.5 วินาที: แบต แท่นชาร์จ ตำแหน่ง ความมั่นใจในตำแหน่ง คำสั่งที่ค้างอยู่

**ลำดับทดสอบที่ปลอดภัยที่สุด** เริ่มจากหมุนอยู่กับที่ก่อน เพราะพาหุ่นไปชนอะไรไม่ได้
ถ้าหมุนได้แปลว่าเราคุมล้อได้จริง แล้วค่อยลองเดินหน้าถอยหลังในที่โล่ง
ต้องมีคนยืนข้างหุ่นและมือถึงปุ่มหยุดกายภาพตลอดการทดสอบ

**ไมค์ของหุ่นคือ USB dongle ยี่ห้อ Bothlent (UAC)** `/proc/asound/card0/stream0` บอกตรงๆ:

```
Capture:  Status: Running
  Format: S16_LE   Channels: 8   Rates: 16000
  Channel map: FL FR FC LFE RL RR FLC FRC
```

**แปดช่องจริง ที่ 16 kHz** — จบข้อสงสัย "คู่มือบอกไมค์ 4 ตัว แต่ `MicConfig.channels` บอก 8"
ระดับฮาร์ดแวร์คือ 8 ช่อง ส่วนจะเป็นไมค์ 4 ตัว + ช่องอ้างอิงสำหรับ AEC หรือไม่
ยังต้องดูจากค่าที่วัดได้ต่อช่อง ซึ่งหน้า `/hardware` แสดงให้ทีละช่องแล้ว

**ไมค์ไม่ได้ถูกปิด** `dumpsys audio` ตอบว่า
`mic mute FromSwitch=false FromRestrictions=false FromApi=false from system=false`
ครบทั้งสี่ทาง ดังนั้นถ้าเบราว์เซอร์เปิดไมค์แล้วได้ศูนย์ ต้นเหตุไม่ใช่สวิตช์ปิดไมค์

**ระบบเสียงเดิมของหุ่นกำลังรันอยู่จริง** — ข้อที่ CLAUDE.md ระบุว่าเสี่ยงที่สุด
ตอนนี้มีหลักฐานแล้ว ไม่ใช่การคาดเดา: `com.aobo.robot.ai3` (pid 2880) เป็น audio client
ใน `dumpsys media.audio_flinger` และ `com.iflytek.vflynote` ก็รันอยู่ด้วย
(iFLYTEK คือเอนจินเสียงที่ `call.bnf` ในโฟลเดอร์ aobocenter ชี้ไป — ไฟล์ grammar นั้น
เป็นภาษาจีนล้วนและเป็นเดโมขายบ้านของโครงการอื่น คำปลุกในไฟล์คือ 维纳斯)

**ยังไม่ได้พิสูจน์ว่ามันยึดไมค์แบบผูกขาด** Android ปกติให้แอปที่อยู่หน้าจอได้เสียงจริง
ที่เหลือได้ความเงียบ วิธีทดสอบที่ถูกต้องคือเปิด `/hardware` บนหุ่นแล้วดูว่าได้ศูนย์หรือไม่
ถ้าได้ศูนย์ ให้ `adb shell am force-stop com.aobo.robot.ai3` แล้ววัดซ้ำ —
**แต่ต้องถามเจ้าของก่อน** เพราะแอปนั้นอาจถือบริการอื่นของหุ่นอยู่ด้วย

### สิ่งที่วัดได้จากไมค์ของ PC (คนละตัวกับของหุ่น)

หน้า `/hardware` ที่เปิดบน PC รายงาน `Microphone (LCS_USB_AUDIO) (0a67:8524)`
2 ช่อง 48 kHz track `live` ปิด AEC/AGC/noise suppression ครบ แล้วได้ **ศูนย์ล้วนทุกช่อง**
ตรงกับ `DIGITAL SILENCE` ที่ `session.py` เขียนใน log ซ้ำๆ ทั้งเย็น
เป็นปัญหาของไมค์ตัวนั้นเอง ไม่ใช่ของหุ่นและไม่ใช่ของโค้ด
**และไม่ขวางหุ่น** เพราะเมื่อ Emma รันบนเบราว์เซอร์ของหุ่น มันใช้ไมค์กับลำโพงของหุ่นเอง
ไมค์ของ PC ไม่ได้อยู่ในเส้นทางนั้นเลย

## หน้าตรวจไมค์และกล้อง และผลทดสอบสั่งเดินครั้งแรก (10 ก.ย. เย็น)

**เปิด `https://<เซิร์ฟเวอร์>:8001/hardware` บนเบราว์เซอร์ของหุ่น** ไม่ต้องใส่ token
หน้านี้วัดไมค์กับกล้องของเครื่องที่เปิดมันเอง ไม่ส่งอะไรออกไปที่ไหนเลย
มีปุ่มคัดลอกสรุปเป็นข้อความสำหรับส่งต่อ สิ่งที่มันตอบได้และ log ฝั่งเซิร์ฟเวอร์ตอบไม่ได้:
ไมค์ถูก mute หรือแอปอื่นยึดอยู่ หรือคนแค่ยืนไกล — สามอย่างนี้หน้าตาเหมือนกันหมดจากฝั่งเซิร์ฟเวอร์
และมันวัดทีละช่องของชุดไมค์ ทำให้เห็นว่าช่องไหนคือช่องที่ตัดเสียงสะท้อนแล้ว

### สั่ง "กลับแท่นชาร์จ" ครั้งแรก — ระบบทำถูก หุ่นไม่ขยับ

ลำดับที่เกิดจริงตาม log: สร้าง action สำเร็จ → poll 13 ครั้ง (~26 วิ) → action หายไป →
ตัดสินจาก `dockingStatus` ว่าไม่ได้จอด → ประกาศว่าไปไม่สำเร็จและเสนอเรียกเจ้าหน้าที่
**ไม่มีการอ้างว่าถึงแล้ว** ซึ่งเป็นพฤติกรรมที่ต้องการ
ชิป "สำเร็จ" ที่เห็นบนจอคือผลของ*การส่งคำสั่ง* ไม่ใช่ผลของการเดินทาง ตามสัญญาของ `go_to_place`

สาเหตุที่หุ่นไม่ขยับคือ `ROBOT_CHASSIS_MOTION_ENABLED` ปิดอยู่ (default false)
`robot_chassis.send()` ปฏิเสธ `move_to_point`/`go_home` ทุกครั้งจนกว่าจะเปิด
เป็นสวิตช์แยกจาก `ROBOT_CHASSIS_URL` โดยตั้งใจ: **ต่อเพื่ออ่านค่าได้ ไม่เท่ากับอนุญาตให้ขยับ**

กับ `_poi_pose()` เขียนรอไว้ — เดิมรู้จากเอกสารอย่างเดียว ตอนนี้มีของจริงจากเฟิร์มแวร์

## แชสซีเป็น SLAMTEC และมี REST API สาธารณะ — สั่งเดินได้โดยไม่ต้องใช้ AAR ของ Aobo (10 ก.ย. ~16:30)

**นี่เปลี่ยนแผนทั้งหมด** ตัวบล็อกที่เคยเขียนว่า "ต้องรอ AAR จากผู้ขาย" ไม่ได้บล็อกการเดินอีกต่อไป

บอร์ดนำทางอยู่ที่ 192.168.11.1 ตอบ ping ใน ~1 ms พอร์ตที่เปิด: **1445** (SDK 1.0),
**1448** (SDK 2.0 / RESTful API), **80**, **22**

อ่านจาก `/api/core/system/v1/robot/info` ได้ว่าเป็น **Slamware SDP ของ Slamtec**
firmware `5.1.1-deb-for-aobo-hermes+20250226` คือ Slamware ที่ build ให้ Aobo อีกที
แปลว่า `quickConnect()` ใน AAR ก็แค่ห่อโปรโตคอลตัวนี้ไว้ และ SLAMTEC เปิดเอกสารกับ SDK

### วิธีต่อจาก PC (ทำซ้ำได้ ไม่ต้องเปลี่ยน Wi-Fi)

PC อยู่วง 192.168.1.x จึงเข้า 192.168.11.1 ตรงๆ ไม่ได้ แต่แท็บเล็ตของหุ่นเข้าได้ทั้งสองวง
จึงให้แท็บเล็ตเป็นสะพาน ใช้ `nc` ที่มีอยู่แล้วบนเครื่อง ไม่ต้องติดตั้งอะไร

```powershell
$adb = "tools\android\platform-tools\adb.exe"
& $adb connect 192.168.1.23:5555
& $adb shell "(nohup nc -s 127.0.0.1 -p 11448 -L nc -q 5 192.168.11.1 1448 >/dev/null 2>&1 &)"
& $adb forward tcp:11448 tcp:11448
curl.exe -s http://127.0.0.1:11448/api/core/system/v1/power/status
```

`nc` ของ toybox บนหุ่นมีกับดัก: `-w` คือ timeout ตอน**เชื่อมต่อ** ไม่ใช่ตอนรออ่าน
ถ้าไม่ใส่ `-q` มันปิดทันทีที่ stdin หมดแล้วไม่ทันรับคำตอบ — ยิงตรงจาก adb shell
จะได้ผลลัพธ์ว่างเปล่าโดยไม่มี error ทางที่เชื่อถือได้คือ relay แล้วใช้ curl จริงจากฝั่ง PC

### ค่าที่อ่านได้จริงตอนตรวจ

| endpoint | ผล |
|---|---|
| `/api/core/system/v1/power/status` | แบต 35%, `on_dock`, กำลังชาร์จ, `running`, `awake` |
| `/api/core/system/v1/robot/info` | Slamware SDP, Slamtec, fw 5.1.1-deb-for-aobo-hermes |
| `/api/core/slam/v1/localization/pose` | x -0.592, y 3.627, yaw 0.187 — หุ่นรู้ตำแหน่งตัวเอง |
| `/api/core/artifact/v1/pois` | `[]` **ยังไม่มีจุดหมายสักจุด** ตรงกับที่เห็นใน RoboStudio |

### ที่ต้องระวังถ้าเลือกทางนี้

สั่งแชสซีตรงๆ = **ข้ามชั้นของแอป Aobo ทั้งชั้น** กฎความปลอดภัยในเอกสาร
[สัญญาเชื่อมต่อ](ต่อกับหุ่นยนต์%20Astronaut.md) ไม่ได้หายไป มันย้ายมาเป็นความรับผิดชอบ
ของฝั่งเราแทน: watchdog ที่สั่งหยุดเมื่อขาด heartbeat, เส้นทางหยุดที่ไม่ผ่าน Gemini
และปุ่มหยุดกายภาพ ยังต้องมีครบก่อนเปิดให้เดินจริงต่อหน้าลูกค้า
การหลบสิ่งกีดขวางอยู่ในแชสซีอยู่แล้ว แต่ **ห้ามถือว่าการหลบได้เท่ากับหยุดได้**

process `nc` ที่ค้างอยู่บนหุ่นเป็น relay ผูกกับ 127.0.0.1 เท่านั้น เข้าถึงได้ผ่าน adb
เท่านั้น และหายไปเองเมื่อรีบูต ปิดก่อนได้ด้วย `adb shell "pkill -f 11448"`

## ADB ผ่าน Wi-Fi เปิดอยู่ — คุมหุ่นได้โดยไม่ต้องคลิกบนจอ (10 ก.ย. ~16:00)

พอ PC กับหุ่นอยู่วงเดียวกันแล้ว พอร์ต 5555 ของหุ่นเปิดอยู่ และ `adb connect 192.168.1.23:5555`
**ต่อติดทันทีโดยไม่มีหน้าต่างขออนุญาตบนจอหุ่น** ใช้ `tools/android/platform-tools/adb.exe`
ที่โหลดไว้แล้ว ไม่ต้องลงอะไรเพิ่ม นี่แปลว่าเลิกคลิกมั่วผ่าน AnyDesk ได้ ติดตั้งแอป

| อ่านได้จากเครื่องจริง | ค่า |
|---|---|
| Android | 15 |
| รุ่น / CPU | ZC-3588A (Rockchip RK3588), arm64-v8a |

## เช้าวันรับหุ่น (9 ก.ย. ~10:50) — ผลเตรียมเครื่อง PC

ตรวจซ้ำก่อนหุ่นมาและแก้สิ่งที่จะทำให้หุ่นต่อไม่ติด ทุกข้อวัดจากเครื่องจริง ไม่ได้เปิดไมค์หรือสั่งอุปกรณ์

| รายการ | ผล | ต้องทำ |
|---|---|---|
| IP ของ PC | Ethernet `192.168.0.3` (Marketingroom-5G), Wi-Fi `192.168.1.43` (Embassy 2) | ให้หุ่นอยู่เครือข่ายเดียวกับ IP ที่จะใช้ |
| TLS certificate | **ออกใหม่แล้ว** SAN: localhost, DESKTOP-7ISE9HB, 192.168.0.3, 192.168.0.2, **192.168.1.43**, 127.0.0.1, ::1 หมดอายุ 9 ธ.ค. 2028 — ของเดิม*ไม่มี* Wi-Fi IP สำรองไว้ที่ `certs/backup-2026-09-09/` | — |
| HTTPS 8001 | เปิดชั่วคราวแล้ว `/health`, `/?kiosk=1`, `/display?chat=1` ตอบ 200 ทั้ง 4 ที่อยู่; TLS ผ่านทั้ง Windows store และ mkcert CA (TLS 1.3) | เปิด `run_server.py` ก่อนหุ่นต่อ |
| Firewall | **ยังไม่ผ่าน** rule "Condo Voice LAN 8001" เปิดเฉพาะ profile Private แต่ทั้งสองเครือข่ายเป็น **Public** = หุ่นต่อ 8001 ไม่ได้ | รัน PowerShell แบบ Administrator (ด้านล่าง) |
| Root CA สำหรับ Android | ก๊อปไว้ที่ `certs/rootCA-android.crt` (public cert ไม่มี key) | ติดตั้งบนหุ่นก่อนเปิดเว็บ |
| ADB | 37.0.1 ใน `tools/android/platform-tools/` ใช้ได้ | ต่อ USB + เปิด USB debugging บนหุ่น |
| ตัวจำลอง 8010 | รันค้างอยู่จากรอบก่อน | ปิดถ้าไม่ใช้ กันสับสนกับ 8001 |
| `.env` ส่วนหุ่น | ROBOT_TOKEN ว่าง, ROBOT_ENABLED ไม่ได้ตั้ง (=false), TOOL_GROUPS ไม่มี `robot`, ROBOT_MOCK_PLACES ไม่ได้ตั้ง (`/health` รายงาน `places_known: 0`) | ตั้งตามลำดับด้านล่างเมื่อถึงขั้นนั้น |

**Firewall — ต้องทำก่อนหุ่นต่อ (PowerShell → Run as Administrator):**

```powershell
netsh advfirewall firewall set rule name="Condo Voice LAN 8001" new profile=private,public
```

หรือเปลี่ยนเครือข่ายเป็น Private แทน: `Set-NetConnectionProfile -InterfaceAlias "Wi-Fi" -NetworkCategory Private`
(ทำกับ `"Ethernet"` ด้วยถ้าหุ่นมาทางสาย) ตรวจด้วย `Get-NetConnectionProfile`
ทดสอบจากมือถือในเครือข่ายเดียวกัน: เปิด `https://192.168.1.43:8001/health` ต้องได้ JSON — cert error ในขั้นนี้ไม่เป็นไร แต่ต้องไม่ timeout

**ติดตั้ง CA บนหุ่น (Android 10):** `tools\android\platform-tools\adb.exe push certs\rootCA-android.crt /sdcard/Download/`
→ Settings → Security → Encryption & credentials → Install a certificate → CA certificate → เลือกไฟล์
Chrome บนหุ่นจะเชื่อ cert แล้ว **แต่ WebView ในแอป bridge ไม่เชื่อ user CA โดย default** (targetSdk ≥ 24)
แอปต้องมี `network_security_config` ที่มี `<certificates src="user"/>` หรือฝัง rootCA เป็น `src="@raw/..."`
ไม่งั้นหน้าเว็บขาวเงียบ — อาการเดียวกับ X-Frame-Options ที่โปรเจกต์นี้เคยไล่มาสามรอบ

**หน้าที่เปิดบนจอหน้าอกหุ่น:** `https://<IP-ของ-PC>:8001/?kiosk=1&token=<WS_TOKEN>`
(หน้าคุย มีไมค์ — ไม่ใช่ `/display` ซึ่งรับอย่างเดียว ตามกฎสกิน kiosk ใน CLAUDE.md)

**ลำดับแก้ `.env` ต่อขั้น (ห้ามข้ามขั้น, รีสตาร์ตเซิร์ฟเวอร์ทุกครั้งที่แก้):**

- ขั้น 3 เสียงอย่างเดียว: ไม่ต้องแก้อะไร
- ขั้น 4 bridge MOCK: `ROBOT_TOKEN=` จาก `python -c "import secrets;print(secrets.token_urlsafe(24))"` + เพิ่ม `robot` ใน `TOOL_GROUPS`
  (ทางเลือก) `ROBOT_MOCK_PLACES=ห้องตัวอย่าง,สระว่ายน้ำ,ฟิตเนส,โต๊ะเซลส์` เพื่อซ้อมบทสนทนาก่อน bridge ส่ง `robot_ready` — ไม่มีอะไรขยับ
- ขั้น 5 เดินจริง: `ROBOT_ENABLED=true` เฉพาะตอนมีคนถือปุ่มหยุด และให้แอปตั้งความเร็วต่ำก่อน (`manager.setSpeed(SPEED_LOW)` หรือ `setCustomSpeed(0.3)`)

**สิ่งที่อ่านจาก SDK v2.0 ที่ bridge ต้องใช้ (เลข section ตรงกันทั้งฉบับจีนและไทย):**
`AoboRobotManager.init(context, SdkMode.MOCK)` ก่อน REAL (7.1) · `places` มาจาก `getPoints()` (2.6.1) ·
`robot_arrived ok:true` มาจาก `onReachedTarget` (5.4.2), `ok:false` จาก `onNavigationFailed` (5.4.3) ·
`onConnectionLost` (5.1.3) และ WebSocket หลุด = `cancelNavigation()` (2.3.4) ในเครื่องเองโดยไม่รอเซิร์ฟเวอร์ ·
แบต/ชาร์จ/คุณภาพ localization อยู่ใน `onStatusUpdate` (5.2.1) — ยังไม่มี handler ฝั่งเซิร์ฟเวอร์ ·
ความเร็ว 2.3.10/2.3.11 · self-check ไมค์ `runMicSelfCheck` (4.5.1) ทำก่อนขั้นเสียง — ข้อ 5 ยืนยันสิทธิ์ CAE
จะบอกว่าการปลุกของหุ่นต้องออนไลน์ไหม

## สิ่งที่แก้ก่อนรับหุ่น

- Live check พบ Gemini เปิดสายแต่ไม่ส่งเสียงทักทาย: เปลี่ยน Gemini 3.1 Flash Live ให้ส่งข้อความสดด้วย `send_realtime_input` ตาม API รุ่นนี้ ทดสอบจาก API จริงแล้วทั้ง greeting และประกาศถึงจุดหมายจำลอง ส่วน Gemini 2.5 ใช้เส้นทางเดิม

- JSON ที่ไม่ใช่ object หรือ type ไม่ใช่ข้อความจะถูกข้าม ไม่ทำให้สายเสียงล้ม
- `robot_ready.places` ต้องเป็น list ของชื่อที่ไม่ว่าง; ปฏิเสธชนิดผิดและชื่อยาวผิดปกติ ไม่แทนที่แผนที่ด้วยข้อมูลเสีย
- `robot_arrived` ต้องมีชื่อจุดหมายตรงกับงานที่รอ และ `ok` เป็น boolean จริง; `"false"`, `1`, ค่าว่าง หรือไม่ส่ง `ok` ไม่กลายเป็นข้อความถึงแล้ว
- คำขอที่ตรงหลายจุดหมายซึ่งไม่ใช่ชื่อซ้อนกันจะถูกปฏิเสธเพื่อถามให้ชัดก่อนส่งคำสั่ง
- เมื่อ timeout แยกได้ว่าส่ง cancel สำเร็จหรือไม่ และไม่ยืนยันว่าหุ่นหยุดจริง; สถานะสาธารณะใช้ `moving: null` เมื่อไม่ทราบ รวมตอนตัดสายและส่ง stop
- `status_source` แสดงที่มาของสถานะ: `command_sent` เป็นคำสั่งที่ส่ง ไม่ใช่ telemetry; `arrival_report` เป็น callback ของแอป

## Contract ที่มีจริงตอนนี้

ใช้ `/ws?token=<WS_TOKEN>` บน production ผ่าน TLS; bridge ต้องเป็นไคลเอนต์เสียงบน socket เดียวกัน ส่ง `robot_ready` หลัง SDK พร้อมพร้อม `token=<ROBOT_TOKEN>` ซึ่งเป็นคนละ secret กับ WS_TOKEN

```json
{"type":"robot_ready","token":"<ROBOT_TOKEN>","places":["Lobby"]}
{"type":"robot","action":"move_to_point","args":{"place":"Lobby"}}
{"type":"robot","action":"cancel_navigation","args":{}}
{"type":"robot","action":"go_home","args":{}}
{"type":"robot_arrived","place":"Lobby","ok":true}
{"type":"robot_arrived","place":"Lobby","ok":false}
```

เมื่อ `go_home` จบ callback ใช้ `place:"base"`; ถึงฐานไม่ได้ยืนยันกำลังชาร์จ ต้องตรวจจาก SDK จริง การเปิดเว็บธรรมดาไม่ทำให้เว็บเรียก AAR หรือส่ง `robot_ready` เองได้

**ข้อจำกัดที่ต้องแก้ร่วมกับ bridge ก่อนใช้งานเดินอิสระ:** production ยังไม่มี command ID/ACK/heartbeat/handler สำหรับ battery หรือ charging telemetry การส่ง socket สำเร็จหมายถึงส่งออกได้เท่านั้น และ callback เก่าของจุดหมายเดิมยังแยกจากงานใหม่ที่จุดเดียวกันไม่ได้ ตัวจำลองมี lifecycle ของตัวเองแต่ไม่ได้ทำให้ protocol จริงมีสิ่งเหล่านี้ การสลับ/จบสายเสียงยังทำให้ช่องสั่งหุ่นหลุด ต้องทดสอบ local cancel/watchdog ด้วย

## ตรวจซ้ำได้โดยไม่สั่งอุปกรณ์

รันในโฟลเดอร์โปรเจกต์:

```powershell
.venv-smoke\Scripts\python.exe -X utf8 scripts/check_robot_readiness.py --health
# เมื่อได้รับไฟล์แล้ว เพิ่ม --sdk "path\vendor.aar" --apk "path\bridge.apk"
```

Exit 2 = ยังขาด prerequisite, exit 0 = prerequisite ที่สคริปต์ตรวจผ่านเท่านั้น ไม่ใช่รับรองฮาร์ดแวร์ ไฟล์ APK มีอยู่ไม่ได้แปลว่าเข้ากันกับหุ่น ห้ามใส่ secret จริงลง CHANGELOG หรือเอกสาร

Production ใช้ `.venv-smoke\Scripts\python.exe run_server.py` ซึ่งอ่าน HOST/PORT/TLS จาก `.env`; อาจเปิด background features ตาม config จึงให้ผู้ดูแลเปิดขณะเตรียมทดสอบจริง หากพอร์ตใช้อยู่ให้ตรวจ process เดิมก่อนเปิดซ้ำ ตัวจำลองก่อนหุ่นมาที่พอร์ต 8010 ถูกเลิกใช้แล้ว
