# ต่อ Emma เข้ากับหุ่นยนต์ Astronaut (Aobo SDK)

ฝั่งเซิร์ฟเวอร์ทำเสร็จแล้วและเทสต์ครบ ฝั่งแอป Android ยังไม่ได้เขียน
เอกสารนี้คือสิ่งที่แอปต้องทำ เขียนไว้ให้ครบพอที่คนเขียนแอปไม่ต้องมาถาม

---

## ทำไมแบ่งแบบนี้

SDK (`aoborobotsdk-v2.0.aar`) เป็น Android เท่านั้น และ `quickConnect()` วิ่งไปที่
`192.168.11.1:1445` คือบอร์ดนำทางในตัวหุ่นเอง เซิร์ฟเวอร์ FastAPI บน PC
เรียก SDK ตรงๆ ไม่ได้ ต้องมีอะไรที่รันบนหุ่นเป็นคนเรียก

**เซิร์ฟเวอร์ตัดสินใจว่าจะทำอะไร แอปบนหุ่นเป็นคนทำ** และคุยกันผ่าน
**WebSocket เส้นที่เปิดอยู่แล้ว** ไม่ใช่พอร์ตใหม่บนหุ่น

เพราะแอปต่อ `/ws` อยู่แล้วในฐานะไคลเอนต์เสียง — ส่งไมค์ขึ้น รับเสียงกับ
`{"type":"slide"}` ลง การเพิ่ม `{"type":"robot"}` เข้าไปในสายเดิมไม่มีต้นทุน
หุ่นไม่ต้องเปิดรับ connection ขาเข้า และย้าย Wi-Fi เปลี่ยน IP ก็ไม่พัง
ถ้าแยกเป็นอีกช่อง จะกลายเป็นอีกอย่างที่ต้องยืนยันตัวตน ต้อง reconnect
ต้องดีบัก — และเถียงกับช่องแรกได้ว่ากำลังคุยกับหุ่นตัวไหนอยู่

---

## สิ่งที่แอปต้องส่งขึ้น

**ตอนเชื่อมต่อเสร็จ ส่งทันที**

```json
{"type": "robot_ready", "places": ["ห้องตัวอย่าง", "สระว่ายน้ำ", "ฟิตเนส"]}
```

`places` มาจาก `manager.getPoints()` ใช้ชื่อ POI ตามที่อยู่ในแผนที่หุ่นจริง

**นี่คือสิ่งเดียวที่ทำให้เครื่องมือเดินทำงาน** ก่อนได้รับข้อความนี้ เซิร์ฟเวอร์ถือว่า
ยังไม่มีหุ่น และคำสั่งเดินทั้งหมดจะรันใน mock mode — เบราว์เซอร์ธรรมดาก็ต่อ `/ws`
ได้เหมือนกันและมันไม่มีขา `available()` จึงไม่ยอมแปลว่า "มีซ็อกเก็ตเปิดอยู่"

**ตอนเดินถึงที่หมาย หรือไปไม่ได้**

```json
{"type": "robot_arrived", "place": "ห้องตัวอย่าง", "ok": true}
```

ส่งจาก callback ของ SDK (`AoboRobotListener`) `ok: false` เมื่อมีสิ่งกีดขวางหรือหาทางไม่เจอ

---

## สิ่งที่แอปจะได้รับลงมา

```json
{"type": "robot", "action": "move_to_point", "args": {"place": "ห้องตัวอย่าง"}}
{"type": "robot", "action": "cancel_navigation", "args": {}}
{"type": "robot", "action": "go_home",           "args": {}}
```

แปลงเป็น SDK ตรงๆ

| action | SDK |
|---|---|
| `move_to_point` | หา POI จาก `getPoints()` ตามชื่อ แล้ว `moveToPoint(poi)` |
| `cancel_navigation` | `cancelNavigation()` |
| `go_home` | `goHome()` |

---

## ข้อที่พลาดง่ายที่สุด

**`go_to_place` คืนค่าทันที ไม่รอถึงที่หมาย** และแอปต้องไม่ทำให้มันรอ

การเดินไปห้องตัวอย่างใช้เวลาครึ่งนาที ส่วน function calling เป็น synchronous —
โมเดลพูดอะไรไม่ได้เลยจนกว่าเครื่องมือจะคืนค่า ถ้ารอถึงที่หมาย เท่ากับหุ่นยืนเงียบ
ครึ่งนาทีข้างลูกค้าที่มันเพิ่งบอกว่าจะพาไป

บั๊กนี้เคยเกิดที่นี่มาแล้วในรูปแบบเล็กกว่า: `start_presentation` รอหน้าต่างเบราว์เซอร์
แล้ววัดได้ว่าเงียบไป 4 วินาทีต่อหน้าคนที่เพิ่งขอดูของ

การแจ้งว่าถึงจึงกลับมาเป็น**เทิร์นใหม่**ผ่าน `robot_arrived` ไม่ใช่ค่าที่คืนจากเครื่องมือ
ถ้าเก็บไว้ในสถานะเฉยๆ จะไม่มีใครอ่านมันเลย เพราะโมเดลไม่ได้ poll และหลังผลลัพธ์
เครื่องมือที่เงียบก็ไม่มีขอบเทิร์นถัดไปมาให้

## เสียง

ตามคู่มือ เมนบอร์ดไมโครโฟนทำ **ลดเสียงรบกวน ตัดเสียงสะท้อน ระบุตำแหน่งแหล่งเสียง
การขัดจังหวะ และการปลุก** ในตัว แปลว่า AEC กับ barge-in เป็นเรื่องของฮาร์ดแวร์
ไม่ใช่ของเรา — และ `MicConfig.sampleRate = 16000` ตรงกับที่ Gemini Live ต้องการพอดี
ไม่ต้อง resample

**แต่ต้องยืนยันสี่ข้อกับผู้ขายก่อน อย่าเพิ่งเชื่อเอกสาร**

1. **ไมค์ 4 ตัวหรือ 8 ช่อง** คู่มือเขียน "ชุดไมโครโฟน 4 ตัว" แต่ `MicConfig.channels = 8`
   น่าจะเป็น 4 ไมค์ + ช่องอ้างอิงสำหรับ AEC — ต้องรู้ว่า**ช่องไหนคือเสียงที่ผ่านการ
   ประมวลผลแล้ว** เพราะเราส่ง mono เข้า Gemini ส่งผิดช่องคือส่งเสียงดิบที่ยังไม่ตัด echo
2. **wake word ภาษาไทยได้ไหม** `MicConfig.wakeWordModel = "res_ivw_model.bin"` กับ
   การยืนยันสิทธิ์ **CAE** ในรายการ self-check ชี้ว่าเป็นเอนจิน iFLYTEK ซึ่งโมเดลคำปลุก
   เทรนแยกต่อคำ "เอ็มม่า" ภาษาไทยแทบแน่ว่าต้องสั่งทำ ถามราคากับระยะเวลาก่อน
3. **ปิดระบบสนทนาเดิมของหุ่นได้ไหม** คู่มือบอกว่าหุ่นมีระบบเสียงของตัวเอง
   (ฐานข้อมูลบทสนทนาบนคลาวด์ จีน+อังกฤษ) ถ้าปิดไม่ได้ มันจะแย่งไมค์กับ Emma
   **ข้อนี้เสี่ยงที่สุด** ถ้าปิดไม่ได้ต้องคิดสถาปัตยกรรมใหม่ ไม่ใช่แก้โค้ด
4. **การปลุกต้องต่อเน็ตไหม** self-check ข้อ 3 ตรวจเครือข่าย ข้อ 5 ตรวจสิทธิ์ CAE
   ถ้าการปลุกต้องยืนยันสิทธิ์ออนไลน์ แผน offline mode จะพังตั้งแต่ขั้นแรก

## ทดสอบโดยไม่มีหุ่น

SDK มี `SdkMode.MOCK` และฝั่งเซิร์ฟเวอร์ก็มี mock ของตัวเอง — ปล่อย `ROBOT_ENABLED=false`
หรือแค่ไม่ส่ง `robot_ready` เครื่องมือจะทำงานครบ ไม่มีอะไรขยับ และผลลัพธ์ทุกอันจะมี
`hardware: "mock"` เพื่อให้โมเดลบอกลูกค้าตรงๆ ว่ายังพาไปไม่ได้

กฎนี้มาจากบั๊กจริง: เครื่องมือ IR เคยรายงาน "mock" เป็น "ok" แล้วหุ่นประกาศว่า
ปิดแอร์ให้แล้วทั้งที่ไม่มีอะไรถูกส่งออกไปเลย — กับหุ่นที่เดินได้ ความผิดพลาดแบบเดียวกัน
จะดังกว่านั้นมาก เพราะลูกค้ายืนอยู่ข้างๆ และเห็นว่ามันไม่ขยับ

```bash
python -m pytest tests/test_robot.py -q     # 25 ตัว ไม่ต้องมีหุ่น
```

**ลองด้วยเสียงจริงก็ได้** ตั้ง `ROBOT_MOCK_PLACES` ใน `.env` เป็นรายชื่อจุดสมมติ

```
ROBOT_MOCK_PLACES=ห้องตัวอย่าง,สระว่ายน้ำ,ฟิตเนส,โต๊ะเซลส์
```

ไม่มีอันนี้ `KNOWN_PLACES` จะว่าง ทุกคำขอเลยตกลงกิ่ง "ไม่รู้จักจุดนี้" อย่างเดียว
จุดสมมติไม่ทำให้อะไรขยับ `hardware` ยังเป็น `"mock"` เหมือนเดิม
และพอหุ่นจริงส่ง `robot_ready` มา แผนที่ของมันจะทับรายชื่อสมมติทันที

**สิ่งที่จุดสมมติยัง*ไม่*ให้ลอง** คือเส้นทางที่สำเร็จ — "กำลังพาไปนะคะ" → คุยระหว่างทาง
→ "ถึงแล้วค่ะ" เพราะ mock ตอบว่าพาไปไม่ได้เสมอ `moving` จึงไม่เคยเป็น true
และ `arrived()` ไม่เคยถูกเรียก

แปลว่าข้อที่เสี่ยงที่สุด (ห้ามบอกว่าถึงก่อนถึงจริง) **ทดสอบด้วยเทสต์อัตโนมัติได้
แต่ฟังด้วยหูยังไม่ได้** จนกว่าจะมีหุ่นจริง หรือจนกว่าจะเพิ่มโหมดจำลองการเดินสำเร็จ
ซึ่งจงใจยังไม่ทำ เพราะ mock ที่อ้างว่าสำเร็จคือบั๊กที่โปรเจกต์นี้เคยเจอมาแล้วรอบหนึ่ง

## ยังไม่ได้ทำ

- **`gesture()` / `executeArmActionGroup`** จงใจไม่ทำ เพราะหมายเลข action group
  ไม่มีความหมายจนกว่าผู้ขายจะบอกว่าเลขไหนคือท่าอะไร เครื่องมือที่โมเดลใช้ไม่เป็น
  คือเครื่องมือที่ไม่เคยถูกเรียก ซึ่ง `scripts/analyze_log.py` มีไว้ตรวจจับพอดี
- **ยืนยันตัวตนระหว่างหุ่นกับเซิร์ฟเวอร์** `/ws` ยังเปิดรับทุกอย่างที่ถึงพอร์ตได้
- **สถานะแบตเตอรี่** `onStatusUpdate` มีข้อมูลแบตอยู่ แต่ยังไม่มีใครส่งขึ้นมา
