# ผลค้นพอร์ต บอร์ด และคำสั่งหุ่นจากไฟล์เท่านั้น

> **แก้ไขจากหลักฐานที่ได้ภายหลัง:** พบ AIDL, dynamic receiver ของ CH340, คำสั่ง `#STOP` และ parser `#STOP+OK` จากโค้ดที่คลายการห่อแล้ว ดู [รายงาน interface ที่กู้ได้](robot-recovered-interface-2026-09-11.md) ยังไม่ทดสอบผลหยุดกับบอร์ด เนื้อหาด้านล่างเป็นผลตรวจช่วงก่อนหน้านั้น

วันที่ 11 กันยายน 2026 ผู้ใช้กำหนดให้ค้นข้อมูลเท่านั้น ห้ามควบคุมหรือสั่งหุ่น ขอบเขตรอบนี้จึงเป็นการอ่านสำเนาบนคอมและเอกสารสาธารณะ ไม่ใช้ ADB ไม่เรียก REST ของหุ่น ไม่เปิดพอร์ตอนุกรม ไม่เปิดแอปหุ่น และไม่เปลี่ยนค่าหรือเรียก service ใด ๆ บนหุ่น

## สิ่งที่ค้นพบเพิ่ม

| เรื่อง | หลักฐานใหม่ | ข้อสรุปที่ใช้ได้ |
|---|---|---|
| ชนิดควบคุมแขน | ถอด array ใน resources.arsc ได้ Relay คู่ค่า `0`, Servo Board คู่ค่า `1` | แอปมีสองตัวเลือก; ยังไม่ยืนยันโปรโตคอลที่แต่ละโหมดส่ง |
| หมายเลขเซอร์โวใน UI | `servo_number_options`: `1`, `11`, `7`, `8`, `All`; values ตามลำดับ `1`, `11`, `7`, `8`, `0` | เป็นตัวเลือกของแอป ไม่ใช่จำนวนมอเตอร์ทั้งหมดหรือ mapping หัว/แขน/นิ้ว และไม่สรุปว่าเลข 0 เป็น broadcast ของบอร์ด |
| วิธีเชื่อมการควบคุม | Individual access คู่ `0`, Unified Access Control Broad คู่ `1` (ตามการสะกดในแอป) | มีทางเลือกเชื่อมแยกหรือผ่านบอร์ดรวมใน UI; ยังไม่รู้ handler จริง |
| ชิป USB/UART | array มี CP210x, CH340, PL2303, FT232R, FT231X, Teensyduino | เป็นรายการตัวเลือกไดรเวอร์; ไม่ใช่อุปกรณ์ที่ติดตั้งครบทุกชนิด |
| บริการอนุกรม | Manifest ประกาศ `com.aobo.robot.ai3.usbserial.SerialdataService` | พบ component จริง แต่ยังไม่มีวิธีเรียกหรือ schema ของข้อมูล |
| บริการจอสองจอ | Manifest ประกาศ `com.aobo.robot.ai3.services.DoubleScreenService` | มี intent action ชื่อ `com.aobo.robot.luncher.services.DoubleScreenService`; ไม่มีข้อมูลคำสั่งเปลี่ยนภาพใน manifest |
| หน้าสีหน้า | Manifest ประกาศ `FaceExpressionActivity` และ `FaceExpressionNewActivity` ใน `com.aobo.aibot.ui.faceexpression` | สอดคล้องกับ layout และไฟล์ภาพที่เคยพบ; ไม่ยืนยันว่าหน้าดังกล่าวส่งถึงจอบนหัวของตัวนี้ |

ชื่อที่ลงท้าย `com.aobo.robot.luncher.services.DoubleScreenService` เป็น **ชื่อ intent action** ของ service ที่ลงท้าย `com.aobo.robot.ai3.services.DoubleScreenService` ไม่ใช่หลักฐานว่ามี service สองตัวตามสองชื่อนี้ Manifest ไม่ระบุ exported แบบชัดเจนสำหรับ component เหล่านี้ รอบนี้ไม่ลองเปิด component หรือส่ง intent

หน้า `fragment_usb_to_uart.xml` มีตัวเลือกสำหรับไมโครโฟน การ์ด/บอร์ด อัลตราโซนิกหน้า/หลัง มอเตอร์ และ GSM จึงช่วยยืนยันว่าแอปมีการจัดการอุปกรณ์หลายชุด แต่ layout ไม่แสดงพอร์ตจริงที่บันทึกไว้ และไม่มีตารางว่าพอร์ตใดเป็นแขนหรือหัว

## โปรโตคอล Torobot ที่พบจากผู้ผลิตบอร์ด

คู่มือ Astronaut หน้า 6 อ้างถึงซอฟต์แวร์ Torobot จึงค้นต่อและพบ [Servo Controller Instructions for Use จาก Torobot](https://dl.torobot.com/down/usc_en.pdf) โดยตรง ตรวจภาพหน้า 3, 5 และ 6 แล้ว

เอกสารแสดงรูปแบบรายเซอร์โว `#<ช่อง>P<พัลส์>T<เวลา>\r\n` และกลุ่มท่า `#<กลุ่ม>GC<รอบ>\r\n` รองรับสั่งหลายเซอร์โวพร้อมกันหรือเรียกหลายกลุ่มตามลำดับ โดยต้องจบข้อความด้วย CRLF และไม่มีช่องว่าง หน้า 5 ระบุว่าซอฟต์แวร์มีการอ่านหมายเลขกลุ่มที่บันทึกไว้ แต่ไม่ได้ให้โปรโตคอลอ่านกลับในตารางหน้า 6 **บันทึกรูปแบบไว้เป็นข้อมูลอ้างอิงเท่านั้น ไม่ได้สร้างหรือส่งคำสั่งให้หุ่น**

ความเข้ากันได้ยังไม่ยืนยัน: ภาพบอร์ดในเอกสารเป็น USC-32 และกล่าวถึง S1–S32 ขณะที่คู่มือหุ่นระบุ 20 ช่อง เอกสาร Torobot ระบุ 9600 8N1 ส่วน SDK Aobo ให้ค่าเริ่มต้น 115200 ชื่อซอฟต์แวร์เหมือนกันจึงเป็นเบาะแส แต่ยังไม่พอใช้แทนโปรโตคอลของเครื่องจริง

ตาราง Torobot ไม่ได้ให้ wiring map ของ Astronaut ไม่อธิบาย `#CC` และไม่ระบุว่าช่องใดคือหัว มือ หรือนิ้ว จึงยังไม่สามารถแปลงคำว่า “จับมือ” เป็นเลขกลุ่มที่ถูกต้องได้

## เปรียบเทียบ APK ที่มีอยู่

อ่าน ZIP และตาราง DEX ของสำเนา 3 รุ่น โดยไม่ติดตั้งหรือรัน APK:

| สำเนา | string IDs ใน classes.dex | class definitions ที่มองเห็น | ผล |
|---|---:|---:|---|
| APK ที่ติดตั้งปัจจุบัน | 886 | 4 | พบ StubApp / Jiagu; ไม่พบโค้ด handler แขนในส่วน DEX ที่อ่านได้ |
| APK เก่าชื่อไฟล์ระบุ 227 / 4m | 819 | 4 | ห่อป้องกันแบบเดียวกัน |
| APK เก่าชื่อไฟล์ระบุ 226 / 6m | 819 | 4 | ห่อป้องกันแบบเดียวกัน |

ตัวเลขนี้เป็นตารางโครงสร้าง DEX ที่เปิดอ่านได้ ไม่ใช่จำนวน class ทั้งแอปหลังโหลดจริง การค้น printable strings ของ native .so ตามตัวกรอง SerialPort/ttyUSB/ttyACM/Torobot/CH340/CP210 ไม่พบ marker ที่ยืนยันพอร์ต ไม่ใช่ข้อพิสูจน์ว่าไม่มีโค้ดดังกล่าว เพราะข้อมูลอาจถูกห่อไว้หรืออยู่รูปแบบอื่น

ค้นรูปแบบคำสั่ง Torobot และชื่อบริการในไฟล์ข้อความ shared storage 136 ไฟล์กับรายงาน Android ที่เลือก 4 ไฟล์ รวม 140 ไฟล์ พบชื่อ DoubleScreenService ใน package dump แต่ไม่พบชุดคำสั่งที่ผูกกับข้อต่อจากการค้นชุดนี้ ขอบเขตการค้นนี้ไม่รวมข้อมูลส่วนตัวแอปที่ไม่ได้สำรองหรือโค้ดที่ถูกป้องกัน

## พอร์ตที่มีหลักฐานเดิม และสิ่งที่ยังขาด

- SDK ระบุค่าเริ่มต้นแขน `/dev/ttyUSB1` ที่ 115200 แต่ snapshot serial_devices ที่สำรองไม่พบ ttyUSB/ttyACM
- USB inventory เดิมพบ CP2102 และ USB Serial ชนิด CH340-family; ยังไม่ทราบว่าเส้นใดต่ออุปกรณ์ใด การจับคู่ชื่อไดรเวอร์กับ array ในแอปไม่ได้ยืนยันการเดินสาย
- `/dev/ttyS0`, `ttyS1`, `ttyS3`, `ttyS4`, `ttyS6`, `ttyS8`, `ttyS9` ปรากฏใน snapshot แต่ยังไม่มีหลักฐานว่าเป็นพอร์ตแขน จึงไม่เดาหรือเลือกพอร์ต
- ขาด channel map, รุ่นบอร์ดที่อ่านจากตัวจริง, ค่า home/min/max, รายการกลุ่มท่า, สัญญาข้อมูลของ SerialdataService/DoubleScreenService และ SDK implementation ที่ตรงรุ่น

จึงค้นเจอ **ชนิดการตั้งค่า ชื่อบริการ และโปรโตคอลอ้างอิงที่น่าตรวจเทียบ** เพิ่มแล้ว แต่ยังไม่พบเส้นทางคำสั่งหัว/แขน/นิ้วแบบครบตั้งแต่ API ถึงข้อต่อที่พิสูจน์ได้จากสำเนาเหล่านี้

## หลักฐานและการตรวจงาน

- สคริปต์อ่านไฟล์อย่างเดียว: `data/robot-inspection/static-port-research-20260911/inspect_offline.py` ใช้ pathlib/zipfile/struct/json/re ไม่มีโมดูลเครือข่าย เรียก process หรือโค้ดเปิดอุปกรณ์
- `static-evidence.json`: arrays, component declarations, intent action, DEX counts และผลค้น native markers
- `text-search-evidence.json`: จำนวนไฟล์และ token ที่พบ โดยไม่คัดลอกข้อความส่วนตัวจาก log มาลงรายงาน
- `torobot-usc_en.pdf` และ `torobot-reference.json`: สำเนาคู่มือสาธารณะ URL และ SHA-256; ไม่มีการดาวน์โหลด/ติดตั้ง driver หรือโปรแกรมควบคุม
- ตรวจ parser กับค่า Relay/Servo Board ที่มีหลักฐานหน้าจอเดิมตรงกัน และตรวจชื่อ ArmTestActivity ตรงกับผลสำรวจก่อนหน้า; ตรวจตารางคำสั่งจากภาพ PDF แล้ว
- รายงานนี้ไม่มีไฟล์ส่วนตัวจากหุ่นเพิ่ม ไม่มีการอ่านสถานะสดหรือทดสอบการควบคุม และไม่มี runtime code เปลี่ยนแปลง

## เพิ่มเติม: พอร์ตอนุกรมเคยขึ้นจริง แล้วถูกตัดหลังบูต 60 วินาที

อ่าน `backup-20260910-174700/inventory/recent_android_log.txt` ซ้ำแล้วพบลำดับเหตุการณ์
ที่ตอบคำถามว่าทำไม `ls /dev/ttyUSB*` ตอนสำรองจึงไม่พบอะไร:

```
17:07:16  registered new interface driver ch341 / cp210x
17:07:17  usb 9-1.2: Product: CP2102 USB to UART Bridge Controller
17:07:17  cp210x 9-1.2: converter now attached to ttyUSB10
17:07:18  ch341  9-1.4: converter now attached to ttyUSB11
17:08:18  ch341-uart ttyUSB11: converter now disconnected   ← ห่างกัน
17:08:18  cp210x     ttyUSB10: converter now disconnected   ← 3 มิลลิวินาที
```

สามข้อที่อ่านได้จากตรงนี้:

1. **มีตัวแปลง USB→UART สองตัวต่ออยู่จริง** CP2102 ที่พอร์ต `9-1.2` และ CH341 ที่ `9-1.4`
   ตรงกับรายการไดรเวอร์ที่แอปมีตัวเลือกไว้ ตัวใดตัวหนึ่งน่าจะเป็นบอร์ดเซอร์โว
   แต่**ยังไม่ยืนยันว่าตัวไหน** — ต้องดูตอนที่มันขึ้นอยู่
2. **ชื่อพอร์ตคือ `ttyUSB10` และ `ttyUSB11` ไม่ใช่ `ttyUSB1`** ค่าเริ่มต้นที่ SDK ระบุคือ
   `/dev/ttyUSB1` ซึ่งเป็นคนละ device node กัน ถ้าโค้ดใดยึดค่านี้ตายตัว มันจะหาบอร์ดไม่เจอ
   เลขที่เริ่มที่ 10 ยังบอกว่าเลข 0–9 ถูกจองไว้แล้ว มีอุปกรณ์อนุกรมอื่นหรือเคยต่อ–หลุดซ้ำมาก่อน
3. **ทั้งสองตัวหลุดพร้อมกันในระยะ 3 มิลลิวินาที ที่เวลา 60 วินาทีหลังต่อ** สองอุปกรณ์คนละพอร์ต
   คนละชิป หลุดพร้อมกันเป๊ะขนาดนี้ไม่ใช่สายหลวม แต่คือ**ไฟถูกตัด**หรือพอร์ตถูกสั่งปิด
   คู่มือระบุว่าไฟเลี้ยงเซอร์โวแยกวงจรจากบอร์ดควบคุม จึงเข้ากันได้กับภาพนี้

สิ่งที่ต้องทำก่อนเรื่องอื่นทั้งหมด และเป็นการอ่านอย่างเดียว ไม่ส่งคำสั่งมอเตอร์:
**บูตหุ่นแล้วดู `/dev/ttyUSB*` ภายในนาทีแรก** พร้อมเก็บ log ช่วงนั้น ถ้าพอร์ตขึ้นจริงแล้วหายอีก
ให้หาว่าอะไรตัด ถ้าพอร์ตอยู่ต่อ แปลว่าสภาพวันที่ 10 เป็นเรื่องเฉพาะครั้ง

## ทบทวนข้อสงสัยเรื่องความเข้ากันได้ของ Torobot

รายงานข้างบนตั้งข้อสงสัยไว้สองข้อ ตรวจกับข้อความคู่มือ Astronaut แล้วข้อหนึ่งคลายลง:

- **baud ไม่ขัดกัน** คู่มือหน้า 6 ระบุสเปกบอร์ดข้อ 5 ว่า `Baud rate range: 9600, 19200,
  38400, 57600, 115200, 128000` และบอร์ดตระกูลนี้ตรวจ baud อัตโนมัติ ค่า 115200 ของ SDK
  จึง**อยู่ในช่วงที่บอร์ดรับ** ไม่ใช่ค่าที่ขัดกับเอกสาร Torobot ที่ระบุ 9600 เป็นค่าเริ่มต้น
- **จำนวนช่องยังต่างจริง** เอกสารที่โหลดได้เป็น USC-32 (S1–S32) ส่วนคู่มือหุ่นระบุ 20 ช่อง
  เป็นคนละรุ่นในตระกูลเดียวกัน ข้อนี้ยังไม่ยืนยัน

## ข้อสังเกตจากลำดับตัวเลขใน `servo_number_options`

ค่าที่พบคือ `1`, `11`, `7`, `8`, `All` — **ไม่ได้เรียงจากน้อยไปมาก** ลำดับที่คนเขียนจัดเอง
มักสะท้อนการจับกลุ่ม ไม่ใช่การเรียงเลข และบนบอร์ด 20 ช่อง เลข 1 กับ 11 ห่างกัน 10 พอดี
ซึ่งเท่ากับครึ่งหนึ่งของจำนวนช่อง

สมมติฐานที่ทดสอบได้: ถ้าเดินสายเป็นแขนซ้ายช่อง 1–10 แขนขวาช่อง 11–20 แล้ว **ช่อง N กับ
N+10 จะเป็นข้อต่อคู่กระจกกัน** ทดสอบด้วยการสั่งช่อง 1 กับช่อง 11 ด้วยค่าพัลส์เดียวกัน
แล้วดูว่าแขนสองข้างขยับเป็นภาพสะท้อนกันหรือไม่ ถ้าใช่ ได้โครงของ channel map ทันทีครึ่งหนึ่ง
**เป็นสมมติฐาน ไม่ใช่ข้อสรุป** และการทดสอบนี้อยู่หลังเงื่อนไขความปลอดภัยทั้งหมดในหัวข้อ 7
ของรายงานความสามารถการเคลื่อนไหว

## SerialdataService ไม่ใช่ทางผ่านที่จำเป็น

ยังไม่รู้ schema ของ service นี้ และไม่จำเป็นต้องรู้เพื่อสั่งบอร์ด เพราะโปรโตคอลเป็นข้อความ
บนพอร์ตอนุกรม เขียนลง device node ตรงๆ ได้ถ้ารู้ว่าพอร์ตไหนและมีสิทธิ์เข้าถึง
service ของแอปเป็นเพียง client ตัวหนึ่งของพอร์ตเดียวกัน — และถ้ามันเปิดพอร์ตค้างไว้
มันจะเป็นตัวที่ต้องปิดก่อน ไม่ใช่ตัวที่ต้องเรียก **คอขวดจริงคือพอร์ตที่หายไป ไม่ใช่ schema**

## แก้ข้อสรุปเรื่องพอร์ตหลุด: ไม่ใช่ไฟถูกตัด แอปเป็นคนยึดพอร์ต (11 ก.ย. เย็น, ต่อ adb ผ่าน Wi-Fi)

ต่อ adb ผ่าน Wi-Fi (`adb pair` แล้ว `adb connect`) เข้าหุ่นที่ 192.168.1.24 แล้วตรวจสด
ผลคือข้อสรุปก่อนหน้าที่ว่า "ไฟถูกตัดหรือพอร์ตถูกสั่งปิด" **ผิด** หลักฐานสี่ชิ้น:

| ตรวจอะไร | ผล |
|---|---|
| `ls /dev/ttyUSB*` | ไม่มีเลย (บูตมาแล้ว 8 นาที) |
| อุปกรณ์ USB ที่ kernel เห็น | **มีครบ** — `3-1.2` = CP2102 (10c4:ea60), `3-1.4` = CH340 (1a86:7523) |
| ไดรเวอร์ที่ผูกกับสองตัวนั้น | **`usbfs`** ไม่ใช่ `cp210x` / `ch341-uart` |
| `/sys/bus/usb-serial/devices/` | ว่างเปล่า ทั้งที่ `/sys/bus/usb-serial/drivers/` มี cp210x และ ch341-uart ลงทะเบียนอยู่ |

`usbfs` แปลว่ามีแอปเรียก `claimInterface()` ผ่าน Android USB Host API จับอินเทอร์เฟซไว้
ซึ่ง**บังคับให้ไดรเวอร์ของ kernel ปล่อยอุปกรณ์** และ `com.aobo.robot.ai3` กำลังรันอยู่จริง
รายการไดรเวอร์ที่เคยพบใน resources ของแอป (CP210x, CH340, PL2303, FT232R, FT231X,
Teensyduino) คือรายการอุปกรณ์ของไลบรารี usb-serial-for-android ตรงตัว

**นี่อธิบาย log วันที่ 10 ได้หมดและดีกว่าคำอธิบายเดิม** ตอนบูต kernel ผูกไดรเวอร์ก่อน
จึงเห็น `ttyUSB10`/`ttyUSB11` ขึ้น พอแอปสตาร์ตเสร็จที่หกสิบวินาทีแล้วยึดอินเทอร์เฟซ
kernel ก็ปล่อย เลยขึ้นว่า "disconnected" ทั้งสองตัวห่างกันสามมิลลิวินาที —
สองตัวพร้อมกันเป๊ะเพราะเป็นการกระทำของโปรแกรมเดียว ไม่ใช่เพราะไฟเส้นเดียวกัน

### ผลต่อหน้า /arm ที่เพิ่งทำ

สมมติฐาน `ROBOT_ARM_PORT=/dev/ttyUSB10` **ใช้ไม่ได้ตราบใดที่แอป Aobo ยังรัน** และต่อให้
หยุดแอปจนไดรเวอร์ผูกกลับ ก็ยังติดอีกด่าน: ไม่มีกฎใน `ueventd` สำหรับ `ttyUSB` เลย
(มีแต่ `ttyS0/1/3/4/6/8` ตั้งไว้ 0666 system:system) device node ที่ไม่มีกฎจะเป็นของ root
อย่างเดียว ส่วน shell ของ adb คือ uid 2000

ทางที่เหลือ เรียงตามที่มีหลักฐานรองรับ:

1. **ผ่าน usbfs โดยตรง** — `/dev/bus/usb/003/*` เป็น `crw-rw-rw-` เขียนได้โดยไม่ต้อง root
   แต่ต้องทำ control transfer ของ CP210x/CH340 เอง ไม่ใช่ `printf` ลงไฟล์
2. **หยุดแอป Aobo แล้วใช้ ttyUSB** — เครื่องนี้เป็น `userdebug`, `ro.debuggable=1`
   และมี `/system/xbin/su` อยู่จริง จึงยกสิทธิ์ได้ **แต่เป็นการกระทำที่เปลี่ยนสภาพหุ่น
   และหยุดแอปหลักของมัน ต้องให้เจ้าของตัดสินใจ ไม่ใช่เครื่องมืออัตโนมัติ**
3. **ผ่าน `SerialdataService` ของแอปเอง** — กลับมามีน้ำหนักขึ้น เพราะแอปคือผู้ถือพอร์ต
   ข้อสรุปเดิมที่ว่า "ไม่จำเป็นต้องรู้ schema" ถูกเฉพาะกรณีที่พอร์ตว่าง ซึ่งมันไม่ว่าง
4. **เขียนแอป Android ของเราเองด้วย usb-serial-for-android** — ทางเดียวกับที่แอปผู้ขายใช้
   และเข้ากับแผน APK ของ Emma ที่คุยกันไว้

### ของแถมจากการสำรวจครั้งนี้

- `3-1.3` = **Bothlent UAC Dongle** ผูกกับ `snd-usb-audio` คือไมค์อาร์เรย์ ตรงกับคู่มือที่ระบุ 4 ไมค์
- `3-1.1` = **USB RGB Camera** ผูกกับ `uvcvideo`
- `9-1.1` = จอสัมผัส ILITEK
- แชสซีไม่ได้อยู่บน USB เลย ตามที่รู้อยู่แล้วว่าอยู่บน Ethernet
- `ttyS0, S1, S3, S4, S6, S8` มีอยู่และเป็น 0666 เขียนได้โดยไม่ต้อง root
  **ยังไม่มีหลักฐานว่าตัวใดเกี่ยวกับแขน และห้ามลองเขียนมั่ว** — กฎ ueventd ที่อ่านได้
  ผูกบางตัวไว้กับ bluetooth และ gps

## แก้ให้แคบลงอีกชั้น: usbfs บอกว่ามีคนยึด ไม่ได้บอกว่าใคร

ข้อสรุปข้างบนที่เขียนว่า "แอป `com.aobo.robot.ai3` ยึดอินเทอร์เฟซ" **แรงเกินหลักฐาน**
สิ่งที่ `usbfs` พิสูจน์คือ*มีโปรแกรมฝั่งผู้ใช้*ครอบครองอินเทอร์เฟซนั้นอยู่ ส่วนตัวไหน
และเป็นตัวเดียวกันทั้งสองอินเทอร์เฟซหรือไม่ ยังไม่มีหลักฐาน การที่แอปนั้นรันอยู่พร้อมกัน
เป็นเพียงหลักฐานแวดล้อม

ที่ลองแล้วและได้แค่นี้ ทั้งหมดไม่ต้องยกสิทธิ์:

- `ls /proc/<pid>/fd` ของโปรเซสอื่น → **Permission denied** (adb shell เป็น uid 2000)
- `lsof | grep bus/usb` → ไม่มีผลลัพธ์ เพราะเห็นได้เฉพาะโปรเซสของตัวเอง
- `dumpsys usb` → บล็อก `permissions_manager.user_permissions` ของ user 0 **ว่างเปล่า**
  ไม่มีแพ็กเกจใดถือสิทธิ์อุปกรณ์แบบบันทึกถาวร (ที่มีบันทึกไว้มีเพียง USB drive ยี่ห้อหนึ่ง
  ผูกกับ ES File Explorer ซึ่งไม่เกี่ยวกับตัวแปลงอนุกรม) — สิทธิ์ที่ให้แบบไม่ถาวร
  หรือที่ได้มาจาก intent-filter ตอนเสียบอุปกรณ์ จะไม่ปรากฏตรงนี้

**การระบุตัวเจ้าของต้องใช้สิทธิ์ root** (`ls -l /proc/*/fd` ทั้งระบบ) ซึ่งเครื่องนี้ทำได้
เพราะเป็น userdebug และมี `su` — แต่เป็นการยกสิทธิ์บนเครื่องของเจ้าของ จึงไม่ทำเอง
จนกว่าจะได้รับคำสั่ง และคำอธิบายเหตุการณ์วันที่ 10 ยังต้องถือว่า**ยังไม่ยืนยัน**จนกว่าจะมีอันนี้

## และการยึดพอร์ตไม่ได้ถูกข้ามด้วยการเขียน usbfs เองหรือทำ APK ใหม่

`claimInterface()` เป็นการขอใช้**แบบเฉพาะราย** สิทธิ์ของไฟล์อุปกรณ์ที่เป็น `crw-rw-rw-`
บอกแค่ว่า*เปิดไฟล์ได้* ไม่ได้แปลว่า*อ้างสิทธิ์อินเทอร์เฟซได้* ตราบใดที่ยังมีผู้ถืออยู่
ทางที่ 1 กับ 4 ในรายการข้างบนจึงไม่ได้แก้ปัญหาการครอบครอง มันแค่ย้ายว่าใครเป็นคนขอ
— ผู้ถือเดิมต้องปล่อยก่อนเสมอ ไม่ว่าจะด้วยวิธีใด

ผลคือ**ทางที่ 3 ขึ้นเป็นลำดับแรก** และทางที่ 4 เป็นทางสำรองของ APK Emma ที่จะใช้ได้
ก็ต่อเมื่อรู้วิธีจัดการเจ้าของพอร์ตและโปรโตคอลจริงแล้ว

## ปิดเรื่องเจ้าของพอร์ต: วัดได้แล้วว่าเป็นแอปเดียว ถือทั้งสองตัว

เจ้าของโปรเจกต์รัน `su 0 sh -c 'ls -l /proc/*/fd/* | grep bus/usb'` ให้ (ผู้ช่วยยกสิทธิ์เองไม่ได้)
ผลคือมี**โปรเซสเดียว** ที่เปิด usbfs node ไว้:

```
/proc/3465/fd/308 -> /dev/bus/usb/009/006
/proc/3465/fd/309 -> /dev/bus/usb/009/004
/proc/3465/fd/373 -> /dev/bus/usb/009/006
/proc/3465/fd/384 -> /dev/bus/usb/009/004
```

`ps` ระบุ pid 3465 = `com.aobo.robot.ai3` (u0_a118) และ `busnum`/`devnum` จาก sysfs
จับคู่เลขอุปกรณ์ได้ตรงตัว:

| node | อุปกรณ์ |
|---|---|
| `/dev/bus/usb/009/004` | CP2102 (10c4:ea60) |
| `/dev/bus/usb/009/006` | CH340 (1a86:7523) |

**สรุปที่ยืนยันแล้ว**: แอป Aobo ถือตัวแปลงอนุกรมทั้งสองตัว อย่างละสอง fd ไม่ใช่เดมอน
ของผู้ผลิตเครื่อง (`gpioservice`, `lcdparamservice`, `com.wits.witsservices` ที่เคยเป็น
ผู้ต้องสงสัยจาก `ps`) และไม่ใช่คนละโปรแกรมกันคนละตัว — ข้อที่เคยเขียนไว้ว่ายังไม่ยืนยัน
ตอนนี้ยืนยันแล้วด้วยการวัด ไม่ใช่ด้วยการอนุมานจากการที่แอปรันอยู่พร้อมกัน

เหตุการณ์วันที่ 10 (ttyUSB10/11 ขึ้นตอนบูตแล้วหลุดพร้อมกันที่หกสิบวินาที) ยังเป็น
**การอนุมาน** อยู่ เพราะไม่ได้วัด ณ ตอนนั้น แต่เป็นการอนุมานที่หนัก เพราะกลไกและตัวผู้กระทำ
ถูกวัดแล้วในวันนี้ และเวลาหกสิบวินาทีตรงกับจังหวะที่แอปสตาร์ตเสร็จ

### ผลต่อการเลือกทาง

ทางที่ 3 ถูกยืนยันว่าเป็นทางที่ตรงที่สุด **เพราะผู้ถือพอร์ตคือแอปที่มี service ให้เรียก**
ไม่ใช่เดมอนของคนทำเครื่องที่เราไม่มีทางคุยด้วย ถ้าผลออกมาเป็น `gpioservice` แผนทั้งหมด
จะต้องเปลี่ยนไปคุยกับผู้ผลิตเครื่องแทนผู้ผลิตหุ่น ซึ่งเป็นคนละบริษัท

ทางที่ 2 (หยุดแอปแล้วใช้ ttyUSB) **ทำได้จริงในเชิงเทคนิค** — หยุดแอปแล้ว fd ทั้งสี่ถูกปิด
อินเทอร์เฟซถูกปล่อย แต่ยังต้องผูกไดรเวอร์ kernel กลับเองและยังติดสิทธิ์ของ device node
ที่ไม่มีกฎ ueventd รองรับ ทั้งสองอย่างต้อง root **และมันคือการหยุดแอปหลักของหุ่น**
จึงเป็นการตัดสินใจของเจ้าของ ไม่ใช่ของเครื่องมือ

## ทดลองจริง: หยุดแอป → ผูกไดรเวอร์ → ได้ `/dev/ttyUSB10` → แอปกลับมา → พอร์ตหายอีก

เจ้าของรันลำดับนี้ (คำสั่ง root ทั้งหมดรันโดยเจ้าของ ผู้ช่วยวัดผลอย่างเดียว):

| ขั้น | ผลที่วัดได้ |
|---|---|
| `am force-stop com.aobo.robot.ai3` | แอปหยุดจริง ไม่รีสตาร์ตเอง; `9-1.2:1.0` และ `9-1.4:1.0` กลายเป็น `driver=[]` โดย `class=ff` ยังอยู่ = อินเทอร์เฟซถูกปล่อยแล้ว |
| ไม่ทำอะไรต่อ | `/dev/ttyUSB*` ยังไม่มี — **ไดรเวอร์ kernel ไม่ผูกกลับเอง** หลังถูก usbfs แย่งไปครั้งหนึ่ง |
| `echo 9-1.2:1.0 > /sys/bus/usb/drivers/cp210x/bind` | สำเร็จ ได้ **`crw-rw-rw- 1 system system 188,10 /dev/ttyUSB10`** |
| `echo 9-1.4:1.0 > .../ch341-uart/bind` | ล้มเหลว — ชื่อไดรเวอร์บนบัส usb คือ **`ch341`** ส่วน `ch341-uart` เป็นชื่อบนบัส usb-serial |
| `am start -n ...SplashActivity` | แอปกลับมา (pid ใหม่) **ยึดทั้งสองอินเทอร์เฟซคืนเป็น `usbfs` ทันที และ `/dev/ttyUSB10` หายไป** |

ขั้นสุดท้ายคือสิ่งที่ขาดอยู่: **กลไกที่เคยอนุมานเรื่องเหตุการณ์วันที่ 10 ถูกสังเกตตรงๆ แล้ว**
ไดรเวอร์ kernel ผูกอยู่ → แอปสตาร์ต → แอป claim → kernel ปล่อย → node หายไป
ไม่ต้องอนุมานอีกต่อไปว่ากลไกนี้เกิดกับเครื่องนี้ได้จริงไหม เห็นมันเกิดแล้ว

### แก้ข้อสรุปที่ผิดสองข้อ และสาเหตุที่ทำให้ผิด

**1. ที่เขียนว่า "ไม่มีกฎ ueventd สำหรับ ttyUSB เลย node จึงเป็นของ root" — ผิด** กฎมีอยู่:

```
/dev/ttyUSB0 .. /dev/ttyUSB9   0660  radio   radio
/dev/ttyUSB1*                  0666  system  system
```

`ttyUSB0`–`9` จองไว้ให้โมเด็มเซลลูลาร์ ส่วน `ttyUSB1*` ครอบ `ttyUSB10`–`19` ที่ **0666**
ซึ่งตรงกับสิทธิ์ที่วัดได้ของ node จริง และน่าสนใจในตัวมันเอง: คนทำเครื่อง**ตั้งใจ**
เปิดช่วง ttyUSB10 ขึ้นไปให้เขียนได้โดยไม่ต้อง root

สาเหตุที่อ่านผิด: คำสั่งตรวจใช้ `grep 'ttyUSB\|ttyACM'` ซึ่ง **toybox grep ไม่รองรับ
`\|` แบบ BRE** จึงตีเป็นข้อความตรงตัวและไม่แมตช์อะไรเลย — ผลลัพธ์ว่างของการวัดที่พัง
หน้าตาเหมือนผลลัพธ์ว่างที่เป็นความจริง เป็นรูปเดียวกับ `nc -z` เมื่อ 9 ก.ย. เป๊ะ
และรอบนั้นรอดมาได้เพราะมีตัวควบคุมด้านบวก รอบนี้ไม่มี

**2. ที่ตีความว่า `centre(1)` ล้มเพราะสิทธิ์ของ node — ผิด** ข้อความจริงคือ
`can't create /dev/ttyUSB10` ซึ่งคือการพยายาม*สร้างไฟล์ใหม่*ในไดเรกทอรี `/dev`
เพราะ node ยังไม่มีอยู่ ไม่ใช่การถูกปฏิเสธที่ตัว node ตอนนี้ node มีจริงและเป็น 0666
**หน้า `/arm` เขียนได้โดยไม่ต้อง root** ถ้าพอร์ตว่าง

### สิ่งที่ยังไม่รู้ และยังไม่ทำ

- **ตัวไหนคือแขน** CP2102 หรือ CH340 ยังไม่ทราบ ยังไม่ได้เปิดพอร์ตฟัง
- **จุดตัดไฟเลี้ยงเซอร์โว** ยังไม่มีใครหาเจอ — ยังไม่ส่งไบต์ใดไปบอร์ดทั้งสิ้น
- การเปิดพอร์ตจะยก DTR/RTS ซึ่งบนบอร์ดบางรุ่นทำให้ไมโครคอนโทรลเลอร์รีเซ็ต
  แม้จะเปิดเพื่อ*ฟัง*อย่างเดียวก็ตาม

### ลำดับที่ใช้ได้จริงเมื่อจะทดสอบ

1. `am force-stop com.aobo.robot.ai3` — จอหุ่นจะกลับไปเป็น launcher ปกติ ไม่ใช่จอดำ
   เพราะแอปนี้ไม่ใช่ home
2. root: `echo 9-1.2:1.0 > /sys/bus/usb/drivers/cp210x/bind`
   (และ `echo 9-1.4:1.0 > /sys/bus/usb/drivers/ch341/bind` สำหรับอีกตัว)
3. ตั้ง `ROBOT_ARM_PORT=/dev/ttyUSB10` กับ `ROBOT_ARM_ENABLED=true` แล้วรีสตาร์ตเซิร์ฟเวอร์
4. ทดสอบ
5. `am start -n com.aobo.robot.ai3/com.aobo.aibot.ui.activity.SplashActivity` เพื่อคืนสภาพ

**สองอย่างนี้อยู่ร่วมกันไม่ได้** ถ้าแอปผู้ขายรัน หุ่นทำงานปกติแต่เราแตะพอร์ตไม่ได้
ถ้าเราถือพอร์ต แอปหลักของหุ่นต้องหยุด — ข้อนี้เป็นข้อจำกัดถาวรจนกว่าจะไปทางที่ 3

## ไฟเลี้ยงเซอร์โวสั่งได้ด้วยซอฟต์แวร์ — ผ่านรีเลย์บนบอร์ดล่าง STM32 ทาง CP2102 (11 ก.ย. บ่าย)

ค้นหาชื่อช่อง→ข้อต่อในโค้ดแล้ว**ไม่มี** แต่การค้นไปเจอกลไกที่สำคัญกว่า: แอปมีสองโหมดคุมไฟเซอร์โว
(`armSetting`/`armcontrolmethodtype`: 0 = **Relay**, 1 = Servo Board; ค่าที่สำรองจากหุ่น**ไม่มีคีย์นี้**
จึงใช้ default = 0 = Relay) และในโหมดรีเลย์ การจ่าย/ตัดไฟทำด้วยแพ็กเก็ต:

```
SerialdataService.setRelayPower(on)
  → BoardBuildDataUtil.buildRelayControlPacket(on)
  → sendCmdtowhichUart(bytes, 60000)   → sendCmd → broadcast send.usbserial.cmd
```

**เลข route ในโค้ดคือ USB PID ตรงตัว**: 29987 = 0x7523 = CH340 (หัว/แขน), **60000 = 0xEA60 = CP2102**
(`firstUart主板串口` = บอร์ดล่าง STM32 ที่คู่มือหน้า 6 ระบุว่ามี relay/door-lock outputs), 8963 = 0x2303 = PL2303
CP2102 เปิดที่ 115200 8N1 เช่นกัน

แพ็กเก็ตรีเลย์ 10 ไบต์ ถอดจาก `buildRelayControlPacket` + `<clinit>` + `checkCode`:

| ไบต์ | ค่า | ที่มา |
|---|---|---|
| 0 | `A5` | SYNC_HEAD |
| 1 | `01` | USER_ID |
| 2 | `2A` | CUSTOM_DATA_TYPE |
| 3 | `02` | คงที่ |
| 4–6 | `00 00 00` | คงที่ |
| 7 | `08` | คงที่ |
| 8 | **`00` = จ่ายไฟ, `01` = ตัดไฟ** | ขั้วกลับด้านตามโค้ด (true → 0) |
| 9 | checksum | two's complement ของผลรวมไบต์ 0–8 |

จ่ายไฟ = `A5 01 2A 02 00 00 00 08 00 26` · ตัดไฟ = `A5 01 2A 02 00 00 00 08 01 25`

> **แก้ไขหลังตรวจ branch และทดสอบจริง:** CP2102 ใช้ `SerialToothManager` ไม่ใช่ PL232 รับสถานะได้โดยไม่ส่ง handshake และยืนยันปุ่มแดง IO7 แล้ว ทดสอบรีเลย์ช่วงสั้นมีเพียงผลเขียนสำเร็จ ยังไม่วัดแรงดัน ดู [รายงาน CP2102/รีเลย์](robot-cp210-estop-relay-2026-09-11.md) ข้อความถัดไปเป็นข้อสันนิษฐานเดิมที่ไม่ใช้กับ CP2102

**บันทึกข้อสันนิษฐานเดิม (แก้ไขแล้ว)**: `SerialToothManagerPL232` มี handshake (`握手包处理`) ตอนเปิดพอร์ต
และ heartbeat (`心跳`) ต่อเนื่อง บอร์ดล่างเป็นโปรโตคอลที่มีสถานะ แพ็กเก็ตเดี่ยวอาจถูกเมิน และบอร์ดเดียวกัน
คุมมอเตอร์/อัลตราโซนิก/สัมผัส การคุยกับมันคืองานอีกชิ้นหนึ่ง ไม่ใช่ `printf` บรรทัดเดียว

### สมมติฐานที่อธิบาย "หัวขยับ แขนเงียบ" ได้ครบ

โค้ดแอปตัดไฟเซอร์โวเองในหลายกรณี: `红外触发(检测到障碍物) → 舵机断电` (อินฟราเรดเจอสิ่งกีดขวาง → ตัดไฟ),
`触摸触发(检测到手握) → 舵机断电` (สัมผัสที่แขน → ตัดไฟ), และคืนไฟหลังหน่วง 3–5 วิ
หุ่นจอดในที่แคบ (ลิดาร์วัดได้ 0.43–0.48 ม. สามด้านเมื่อ 10 ก.ย.) → IR อาจค้างสถานะ "มีสิ่งกีดขวาง"
