# โครงสร้างโปรเจกต์และแหล่งข้อมูล

## ข้อสรุปจากโครงสร้างปัจจุบัน

โปรเจกต์นี้มีผลิตภัณฑ์สามส่วนอยู่ร่วมกัน:

1. **บริการเสียงและเครื่องมือห้องขาย** — Python ใน `app/`, หน้าเว็บใน `client/`, เริ่มจาก `run_server.py`
2. **การเชื่อมต่อและทดลองหุ่น** — โมดูล `app/robot_*.py`, หน้าทดสอบ `client/robot-*.html`, รายงานใน `docs/robot-*.md`
3. **แอปที่รันบน Android ของหุ่น** — `apps/emma-robot-android/`

การอยู่ใน repository เดียวกันยังเหมาะสม เพราะทั้งสามส่วนใช้กติกาการสนทนา ข้อมูลโครงการ และความรู้ฮาร์ดแวร์ชุดเดียวกัน แต่ต้องแยกขอบเขตให้ชัด แอป Android สร้าง APK ของตัวเอง ส่วนบริการ Python และหน้าเว็บยังสร้างและรันจาก root

## แผนที่โฟลเดอร์

| ตำแหน่ง | หน้าที่ | สิ่งที่ไม่ควรใส่ |
| --- | --- | --- |
| `app/` | runtime Python, provider, session, tools และ adapter หุ่น | ไฟล์ข้อมูลจริงหรือไฟล์ทดลองขนาดใหญ่ |
| `client/` | UI เว็บและทรัพยากรที่ browser ใช้ | business truth ที่แก้ใน HTML โดยตรง |
| `apps/` | แอปที่ build/deploy แยกจากบริการหลัก | cache, APK build output ที่ commit เข้า git |
| `data/` | ข้อมูล runtime, manifest และข้อมูลที่ทีมดูแล | source code และรายงานการทดลอง |
| `docs/` | คู่มือ สถาปัตยกรรม ผลวิเคราะห์ และหลักฐานที่อ่านโดยคน | secret และข้อมูลส่วนตัวของผู้ใช้ |
| `scripts/` | งานนำเข้า ตรวจ วัด และสร้าง artifact แบบเรียกเป็นครั้ง | logic ที่ runtime ต้องใช้ทุกคำขอ |
| `tests/` | invariant และ regression tests | ข้อมูลจริงของลูกค้าหรืออุปกรณ์ |
| `tools/` | เครื่องมือชั่วคราว/เฉพาะงาน เช่น Xbox Direct | แอป production ตัวหลัก |
| `.tmp/`, `tmp/` | SDK, extraction และงานชั่วคราว | ไฟล์ที่ต้องเก็บระยะยาว |

## ปัญหาหลักของข้อมูลเดิม

- ความจริงของโครงการ คำบรรยายการตลาด ข้อมูลยูนิตสด เอกสารส่วนตัว และข้อมูลตัวอย่างอยู่ใต้ `data/` เหมือนกัน แต่ความน่าเชื่อถือไม่เท่ากัน
- กติกาว่าแหล่งใดใช้ตอบอะไรได้กระจายอยู่ใน comment ของ `app/config.py`, `app/prompts.py` และแต่ละ tool
- เอกสารหุ่นมีทั้งคู่มือ ข้อสรุปจาก bytecode และผลทดสอบทางกายภาพ ถ้าไม่แยกชั้นหลักฐาน อาจนำสเปกในคู่มือไปพูดเหมือนวัดกับเครื่องจริงแล้ว
- ไฟล์ runtime ส่วนตัวถูก ignore ถูกต้องแล้ว แต่คนเปิดโฟลเดอร์อาจยังไม่รู้ว่าไฟล์เหล่านี้ห้ามนำไปทำเป็นข้อมูลกลาง

## โครงสร้างความจริงที่ใช้ต่อจากนี้

ทะเบียน [`data/registry/source_registry.json`](../data/registry/source_registry.json) เป็นดัชนีกลาง ไม่ทำสำเนาเนื้อหาจากทุกไฟล์ แต่บอกบทบาทและกติกาของแต่ละแหล่ง

ลำดับการตัดสินแบ่งตามคำถาม:

| เรื่องที่ถาม | แหล่งหลัก | แหล่งช่วย | เมื่อไม่มีข้อมูล |
| --- | --- | --- | --- |
| ข้อมูลโครงการและคำกล่าวเชิงพาณิชย์ | `data/projects/embassy_world/facts/condo_facts.json` | ไม่มีแหล่งช่วยสำหรับแต่งตัวเลข | บอกว่าไม่มีข้อมูลที่ยืนยัน |
| ห้องว่างและรายละเอียดยูนิต | live inventory ที่ scope ถูกโครงการ หรือ `data/units.json` | `units.sample.json` ใช้ได้เฉพาะเดโมที่ติดป้าย | ให้ติดต่อฝ่ายขาย |
| ค้นภาพ/อธิบายแนวคิด | `data/projects/embassy_world/presentations/slides/index.json` | `data/projects/embassy_world/routing/project_knowledge.json` ช่วย routing | ไม่เปลี่ยนจอและไม่เดา |
| ข้อมูลจากเอกสารเจ้าของ | `data/personal-docs/` | ไม่มี | บอกว่าไม่พบในเอกสาร |
| สถานะหุ่นตอนนี้ | telemetry ที่อ่านสด | รายงานเก่าใช้ช่วยวินิจฉัย | แสดงว่าอ่านค่าไม่ได้ |
| ความสามารถและคำสั่งหุ่น | หลักฐานใน `docs/robot-interface-reference/` และผลทดสอบจริง | คู่มือผู้ขายบอกขอบเขตที่เป็นไปได้ | คงสถานะว่ายังไม่ยืนยัน |

## สิ่งที่จัดระเบียบแล้ว

- เพิ่มทะเบียนแหล่งข้อมูลแบบ machine-readable
- เพิ่มตัวตรวจ path, JSON, สถานะอนุมัติ, ไฟล์ใน document catalogue, ป้าย sample และจุดนำทางที่ยังไม่ยืนยัน
- เพิ่ม `data/README.md` เป็นกติกาหน้าโฟลเดอร์
- ย้ายข้อมูลที่ระบุได้ว่าเป็น Embassy World ไป `data/projects/embassy_world/` และแยกสไลด์ `other-project` 15 รายการไป `data/review/other_projects/` โดยคงเนื้อหาเดิม; ภาพเก่าที่ไม่มีรายการในดัชนีอยู่ `data/review/unindexed_slides/`
- เพิ่ม `source_id`/`project_id` ให้แหล่งข้อมูลที่ย้าย และให้ loader กับเครื่องมือปฏิเสธข้อมูลผิดโครงการ; `PROJECT_ID=embassy_world` เป็นขอบเขตคงที่ของ server นี้ ไม่เปิดให้โมเดลเลือกโครงการ
- ย้ายถ้อยคำเฉพาะโครงการจาก `SALES_HOST_BLOCK` ไป `data/projects/embassy_world/presentations/sales_context.json` โดยไม่เปลี่ยนสถานะอนุมัติหรือถ้อยคำที่ส่งให้โมเดล

## ลำดับงานถัดไปที่ปลอดภัย

1. เติม `approved_by` และ `effective_from` ใน `data/projects/embassy_world/facts/condo_facts.json` หลังเจ้าของข้อมูลตรวจเนื้อหา
2. ยืนยันว่าระบบ inventory สดมีข้อมูลชุดใดเป็นข้อมูลจริง โดยคง `UNITS_SHOW_PRICE=false` จนกว่าจะอนุมัติการเปิดราคา
3. ใส่ PDF จริงตาม `data/documents/catalogue.json` หรือลบรายการที่ยังไม่พร้อมออกจาก catalogue
4. วัดและตั้ง `verified=true` ให้จุดใน `data/showroom/layout.json` ทีละจุดก่อนใช้เดินจริง
5. เมื่อ working tree สงบ ค่อยย้ายรายงานหุ่นที่ลงวันที่ไป `docs/robot/research/` และคงไฟล์สรุป canonical ไว้ด้านบน โดยแก้ link ทั้งหมดในชุดเดียว
