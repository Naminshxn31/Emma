# หุ่น Astronaut ขยับอะไรได้บ้าง

ตรวจข้อมูลวันที่ 11 กันยายน 2026 จากคู่มือ Astronaut (Humanoid Arm Motion Version) ที่ผู้ใช้ให้มา, SDK V2, APK Aobo และข้อมูลแชสซีที่สำรองวันที่ 10 กันยายน รวมถึงเว็บผู้ผลิต การตรวจรอบนี้ไม่สั่งหุ่นเคลื่อนไหว

## ข้อค้นพบหลัก

คู่มือระบุการเคลื่อนไหวของฐานล้อ หัว/คอ แขน ท่อนแขน มือและนิ้วทั้งสิบ และการเล่นชุดท่าร่วมกับเสียงพูด แต่หลักฐานบนหุ่นจริงขณะนี้ยืนยันการเคลื่อนหรือหมุนของฐานระหว่างทดสอบกลับแท่นเท่านั้น ยังไม่มีผลทดสอบข้อต่อส่วนบนรายตัว

รุ่นในคู่มือเป็นรุ่นแขนเคลื่อนไหว ไม่ใช่ข้อยืนยันว่าหุ่นทุกตัวที่หน้าตาเหมือนกันมีอุปกรณ์ครบตามตาราง: คู่มือระบุ Android 10 / QCM686 / RAM 4–8 GB ขณะที่เครื่องที่ตรวจเป็น Android 15 / RK3588 / RAM ประมาณ 16 GB แสดงว่ารายละเอียดรุ่นย่อยต่างกันจริง ต้องตรวจกลไกและการต่อบอร์ดของตัวนี้เพิ่มเติม

ระดับหลักฐานในรายงาน: **คู่มือระบุ** = ความสามารถที่เอกสารอธิบาย, **ระบบประกาศ** = มีชื่อฟังก์ชัน/เมนูแต่ยังไม่พิสูจน์การทำงาน, **ทดสอบแล้ว** = มีผลจากเครื่องจริงเฉพาะการทดสอบที่บันทึกไว้

## 1. การเคลื่อนไหวเชิงกลทั้งหมดที่คู่มือระบุ

|---|---|---|---|
| ฐานล้อ | เคลื่อนที่บนพื้น เดินหน้า/ถอยหลังผ่านระบบควบคุมทิศทาง | ช่วงความเร็วทั่วไป 0.3–1.0 m/s | เคยเคลื่อนหรือหมุนจริง; ยังไม่ทดสอบแยกทุกทิศ; ค่า max speed ที่สำรองจากบอร์ดคือ 0.4 m/s |
| ฐานล้อ | เลี้ยว/หมุนตัว เปลี่ยนทิศทาง | คู่มือระบุหมุนเป็นวง ไม่ให้ขอบเขตมุมจำกัด | เคยเคลื่อนหรือหมุนระหว่างกลับแท่น; มี Rotate/RotateTo ในระบบ |

| หัว/คอ | หันซ้าย–ขวา | 180° | คู่มือระบุ; ยังไม่ทดลองจริง |

| แขนซ้ายและขวา | แกว่งไปด้านหน้า–ด้านหลัง | 180° | คู่มือระบุ; ยังไม่ทดลองจริง |

| ท่อนแขนซ้ายและขวา | หมุนรอบแกน | 290° | คู่มือระบุ; ไม่ยืนยันว่าเป็นข้อมือแยกหรือการหมุนของท่อนแขน |
| มือซ้าย นิ้วโป้ง/ชี้/กลาง/นาง/ก้อย | ขยับนิ้วทั้งห้า เลียนแบบมือคน | คู่มือกล่าวถึงนิ้ว 180° ด้วยถ้อยคำกำกวม | ยังไม่มี channel map และไม่ยืนยันการควบคุมแต่ละข้อของนิ้ว |
| มือขวา นิ้วโป้ง/ชี้/กลาง/นาง/ก้อย | ขยับนิ้วทั้งห้า เลียนแบบมือคน | เช่นเดียวกับมือซ้าย | ยังไม่ทดลองกำ/แบหรือจับวัตถุ |

มุมในตารางเป็นตัวเลขที่เอกสารระบุ ไม่ใช่ค่าที่วัดหรือปรับเทียบแล้ว เอกสารไม่ชัดว่ามุมบางรายการเป็นช่วงรวม หรือข้างละเท่าใด จึงไม่แปลง 180° เป็น ±180° และไม่ใช้ปลายช่วงเหล่านี้เป็นคำสั่งทดสอบทันที ข้อความนิ้วหมุน 180° ไม่เพียงพอจะสรุปว่านิ้วหมุนรอบตัวเองได้

ไม่มีตารางแยกแกน shoulder/elbow/wrist/finger พร้อมเลขช่องครบทุกข้อต่อ จึงยังแจกแจงเป็นรายชื่อเซอร์โว 22 ตัวที่เชื่อถือได้ไม่ได้

## 2. ท่าหรือพฤติกรรมที่เกิดจากการขยับหลายส่วน

| ท่า/งาน | หลักฐาน | สิ่งที่ยังขาด |
|---|---|---|
| จับมือทักทาย | คู่มือหน้า 4 ข้อ 18, หน้า 6 และหน้า 8 ระบุ | เลขกลุ่มท่า การเชื่อมบอร์ด เงื่อนไขเริ่ม/หยุด และแรงจับที่ยืนยันกับเครื่องจริง |
| จับแก้วและเอียงเทน้ำ | คู่มือหน้า 6 ระบุว่าต้องเขียนโปรแกรมเพิ่ม | โปรแกรมท่า น้ำหนักบรรทุก แรงจับ ระยะเอื้อม และการตรวจวัตถุ; ยังไม่ถือว่าพร้อมใช้ |
| เล่นชุดท่าต่อเนื่อง หรือเล่นเป็นช่วง | คู่มือหน้า 4 ข้อ 21 และ SDK action group | รายการกลุ่มท่าที่บันทึกในบอร์ดและเนื้อหาแต่ละท่า |
| ขยับแขนประกอบคำพูด/การบรรยาย | คู่มือหน้า 7; แอปมี voice action group | ท่าที่ปลอดภัยและการจับเวลาให้ตรงเสียงจริง |
| ขยับแขนขณะพาเดินนำทาง | คู่มือหน้า 7; แอปมีค่ากลุ่ม navigation/walking | ยังไม่ทดลองพร้อมกัน; ต้องยืนยันระยะกวาดแขนกับสิ่งรอบตัว |
| เคลื่อนเข้าจุดต้อนรับเมื่อพบคน | คู่มือหน้า 4 ข้อ 15 | การตั้งจุดและระบบตรวจจับของแอป ไม่ใช่ความสามารถที่ทดสอบแล้ว |
| หมุนตัว/พูดตอบเมื่อสัมผัส | คู่มือหน้า 4 ข้อ 19 | คู่มือหน้า 8 กลับบอกเซ็นเซอร์อยู่ข้างหัว จึงยังไม่ยืนยันตำแหน่งเซ็นเซอร์จริง |
| โบกมือ ชี้ทาง พยักหน้า ส่ายหน้า หรือท่าแสดงประกอบเพลง | อนุมานว่าอาจสร้างจากแกนที่คู่มือระบุ; แอปมี arm movement with background music | ยังไม่พบ preset ที่ใช้ได้ทันที; ต้องออกแบบภายในระยะข้อต่อจริง |
| ไหว้/ปรบมือ | ยังไม่มีหลักฐานเฉพาะท่า | ไม่รับรองว่าช่วงเอื้อมและระยะระหว่างมือทำได้ โดยเฉพาะท่าที่มือชนหรือสัมผัสกัน |

ยังไม่พบค่าบรรทุกของแขน แรงบีบนิ้ว ความเร็วข้อต่อ ความแม่นยำ หรือเซ็นเซอร์แรงสำหรับหุ่นตัวนี้ จึงยังสรุปความสามารถด้านหยิบจับวัตถุจริงจากภาพมือหรือข้อความจับแก้วเพียงอย่างเดียวไม่ได้

## 3. การเคลื่อนฐานและงานนำทาง

คู่มือระบุนำทางไปตำแหน่ง พาเดินหลายจุด เดินตามเส้นทาง เลี่ยงสิ่งกีดขวาง กลับจุดเริ่มต้น ลาดตระเวนตามกำหนด และกลับชาร์จอัตโนมัติ โดยระบบลิฟต์/ประตูต้องมีอุปกรณ์และการเชื่อมต่อเพิ่มเติมตามคู่มือหน้า 3 และ 7

บอร์ดที่สำรองประกาศ action factories 21 ชื่อดังนี้ **รายชื่อบอกว่ามีตัวจัดการในซอฟต์แวร์ ไม่ใช่การทดสอบว่าหุ่นทำงานนั้นได้ครบ และยังไม่ใช่สเปก payload สำหรับสั่งงาน**:

| ชื่อท้ายของ `slamtec.agent.actions.*` | ความหมาย/ขอบเขตหลักฐาน |
|---|---|
| `MoveToAction` | นำทางไปเป้าหมาย; มีสัญญา API และโค้ดเชื่อมในโปรเจกต์ |
| `SeriesMoveToAction` | ชื่อสื่อถึงไปหลายเป้าหมาย; ยังไม่ทดลอง |
| `MoveByAction` | ชื่อสื่อถึงเคลื่อนตามคำสั่งทิศทาง/ระยะ; ยังไม่ยืนยัน REST payload |
| `RotateAction` | ชื่อสื่อถึงหมุน; ยังไม่ยืนยัน REST payload |
| `RotateToAction` | ชื่อสื่อถึงหมุนไปมุมเป้าหมาย; ยังไม่ทดลอง |
| `GoHomeAction` | สั่งกลับแท่นเคยทำให้เคลื่อน/หมุน แต่เข้าแท่นไม่สำเร็จและยกเลิกแล้ว |
| `ReturnToParkingAction` | ชื่อสื่อถึงกลับจุดจอด; ยังไม่ทดลอง |
| `FollowPathPointsAction` | ชื่อสื่อถึงตามชุดจุดเส้นทาง; ยังไม่ทดลอง |
| `FollowTargetAction` | ติดตามเป้าหมายตามชื่อ; ยังไม่ยืนยันว่าเป้าหมายคือคนหรือมีระบบตรวจจับรองรับ |
| `ModifyParamsMoveToAction` | งาน MoveTo ที่ปรับพารามิเตอร์ตามชื่อ; ยังไม่ทดลอง |
| `MoveToTagAction` | เคลื่อนไป tag ตามชื่อ; ยังไม่ยืนยันชนิด tag หรืออุปกรณ์ |
| `BackOffFromTagAction` | ถอยออกจาก tag ตามชื่อ; ยังไม่ทดลอง |
| `SweepAction` | ชื่องาน sweep; ไม่ใช่หลักฐานว่าติดตั้งแปรง/เครื่องดูดฝุ่นหรือทำความสะอาดได้ |
| `ManualRelocalizationAction` | กระบวนการระบุตำแหน่งใหม่; ต้องอ่านสัญญาก่อนใช้งาน |
| `RecoverLocalizationAction` | กระบวนการกู้การระบุตำแหน่ง; อาจเกี่ยวกับการเคลื่อนไหว ยังไม่ทดลอง |
| `HealthSupervisoryAction` | งานตรวจสุขภาพระบบ ไม่ใช่ท่าของร่างกาย |
| `MultiFloorBackHomeAction` | กลับแท่นข้ามชั้น; ต้องมีแผนที่/ระบบลิฟต์ที่ตั้งค่า |
| `MultiFloorMoveAction` | นำทางข้ามชั้น; ยังไม่มีผลทดสอบ |
| `TransferElevatorAction` | งานลิฟต์ตามชื่อ; ไม่ถือว่ามีอุปกรณ์ครบแล้ว |
| `EnterElevatorAction` | เข้าลิฟต์ตามชื่อ; ยังไม่ทดลอง |
| `LeaveElevatorAction` | ออกจากลิฟต์ตามชื่อ; ยังไม่ทดลอง |

ค่า snapshot ที่บันทึกได้คือ `base.max_moving_speed=0.400000` และ `base.max_angular_speed=1.000000` เป็นค่าตั้ง ไม่ใช่ผลวัดความเร็วจริง รอบนี้ไม่ได้ปรับค่า หุ่นใช้ฐานล้อ ไม่พบหลักฐานขาสำหรับก้าวเดินหรือขึ้นบันได

## 4. สีหน้าที่เห็นเหมือนเคลื่อนไหว แต่เป็นภาพบนจอ

คู่มือหน้า 3 และ 9 ระบุจอหน้าขนาด 7 นิ้วสำหรับสีหน้า ภาพและวิดีโอ ส่วนจอหน้าอก 18.5 นิ้วเป็นจอสัมผัส APK มีตัวแสดงภาพ/GIF/ภาพเคลื่อนไหว และสำเนาไฟล์สีหน้า 16 ไฟล์ (10 hash ที่แตกต่าง)

ส่วนนี้แยกจากมอเตอร์คอ: เปลี่ยนภาพตาไม่ได้แปลว่าหัวหัน และการหันหัวไม่ได้ยืนยันว่าเปลี่ยนภาพตาผ่าน API ได้ Android dump ที่สำรองพบจอจริงหนึ่งจอกับจอเสมือน AnyDesk ยังไม่ยืนยันช่องทางจอหัว

ไม่พบหลักฐานกลไกเปลือกตา ปาก หรือหูเคลื่อนไหว คู่มือกล่าวถึงไฟ LED บางตำแหน่ง ซึ่งไม่ใช่ข้อต่อ

## 5. สิ่งที่ยังสรุปว่าทำได้ไม่ได้

- เดินด้วยขา วิ่ง กระโดด ขึ้นบันได ย่อเข่า: ไม่มีหลักฐานกลไกขาในคู่มือรุ่นนี้ คำ `ROBOTJUMP` ใน voice configuration ไม่ใช่หลักฐานว่าหุ่นกระโดดจริง
- เคลื่อนด้านข้างตรง ๆ โดยไม่หันฐาน: ยังไม่ยืนยันชนิดล้อและความสามารถเคลื่อนด้านข้าง
- บิดเอว โค้งคำนับด้วยเอว ยกหรือลดความสูงลำตัว: ไม่มีแกนเอวหรือลำตัวยกขึ้นลงที่ระบุชัด
- ข้อมืออิสระครบสามแกนหรือควบคุมทุกปล้องนิ้วแยกกัน: คู่มือไม่แจกแจงระดับนี้
- หยิบวัตถุทั่วไปแบบอัตโนมัติ ยกของหนัก บีบจับคนด้วยแรงที่กำหนด: ยังไม่มีข้อมูลและผลทดสอบรองรับ
- ใช้ลิฟต์ เปิดประตู หรือทำความสะอาดได้ทันที: ชื่อ action และพอร์ตบอร์ดไม่ยืนยันอุปกรณ์เสริม

## 6. ความไม่ตรงกันของเอกสารและเงื่อนไขปิดงานสำรวจฮาร์ดแวร์

คู่มือหน้า 6 ระบุส่วนบน 22 joints และทั้งตัว 24 degrees of freedom แต่บอร์ดควบคุมระบุ 20 channels คำว่า joint, degree of freedom และช่องสัญญาณไม่จำเป็นต้องเท่ากัน และเอกสารไม่ได้บอกการแบ่งบอร์ด/การผูกช่อง จึงยังไม่ถือว่าเครื่องนี้มีมอเตอร์ส่วนบนอิสระ 22 ตัว หรือเดาว่าอีกสองแกนเป็นล้อโดยไม่มี wiring map

เพื่อยืนยันทุกส่วนของตัวจริง ยังต้องได้:

1. รุ่นบอร์ดและ wiring/channel map ว่าช่องใดต่อหัว ไหล่ ศอก ข้อมือ และนิ้ว
2. ค่า home/min/max ทิศกลับด้าน ความเร็ว และข้อจำกัดน้ำหนัก/แรงของแต่ละกลไก
3. รายชื่อ action groups พร้อมท่าจริง; กลุ่ม 11/21/17 ที่เห็นในแอปเป็นค่าตามสถานการณ์ ไม่ใช่ชื่อท่าที่พิสูจน์แล้ว
4. SDK library หรือโปรโตคอลที่ตรงเฟิร์มแวร์; PDF อธิบายเมธอดแต่ยังไม่มี implementation ที่เราเชื่อมได้
5. การทดสอบทีละแกนพร้อมบันทึกผลตอบรับและวิธีหยุดส่วนบน ก่อนรวมเป็นท่าที่สัมผัสคนหรือวัตถุ

## 7. บอร์ดข้อต่อส่วนบนเป็น Torobot — โปรโตคอลเปิด ไม่ต้องรอผู้ขาย (11 ก.ย. ต่อจากรายงาน)

ข้อความคู่มือหน้า 6 หัวข้อ *Upper body joint control panel* ระบุข้อ 9 ไว้ตรงตัวว่า
**"Controlled using Torobot programming software"** พร้อมสเปกที่ระบุตัวบอร์ดได้:
20 ช่อง, สัญญาณออก PWM ความละเอียด 0.5 μs, baud 9600–128000, USB หรือ TTL,
PCB 63 × 46 mm, รูยึด 55.5 × 38.5 mm, ไฟเลี้ยงเซอร์โวแยกจากไฟบอร์ด,
และแต่ละช่องมีวงจรป้องกันกระแสเกิน

Torobot เป็นบอร์ดควบคุมเซอร์โวเชิงพาณิชย์ที่ขายทั่วไปและ**มีคู่มือโปรโตคอลเปิดเผย**
สำเนาข้อความที่ดึงมาเก็บไว้ที่
`data/robot-inspection/motion-capabilities-20260911/torobot-usc-protocol-en.txt`
(ที่มา: `torobot.com/down/usc_en.pdf`) ชุดคำสั่งเป็นข้อความล้วนบนพอร์ตอนุกรม
จบด้วย `\r\n` และห้ามมีช่องว่าง:

| คำสั่ง | ความหมาย |
|---|---|
| `#1P1500T100\r\n` | สั่งช่อง 1 ไปตำแหน่ง 1500 (ช่วง 500–2500) ใช้เวลา 100 ms (ช่วง 100–9999 ยิ่งมากยิ่งช้า) |
| `#1P600#2P900#8P2500T100\r\n` | สั่งหลายช่องพร้อมกัน มี `T` ได้ค่าเดียวต่อคำสั่ง |
| `#1GC2\r\n` | เล่นกลุ่มท่าหมายเลข 1 จำนวน 2 รอบ |
| `#1G#3G#1GC2\r\n` | เล่นกลุ่มท่าเรียงตามลำดับ กลุ่มเดิมซ้ำได้ มี `C` ได้ค่าเดียว |

สิ่งที่ตามมาสามข้อ ทั้งหมด**ไม่ต้องขอผู้ขาย**:

1. **คุมทีละข้อต่อได้ตรงๆ โดยไม่ต้องรู้กลุ่มท่าเลย** `#nP…T…` คือคำสั่งรายช่อง
   การทำ channel map (ข้อ 1 ของหัวข้อ 6) จึงทำเองได้ด้วยการขยับทีละช่องช้าๆ
   แล้วจดว่าช่องไหนคือข้อต่อไหน
2. **ซอฟต์แวร์ของ Torobot มีปุ่ม `read` ที่อ่านหมายเลขกลุ่มท่าทั้งหมดที่มีอยู่ในบอร์ด**
   ตัดพื้นที่ค้นจาก "ไล่ 0–255 มั่วๆ" เหลือเฉพาะเลขที่มีจริง (บอร์ดตระกูลนี้เก็บได้ถึง
   ~230 กลุ่ม) การไล่เลขจึงเป็นการไล่ของที่รู้ว่ามี ไม่ใช่การยิงสุ่ม
3. **ไม่จำเป็นต้องใช้ซอฟต์แวร์ Windows ของ Torobot ในการสั่งงาน** เพราะเป็นข้อความ
   บนพอร์ตอนุกรม — เขียนลง `/dev/ttyUSB1` (115200 ตรงกับช่วง baud ที่บอร์ดรับ)
   จากเชลล์ของหุ่นเองก็ได้ ใช้ซอฟต์แวร์เฉพาะตอนอ่านรายการกลุ่มท่ากับตอนบันทึกท่าใหม่

### ข้อจำกัดที่ต้องเขียนไว้ ไม่ใช่ข้ามไป

- **คู่มือ Torobot ที่อ่านได้ไม่มีคำสั่ง "หยุด"** ชุดคำสั่งมีแค่สั่งไปตำแหน่ง กับสั่งเล่นกลุ่มท่า
  ตัวหยุดที่แน่นอนที่สุดตามสเปกคือ **ไฟเลี้ยงเซอร์โวที่แยกวงจรจากบอร์ด** ต้องหาให้เจอว่า
  ตัดตรงไหนก่อนทดสอบใดๆ ส่วน `stopArm()` / `stopArmAll()` ใน SDK ยังไม่รู้ว่าส่งอะไรลงสาย
- **เซอร์โว PWM ไม่มีการอ่านตำแหน่งกลับ** คำสั่งแรกที่ส่งเข้าช่องใดก็ตามคือการขยับจาก
  ตำแหน่งที่เราไม่รู้ ไปยังตำแหน่งที่เราระบุ จึงต้องใช้ `T` ค่าสูง (ช้าที่สุด) เสมอในการทดลอง
- คู่มือที่ดึงมาเป็นรุ่น USC 24/32 ช่อง ส่วนบอร์ดในหุ่นระบุ 20 ช่อง ตระกูลคำสั่งเดียวกัน
  แต่**ยังไม่ยืนยันกับบอร์ดตัวนี้** ยืนยันได้เมื่อมีคนเปิดดูบอร์ดจริง (เทียบขนาด PCB
  63 × 46 mm และระยะรูยึด 55.5 × 38.5 mm) หรือเมื่อคำสั่งแรกได้ผลตามที่คาด

### ลำดับที่ปลอดภัยที่สุดเมื่อหุ่นพร้อม

1. หาตำแหน่งตัดไฟเลี้ยงเซอร์โว และให้มีคนยืนถึงตลอดการทดสอบ
2. อ่านรายการกลุ่มท่าที่มีอยู่จริงในบอร์ด (`read`)
3. เล่นกลุ่มที่มีอยู่ทีละกลุ่ม `C=1` พร้อมถ่ายคลิป → ได้ตารางท่า
   ปลอดภัยกว่าเพราะกลุ่มเหล่านี้ผู้ผลิตบันทึกไว้เองภายในระยะกลไกจริง
4. ค่อยทำ channel map ด้วย `#nP…T` ค่าช้าสุด ทีละช่อง
5. **ห้ามให้เครื่องมือที่โมเดลเรียกได้แตะขั้นตอน 3–4** ทั้งหมดนี้เป็นงานหน้าโต๊ะ

### สองข้อที่คู่มือเคลียร์ให้ด้วย

- **ไมค์เป็นอาร์เรย์ 4 ตัว พร้อม echo cancellation และ sound source localization ในตัว**
  (คู่มือหน้า 6 หัวข้อ Microphone motherboard) ตรงกับที่วัดได้ว่าดองเกิลส่งมา 8 ช่อง
  ที่ 16 kHz — 4 ช่องดิบบวกช่องที่ผ่านการประมวลผล การหาว่าช่องไหนคือ AEC จึงเป็น
  การวัด ไม่ใช่การถามผู้ขาย
- **คู่มือระบุว่าจอสองจอเป็นสเปกมาตรฐาน** จอสีหน้า 7 นิ้วที่หัว และจอสัมผัส 18.5 นิ้วที่อก
  สอดคล้องกับสมมติฐาน `switch_doublescreen` และยืนยันว่าจอหัวมีอยู่จริงตามสเปก
  ไม่ใช่ออปชัน
