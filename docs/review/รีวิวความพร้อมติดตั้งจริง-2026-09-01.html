A. Executive Summary

สิ่งที่ระบบนี้เป็นจริงๆ: เอนจินผู้ช่วยเสียง speech-to-speech (Gemini Live) ที่โตมาจากห้องขายคอนโด Embassy World แล้วต่อยอดเป็นผู้ช่วยส่วนตัว "Emma" — มี wake word ในเครื่อง, VAD ในเครื่อง, จดจำใบหน้าในเครื่อง, คุม IR/สไลด์/เว็บ, และมีฝั่งเซิร์ฟเวอร์ของการต่อหุ่นยนต์ Aobo Astronaut ที่เขียนเสร็จพร้อมเทสต์ แต่ฝั่งแอปบนหุ่นยังไม่ได้เขียน และยังไม่เคยแตะฮาร์ดแวร์หุ่นจริง

ความพร้อมโดยรวม: Prototype ที่ใช้ในพื้นที่ควบคุมได้ (ระดับ 2–3) สำหรับส่วนเสียง และ ระดับ 1 สำหรับส่วนหุ่นยนต์และความปลอดภัยทางกายภาพ

จุดเด่นที่ยืนยันได้

  • วินัยด้านวิศวกรรมสูงผิดปกติสำหรับทีมเล็ก — เทสต์ 989 ตัว (นับจริงด้วย pytest --collect-only), ทุกกลไกมีคอมเมนต์บอกว่าบั๊กไหนทำให้เกิด, มี turn log + สคริปต์วิเคราะห์, และมีวัฒนธรรม "วัดก่อนเชื่อ" ที่เห็นได้จากตัวเลขในโค้ด
  • ตัดสินใจถูกในเรื่องที่คนมักพลาด: โมเดลไม่ได้ตัดสินว่าใครคือใคร (faces.py: เซิร์ฟเวอร์ให้ชื่อ หรือไม่ให้), ราคาไม่ออกจากเซิร์ฟเวอร์, mock ห้ามรายงานเป็น ok, tool เดินหุ่นคืนค่าทันทีไม่รอถึง, gallery เก็บเวกเตอร์ไม่เก็บรูป, โมเดลที่มี age/gender ถูกปิดไม่ให้โหลด
  • เสียงไม่ออกนอกเครื่องจนกว่าจะเรียกชื่อ (wake word + VAD ในเครื่อง) — ถูกทั้งเรื่องเงินและ privacy

ความเสี่ยงสำคัญที่สุด 5 ข้อ

  1. Blocker คำสั่ง "หยุด" ของหุ่นยนต์วิ่งผ่าน LLM บนคลาวด์ — stop_moving เป็น tool ที่โมเดลต้องเลือกเรียก ไม่มีเส้นทางหยุดในเครื่อง ไม่มี E-Stop ไม่มีการอ่านเซนเซอร์ ไม่มี command gateway
  2. Blocker ใครก็ตามที่มี token เป็น "หุ่นยนต์" ได้ — ข้อความ robot_ready บน /ws คือสิ่งเดียวที่ทำให้ client กลายเป็นหุ่น ไม่มี device identity แยก
  3. Blocker จดจำใบหน้าไม่มีบันทึกความยินยอม ไม่มีทางถอน และ prompt สั่งให้ซ่อนว่ามีกล้อง ("ห้ามพูดถึงกล้อง") — ขัดหลักความโปร่งใสของข้อมูลชีวมิติ ต้องผ่าน DPO ก่อนใช้กับคนนอกทีม
  4. Critical เสียงลูกค้าส่งไป Google free tier ที่ "ใช้ปรับปรุงผลิตภัณฑ์" โดยไม่มี privacy notice หน้าเครื่อง
  5. Critical ไม่มีโหมดออฟไลน์เลย — เน็ตหลุด = หุ่นเงียบ ไม่มีแม้ประโยค "ระบบขัดข้อง" ในเครื่อง และไม่มี tool เรียกพนักงาน (call_staff ไม่มีอยู่ในรายการ tool 40 ตัว)
ข้อสังเกตเรื่องกรอบคำถาม: brief ของการรีวิวพูดถึง "โรงแรม/ระบบสมาชิก/แจ้งงาน" แต่รีโปนี้คือห้องขายคอนโด + ผู้ช่วยส่วนตัวของเจ้าของ ไม่มีการเชื่อมต่อระบบโรงแรม/PMS/สมาชิกใดๆ (มีเฉพาะ Supabase ผังขายและ Broadlink IR) ผมประเมินตามที่โค้ดเป็นจริง และระบุว่าอะไรยังไม่มีเมื่อ brief ถามถึง

Use case ที่มีความเสี่ยง

  • พาลูกค้าเดินไปจุดต่างๆ (go_to_place) — เคลื่อนที่ในพื้นที่มีคน
  • ทักชื่อคนจากกล้อง (greeter.py) — ประกาศตัวตนออกเสียงในที่สาธารณะ
  • เปิดโปรแกรม/เว็บบนเครื่อง (computer group เปิดอยู่ใน .env เจ้าของ) — ฟังผิดแล้วลงมือ
  • พิมพ์เอกสาร, ทวนเบอร์โทรออกเสียง — ข้อมูลส่วนบุคคลออกสู่กระดาษ/อากาศ/log

ข้อมูลที่ยังขาด (คำถามที่ต้องตอบก่อน pilot)

  1. สเปกหุ่น Astronaut ที่จะส่งมอบจริง: เฟิร์มแวร์, AAR เวอร์ชัน, ไมค์กี่ช่อง, AEC ในฮาร์ดแวร์ทำงานเมื่อดึง PCM ดิบไหม, ปิดระบบสนทนาจีน+อังกฤษของเดิมได้ไหม (docs/robot-integration.md ตั้งคำถามไว้ถูกแล้วแต่ยังไม่มีคำตอบ)
  2. หุ่นมี E-Stop กายภาพ / bumper / อัลตราโซนิก / LiDAR ไหม และ cancelNavigation() ใช้เวลากี่ ms
  3. ฐานกฎหมายที่จะใช้กับข้อมูลชีวมิติของพนักงาน (ลงทะเบียนแล้ว 4 คน + staff.csv) และของลูกค้าที่เดินผ่าน — ต้องถาม DPO
  4. บัญชี Gemini จะเปิด billing ก่อน pilot หรือไม่ (เปลี่ยนเงื่อนไขการใช้ข้อมูล)
  5. ใครเป็นเจ้าของเครื่องห้องขาย ใครมีสิทธิ์อ่าน data/logs และ data/faces

B. System Architecture

ปัจจุบัน (จากโค้ด)

ไมค์ (เบราว์เซอร์: AEC/NS/AGC ซอฟต์แวร์ + compressor)
  │ PCM16 16k ─▶ /ws/wake ─▶ sherpa-onnx KWS "EMMA/IMMA/A MA"  (ในเครื่อง)
  │                              │ ได้ยินชื่อ → เบราว์เซอร์เปิด /ws
  │ PCM16 16k ─▶ /ws ─▶ VoiceSession ─▶ VadGate (Silero, ในเครื่อง)
  │                                        │ เฉพาะช่วงพูด + activity_start/end
  │                                        ▼
  │                              Gemini Live (S2S, cloud) ◀── system prompt + 40 tools
  │                                        │ audio 24k + transcript + tool calls
  ◀────────────────────────────────────────┘
กล้อง USB ─▶ greeter.run() ─▶ facewatch.Watcher (SCRFD+AuraFace, ในเครื่อง)
                                 │ known/stranger → events.announce(summon=True)
                                 └─▶ wake.summon() → เบราว์เซอร์ standby เปิด /ws
tools ─▶ Broadlink IR · Canva (Playwright) · Supabase · เครื่องพิมพ์ · os.startfile
      └▶ robot_link.send() ─▶ {"type":"robot"} ลง /ws เดิม ─▶ [แอป Android ยังไม่มี] ─▶ Aobo SDK

ข้อสังเกตเชิงสถาปัตยกรรม:

  • เซิร์ฟเวอร์เป็น proxy (คีย์ไม่ถึงเบราว์เซอร์, prompt อยู่ฝั่งเซิร์ฟเวอร์) — ถูกต้อง
  • ทุกอย่างอยู่ใน process เดียวบน Windows PC: เสียงสด + ONNX ใบหน้า + Chromium automation + คิวเสียง ไม่มี watchdog/service manager ที่เห็นในรีโป (มีแค่ run_server.py) — process ตายครั้งเดียว ทุกอย่างตายพร้อมกัน
  • ไม่มีชั้น "Robot Command Gateway" ตามหลักข้อ 6 ของ brief: เส้นทางคือ LLM → @tool → find_place (ตรวจแค่ชื่อ POI) → ส่งลง WS → SDK ไม่มี permission check, ไม่มี safety policy, ไม่มี robot-state check ฝั่งเซิร์ฟเวอร์ (STATE["moving"] เป็นสิ่งที่ส่งไป ไม่ใช่วัดจริง — โค้ดยอมรับเองใน docstring)
  • state ระดับ module (robot_link.STATE, slides.STATE, calc) ผูกกับ "หุ่นตัวเดียว เซสชันเดียว" — ขยายไปหลายหุ่นต้องรื้อ

C. Critical Issues (จัดลำดับ)

#ระดับปัญหาหลักฐานทางที่ปลอดภัยกว่า
1Blockerหยุดฉุกเฉินพึ่ง LLM + อินเทอร์เน็ต ไม่มีเส้นทางหยุดในเครื่องapp/tools/robot.py stop_moving เป็น @tool; ไม่มีโค้ดใดจับคำ "หยุด" นอก LLM ยกเว้น heard.asks_to_stop ซึ่งใช้กับสไลด์เท่านั้น; README ยอมรับว่า offline fallback ยังไม่มีKWS ในเครื่อง (sherpa มีอยู่แล้ว) จับ "หยุด/stop" → ส่ง cancel_navigation ตรงจากแอปบนหุ่นโดยไม่ผ่านเซิร์ฟเวอร์; ปุ่ม E-Stop กายภาพตัดมอเตอร์; bumper/obstacle อยู่ในเฟิร์มแวร์นำทาง ไม่ใช่ใน Python
2Blockerสวมรอยเป็นหุ่นได้ด้วย token เดียวกับเบราว์เซอร์session.py รับ robot_ready/robot_arrived จาก client ใดก็ได้บน /ws; docs/ต่อกับหุ่นยนต์ Astronaut.md ระบุ "ยืนยันตัวตนระหว่างหุ่นกับเซิร์ฟเวอร์ ยังไม่ได้ทำ"; token อยู่ใน query string (?token=) ติดใน browser history/proxy logtoken แยกสำหรับหุ่น (ROBOT_TOKEN) หรือ mTLS; ส่ง token ใน header/first message ไม่ใช่ URL; เซิร์ฟเวอร์รับ robot_* เฉพาะซ็อกเก็ตที่ยืนยันเป็นหุ่น
3Blockerข้อมูลชีวมิติไม่มี consent record, ไม่มีทางถอน, prompt สั่งซ่อนกล้องgallery.npz meta มีแค่ group; data/faces/enrolled/<ชื่อ>/*.jpg เก็บรูปหน้าดิบ (652 KB, 4 คน); greeter.greeting_for: "ห้ามพูดถึงกล้อง"; ลบได้แค่ลบโฟลเดอร์ + rebuild ด้วยมือ; ไฟล์ไม่เข้ารหัสเพิ่มฟิลด์ consent_at / consent_by / expires ใน meta และปฏิเสธ build ถ้าว่าง; คำสั่ง revoke_face --name ที่ลบ crops + rebuild + บันทึก audit; ป้ายที่กล้อง + ข้อความบนจอ (มีแล้วบางส่วน: "กล้องหน้าประตูกำลังดูอยู่"); ให้ DPO ตัดสินฐานกฎหมาย
4Criticalเสียงลูกค้าออกไป Google free tier ที่ใช้ข้อมูลปรับปรุงผลิตภัณฑ์ โดยไม่มีประกาศCLAUDE.md ระบุเงื่อนไข pricing; ไม่มี privacy notice ใน client/index.html; /health คืน free_tier: trueเปิด billing ก่อน pilot; ป้าย/หน้าจอแจ้งว่าเสียงถูกประมวลผลบนคลาวด์ ไม่บันทึกเสียง เก็บข้อความ 30 วัน
5Criticalไม่มีโหมดออฟไลน์/degraded และไม่มี tool เรียกพนักงานรายการ tool 40 ตัวไม่มี call_staff/create_service_request; README "Offline fallback — both providers need network by design"; local TTS มีแล้วสำหรับสถานีลงทะเบียน (app/voice.py) แต่ไม่ได้ใช้เป็น fallback ของสายชุดประโยคเสียงพร้อมใช้ในเครื่อง ("ระบบขัดข้อง กรุณากดปุ่มเรียกพนักงาน"), ปุ่ม/tool call_staff ที่ทำงานโดยไม่พึ่ง LLM (LINE Notify/เสียงเรียก), state machine ที่รู้ว่า provider หลุดแล้วพูดเอง
6Criticalชื่อจากกล้องถูกฝังเข้าบทสนทนา → โมเดลผูกเสียงทุกคนหลังจากนั้นกับชื่อนั้นgreeting_for ส่ง "พีท เพิ่งเดินเข้ามา…" เป็น user turn; ไม่มี active-speaker detection; facewatch.see ดูเฉพาะหน้าที่ใหญ่สุด; วัดจริง 1 ก.ย.: คน 2 คนคุยอยู่ถูกจับเป็น stranger 3 ครั้ง (0.355–0.478)ใช้ชื่อเฉพาะในประโยคทักครั้งแรก แล้วบอกโมเดลว่า "หลังจากนี้ห้ามสรุปว่าใครพูด"; ไม่ส่งชื่อเมื่อมี >1 หน้าในเฟรม; ไม่นำชื่อไปใช้กับการตัดสินใจใดที่มีสิทธิ์ต่างกัน

I. Cost & Scalability Review

  • ต้นทุนต่อบทสนทนาต่ำและวัดแล้ว: Live API ~10 บาท/10 นาทีเมื่อเปิด billing; wake word + VAD ทำให้ไม่จ่ายตอนห้องว่าง (วัดแล้วใน log); peak 7K tokens/นาที จาก 65K — ห้องขายหุ่นตัวเดียวไม่ชนเพดาน

  • Scale: ออกแบบเป็น "หุ่นหนึ่งตัว บทสนทนาเดียว" ทั้งระบบ (module state, _active, Canva handle เดียว); MULTI_SESSION มีไว้ให้ทดลองเท่านั้นและตัด tool ที่แชร์ไม่ได้ออก — ขยายหลายหุ่น/หลายสาขาต้องทำ state per-session และแยก inference ออกเป็น service

M. Go / Conditional Go / No-Go

Conditional Go — Pilot เสียงในห้องขาย โดยมีพนักงานอยู่

อนุญาตเมื่อครบ: billing เปิด + ป้ายแจ้ง + degraded mode/ปุ่มเรียกพนักงาน + เครื่องล็อก (token/BitLocker/read-only key) + monitoring + วัด V-01..V-11 หนึ่งวัน · profile condo เท่านั้น · TOOL_GROUPS ไม่มี computer/websearch/robot

No-Go จนกว่า DPO อนุมัติ — Face recognition นอกโต๊ะเจ้าของ

ปลดล็อกเมื่อ: DPIA + consent record + revoke path + calibrate ที่จุดติดตั้ง + แก้ C-6 · ระหว่างนั้น pilot ด้วย FACE_ENABLED=false หรือ FACE_GREET_STRANGERS=true แต่ gallery ว่าง (anonymous detection อย่างเดียว) — ถ้า DPO เห็นชอบว่าการ detect โดยไม่ระบุตัวตนไม่ต้องขอความยินยอม

No-Go — หุ่นเคลื่อนที่ในพื้นที่มีลูกค้า

ไม่มีข้อยกเว้นจนกว่า: แอปบนหุ่นมี Safety Controller ที่หยุดในเครื่อง, E-Stop กายภาพ, Command Gateway + allow-list, ROBOT_TOKEN, และ R-01/R-03/R-08/R-09 ผ่านในแผนที่ปิด · การที่ HALF_DUPLEX=true ปิดไมค์ขณะหุ่นพูด คือเหตุผลที่ชัดที่สุดว่า "หยุด" ผ่านเส้นทางเสียงปัจจุบันไม่ได้
