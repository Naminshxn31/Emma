## ความเห็นโดยรวม

โปรเจคนี้เป็นระบบผู้ช่วยเสียงสำหรับเครื่องประจำจุดที่พัฒนาไปไกลกว่าต้นแบบแล้ว มีการรับมือปัญหาที่เกิดในการใช้งานจริงอย่างจริงจัง โดยเฉพาะการพูดแทรก การรอให้ผู้ใช้ได้ยินก่อนเปลี่ยนสไลด์ การปลุกด้วยเสียง/กล้อง และการรายงานผลอุปกรณ์อย่างตรงไปตรงมา

อย่างไรก็ตาม **ยังไม่ควรถือว่าพร้อมเปิดเป็นระบบหลายผู้ใช้หรือพร้อมใช้งานโดยไม่มีคนดูแล** จุดที่น่าห่วงที่สุดคือข้อจำกัดที่ตั้งไว้ใน configuration ไม่ได้ถูกบังคับครบทุกเส้นทาง และข้อมูล/สถานะของเครื่องยังปะปนกับข้อมูลของแต่ละการสนทนา

ชุดทดสอบเดิมผ่านทั้งหมด แต่พบปัญหาที่จำลองยืนยันเพิ่มได้ 8 เรื่อง ดังนั้นผลทดสอบสีเขียวรอบนี้บอกว่า regression ที่มีอยู่ยังผ่าน ไม่ได้ยืนยันว่าขอบเขตสิทธิ์ ความเป็นส่วนตัว และความต่อเนื่องของระบบเสียงครบถ้วนแล้ว

## สถาปัตยกรรมและจุดแข็ง

| ส่วน | หน้าที่ | ความเห็น |
|---|---|---|
| `app/main.py` | HTTP, WebSocket, startup/shutdown | ทางเข้าแยกชัด แต่ startup มีการ import เครื่องมือที่กระทบ registry |
| `app/session.py` | เชื่อมเสียงและ event ระหว่าง client กับ provider | รวมพฤติกรรมการสนทนาได้ดี แต่รับผิดชอบมาก และพึ่งสถานะส่วนกลางหลายชุด |
| `app/providers/` | แปลง Gemini/OpenAI เป็น protocol กลาง | เป็นขอบเขตที่เหมาะสม ช่วยให้เปลี่ยน provider โดยไม่เปลี่ยน client ทั้งชุด |
| `app/tools/registry.py` | ประกาศและเรียกเครื่องมือ | ใช้ง่าย แต่ registration, authorization และ execution ยังไม่แยกกันชัด |
| `app/display.py` และ presentation tools | ควบคุมภาพและเวลาตามเสียงที่เล่นจริง | แนวคิด audio lead เหมาะกับงานนี้ และมี regression tests รองรับมาก |
| `app/tools/retrieval.py` และ search tools | ค้นข้อมูลจากคลังโครงการ/เอกสาร | มีการแบ่งแหล่งข้อมูลและป้องกันการเดาราคา แต่สถานะการอนุมัติหลุดในหนึ่งเส้นทาง |
| กล้อง/wake/greeter/events | ปลุกและทักทายโดยไม่เปิด Live session ตลอดเวลา | แยกองค์ประกอบค่อนข้างดี แต่ยังต้องวัดกับสภาพห้องจริง |
| `client/index.html` | ไมโครโฟน playback transcript และหลายรูปแบบหน้าจอ | ครบสำหรับเครื่อง kiosk แต่ไฟล์เดียวประมาณ 136 KB ทำให้ตรวจ lifecycle และการเปลี่ยนโหมดได้ยาก |

จุดแข็งที่ควรรักษา:

1. API key อยู่ฝั่งเซิร์ฟเวอร์ และระบบไม่รับ system instruction ตรงจาก browser
2. มี provider abstraction และทดสอบ transport ด้วย fake upstream รวมถึง local WebSocket server
3. มีการแยกผล `ok/mock/failed` ในเครื่องมืออุปกรณ์หลายส่วน และจำกัดจำนวนสำเนาเอกสาร
4. มี regression tests จากเหตุการณ์จริง เช่น เสียงนำภาพ การปลุกแล้วไมค์ไม่ทำงาน และการส่งประกาศทับกัน
5. มีมาตรการลดการแต่งข้อมูลขาย รวมทั้งราคาที่ไม่ควรอ่านออกเสียงและการแยก draft/approved ในเส้นทางสไลด์
6. `.gitignore` แยก secret, logs, memory, รูปใบหน้าและ embeddings ออกจากไฟล์ที่ควร commit

### 1. [P1] การปิดกลุ่มเครื่องมือและ MULTI_SESSION ไม่ได้บังคับสิทธิ์ที่ registry

**ตำแหน่ง:** [load_tools](../../app/tools/__init__.py#L88), [knowledge import](../../app/tools/knowledge.py#L28), [dispatch](../../app/tools/registry.py#L139), [startup import units](../../app/main.py#L188)

`enabled_tool_groups()` เลือกโมดูลที่จะ import แต่ decorator ลงทะเบียนทุกเครื่องมือทันทีเมื่อโมดูลถูก import และทั้ง schema ที่ส่งให้โมเดลกับ `dispatch()` อ่าน registry ทั้งหมด ไม่มีการตรวจ allowed groups อีกชั้น

ตัวอย่างชัดเจนคือ `knowledge.py` import ฟังก์ชันจาก `slides.py` ทำให้เครื่องมือสไลด์ทั้งกลุ่มถูกลงทะเบียน แม้ตั้ง `TOOL_GROUPS=knowledge` และเปิด `MULTI_SESSION=true` ซึ่งควรห้ามกลุ่ม slides

**ยืนยันใน process ใหม่:** allowed groups มีเพียง `knowledge` แต่ registry มี `show_slide`, `start_presentation`, `next_slide`, `go_to_page`, `previous_slide`, `hide_slide`, `close_presentation`, `stop_presentation`, `resume_presentation` รวมกับ `search_condo_info`

ยังมีช่องทางที่ต้องแก้พร้อมกัน: `search_condo_info()` เขียน `slides.STATE` ผ่าน `show_current()` ที่บรรทัด 217 ทั้งที่ knowledge ถูกจัดเป็นเครื่องมืออ่านข้อมูลที่ใช้ร่วมกันได้ ส่วนกลุ่ม units มี `show_quotation`/`show_project_map` ที่เรียก webstage ซึ่ง `enabled()` ตรวจเพียง `WEB_STAGE` ไม่ตรวจ multi-session ดังนั้นแค่กรอง schema ยังไม่เพียงพอสำหรับการแยกผลข้างเคียง

**ผลกระทบ:** ผู้ใช้ในโหมดแชร์อาจได้เครื่องมือที่เปลี่ยนสถานะ presentation หรือหน้าต่างของเครื่อง และพฤติกรรมขึ้นกับลำดับ import การปิดเครื่องมือใน configuration จึงยังใช้เป็นขอบเขตสิทธิ์ที่เชื่อถือไม่ได้

**แนวทางแก้:** แยก catalog ของเครื่องมือที่รู้จักออกจากชุดเครื่องมือที่เซสชันได้รับอนุญาต กรองทั้งตอนสร้าง provider schema และก่อน dispatch ย้ายฟังก์ชันอ่านคลังสไลด์ออกจากโมดูลที่มี decorator และแยกการค้นข้อมูลออกจากการเปลี่ยนจออย่างชัดเจนในโหมดแชร์

**การทดสอบที่ขาด:** cold-process tests สำหรับ `TOOLS_ENABLED=false`, แต่ละกลุ่มเดี่ยว และ multi-session โดยตรวจทั้ง schema, dispatch ของเครื่องมือที่ถูกห้าม และผลข้างเคียงต่อจอ/STATE หลัง import และ startup จริง

### 2. [P1] ความจำส่วนตัวถูกใส่ในพรอมป์ต์ของโหมดแชร์ และเลือก Emma ได้จาก URL

**ตำแหน่ง:** [profile ต่อเซสชัน](../../app/session.py#L90), [build_instructions](../../app/prompts.py#L437), [memory injection](../../app/prompts.py#L464)

เมื่อ profile เป็น `emma`, `build_instructions()` เรียก `memory_store.prompt_block()` เสมอ โดยไม่ตรวจ `MULTI_SESSION` หรือสิทธิ์อ่าน memory การตัดกลุ่มเครื่องมือ memory ออกจึงป้องกันได้เฉพาะการเรียกเครื่องมือ แต่ข้อมูลยังถูกใส่ใน system prompt ตั้งแต่ต้น

นอกจากนี้ `/ws` รับ `profile` จาก query parameter ทำให้ผู้ถือ token สำหรับเข้าใช้งานระบบสามารถขอ profile `emma` ได้แม้เครื่องตั้งค่าเป็น `condo` ไม่มีการแยกสิทธิ์เจ้าของสำหรับ profile นี้

**ยืนยัน:** ตั้ง multi-session และแทน memory ด้วยข้อความสังเคราะห์ `PRIVATE_REVIEW_SENTINEL` จากนั้นสร้างพรอมป์ต์ Emma พบ sentinel ในพรอมป์ต์จริง

**ผลกระทบ:** ข้อมูลที่บันทึกไว้เกี่ยวกับเจ้าของถูกส่งเข้า provider session ของผู้ใช้ร่วมเครื่อง/ผู้ทดสอบ และโมเดลอาจนำข้อมูลนั้นมาตอบ แม้เซสชันนั้นไม่มี memory tool

**แนวทางแก้:** ปิดการแนบ personal memory ใน shared mode โดยค่าเริ่มต้น และตรวจสิทธิ์ profile ฝั่งเซิร์ฟเวอร์ หากต้องรองรับผู้ใช้หลายคนจริง ให้จัดเก็บและอ่าน memory ตาม user identity ไม่ใช่ไฟล์ส่วนกลางของเครื่อง

**การทดสอบที่ขาด:** ตรวจว่า shared mode และผู้ใช้ทั่วไปไม่ได้รับ sentinel ทั้งใน system prompt, greeting และ tool result; ทดสอบ `?profile=emma` บนเครื่อง condo โดยไม่มีสิทธิ์เจ้าของ

### 3. [P1] เครื่องมือที่ทำ I/O แบบ synchronous ทำให้วงรอบเสียงค้าง และ timeout ไม่ช่วย

**ตำแหน่ง:** [registry handler call](../../app/tools/registry.py#L160), [print_document](../../app/tools/documents.py#L319), [printer subprocess](../../app/tools/documents.py#L199), [inventory HTTP](../../app/tools/units.py#L219), [web search](../../app/tools/websearch.py#L68)

`dispatch()` เรียก `entry.handler(**args)` บน event loop โดยตรง แล้วจึงตรวจว่าผลเป็น awaitable หรือไม่ เครื่องมือ synchronous ที่รอ HTTP จึงบล็อก loop ก่อนจะมี timeout ครอบ ส่วน `print_document` แม้ประกาศเป็น async แต่เรียก `send_to_printer()` ตรง ๆ ภายใน ซึ่งมี `subprocess.run` ที่รอได้ถึง 60 วินาที

**ยืนยัน:** แทน printer ด้วยฟังก์ชันหน่วง 150 ms และลด tool timeout เหลือ 30 ms ผลยังเป็น `ok=True` ใช้เวลาประมาณ 173 ms และ heartbeat ที่ควรตื่นภายใน 10 ms เพิ่งได้ทำงานหลังงานพิมพ์จบ

**ผลกระทบ:** ระหว่างรอเครื่องพิมพ์/เว็บ/ฐานข้อมูล การรับส่งเสียง การพูดแทรก และงานอื่นบน event loop หยุดไปด้วย ถ้าเปิดหลายเซสชันจะกระทบผู้ใช้พร้อมกัน ไม่ใช่แค่คนเรียกเครื่องมือ

**แนวทางแก้:** ใช้ async HTTP/subprocess หรือย้ายงาน blocking เฉพาะส่วนไป worker thread พร้อมขอบเขตเวลา ระวังไม่ย้าย async tools และฟังก์ชันที่ต้องใช้งาน event loop ไป thread แบบเหมารวม งานอุปกรณ์ที่ถูก timeout ต้องกำหนดด้วยว่าจะมีผลต่อภายหลังได้หรือไม่ เพื่อป้องกันการ retry แล้วทำซ้ำ

**การทดสอบที่ขาด:** ทดสอบ heartbeat/การรับ audio ระหว่าง printer และ network stall รวมถึงพฤติกรรมหลัง timeout และการส่งคำสั่งซ้ำ

### 4. [P1] คลังความรู้ส่งบทที่ยังไม่อนุมัติออกมาในชื่อ approved_script

**ตำแหน่ง:** [knowledge._entry](../../app/tools/knowledge.py#L82), เทียบกับ [slides._public](../../app/tools/slides.py#L235)

`_entry()` นำ `script_th` หรือ `script_en` ใส่ `approved_script` ทันทีที่มีข้อความ ไม่อ่าน `script_approved` ต่างจากเส้นทางแสดงสไลด์ที่แยก `script_is_draft` กับ `script_is_approved_copy`

**ยืนยัน:** ส่ง entry สังเคราะห์ที่มี `script_approved=False` แล้วได้ `approved_script: UNAPPROVED REVIEW FIXTURE` กลับมา ใน index ปัจจุบันมี 150 entries และ 64 entries ที่มีบทบรรยาย ซึ่งทั้ง 64 ยังไม่ถูกระบุว่าอนุมัติ

**ผลกระทบ:** การตอบผ่าน `search_condo_info` ทำให้โมเดลได้รับเนื้อหาร่างในฟิลด์ที่ระบุว่าอนุมัติแล้ว เป็นความผิดพลาดของ provenance แม้มีคำสั่งห้ามเดาราคาอยู่ส่วนอื่น

**แนวทางแก้:** ใช้ตัวแปลงสถานะการอนุมัติร่วมกันทุก retrieval surface ส่งฟิลด์ approved เฉพาะรายการที่อนุมัติ และระบุ draft ให้ชัดหากนโยบายอนุญาตให้ใช้ ห้ามแก้โดยเปลี่ยนสถานะข้อมูลทั้งหมดเป็น approved

**การทดสอบที่ขาด:** matrix ของ approved=true/false/ไม่มีฟิลด์ ทั้งบทไทยและอังกฤษ และตรวจผลจาก `search_condo_info` จริง ไม่ใช่เฉพาะตัวแปลงของ slides

การ reset สไลด์และ ROI อยู่ภายในเงื่อนไขว่ามีเซสชันเก่าให้ takeover เท่านั้น เมื่อคนแรกวางสายปกติ `_active` จะเป็น None คนถัดไปจึงเข้าโดยไม่ล้าง STATE เดิม ขณะที่ `calc_roi` ใช้ `STATE.update()` เพื่อเติมเฉพาะตัวเลขที่ผู้ใช้เปลี่ยน

**ยืนยัน:** จำลองสองสายต่อกันโดยสายแรกตั้ง `price_thb=8765432` และจบตามปกติ สายที่สองเริ่มมาพร้อม `{'price_thb': 8765432}` แทน state ว่าง

**ผลกระทบ:** ลูกค้าคนถัดไปอาจคำนวณจากราคาหรือสมมติฐานของคนก่อน และเห็นตัวเลขเหล่านั้นในผลลัพธ์ ปัญหานี้ต่างจากการตั้งใจเก็บ memory ของเจ้าของ เพราะ ROI เป็นข้อมูลเฉพาะบทสนทนา

**แนวทางแก้:** ทำ calc state เป็นของเซสชัน หรือ reset ที่ขอบเขตเริ่ม/จบการสนทนาปกติด้วย กำหนดแยกให้ชัดระหว่าง reconnect ของคนเดิมกับการเริ่มสนทนาของคนใหม่ และระวัง cleanup ของสายเก่าไปล้างข้อมูลสายใหม่ระหว่าง takeover

**การทดสอบที่ขาด:** สาย A จบปกติ → สาย B เปิด → ให้ B ระบุเฉพาะค่าเช่า ต้องขอราคาจาก B ใหม่ ไม่ใช้ราคาของ A; ครอบคลุม End, idle timeout, upstream disconnect และ takeover

### 6. [P2] ส่งคำสั่งหุ่นยนต์ล้มเหลว แต่รายงานกลับว่า ok

**ตำแหน่ง:** [robot_link.send](../../app/tools/robot_link.py#L207), [VoiceSession._send_json](../../app/session.py#L921)

`robot_link.send()` ครอบ `_send_json()` ด้วย try/except เพื่อคืน `failed` เมื่อส่งไม่ได้ แต่ `_send_json()` กลืน exception ทุกชนิดแล้วคืนปกติอยู่ก่อน จึงไม่ถึง except ชั้นนอก และคืน `ok` แม้ socket ส่งไม่ได้

**ยืนยัน:** ใช้ WebSocket จำลองที่ `send_text()` โยน `ConnectionError` เสมอ เมื่อเรียก `robot_link.send('stop')` ได้ผล `ok`

**ผลกระทบ:** ในช่วงรอยต่อที่ socket เสียแต่ state ยังเห็นว่า connected ระบบสามารถพูดยืนยันว่าส่งคำสั่งเคลื่อนที่/หยุดแล้ว ทั้งที่การส่งล้มเหลว การเรียก `app_gone()` เมื่อ teardown ช่วยได้บางช่วงแต่ไม่แก้เส้นทางส่งนี้

**แนวทางแก้:** แยกการส่งคำสั่งอุปกรณ์ที่ต้องรายงานความล้มเหลวออกจากการส่ง UI ที่ยอมทิ้งได้ และแยกความหมายส่งสำเร็จ/อุปกรณ์รับคำสั่ง/ทำงานสำเร็จ หากต้องยืนยันการรับจริงให้มี command ID และ ACK

**การทดสอบที่ขาด:** เชื่อม VoiceSession จริงกับ robot_link โดยให้ socket โยน error ทดสอบทั้ง navigate และ stop ไม่ patch `_send_json` จนข้ามจุดที่กลืน error

### 7. [P2] WS_TOKEN ไม่ได้ป้องกันการดาวน์โหลดคลังสไลด์และบทบรรยาย

**ตำแหน่ง:** [StaticFiles mount](../../app/main.py#L41)

แอป mount ทั้งโฟลเดอร์ `slides_dir` เป็น public static files รวมถึง `index.json` ไม่ได้ให้บริการเฉพาะไฟล์ภาพ และไม่ตรวจ token ใน HTTP path นี้

**ยืนยัน:** ตั้ง WS_TOKEN เป็นค่าสังเคราะห์ แล้วส่ง `GET /slides/index.json` โดยไม่มี token ผ่าน TestClient ได้ HTTP 200 และข้อมูลประมาณ 439 KB โดยไม่ได้เปิด provider session

**ผลกระทบ:** ผู้ที่เข้าถึงพอร์ตสามารถอ่านคลังคำบรรยายและบท draft ได้ แม้เข้า WebSocket ไม่ได้ หากเนื้อหาเหล่านี้ตั้งใจเปิดเผยทั้งหมด ความรุนแรงด้านข้อมูลจะลดลง แต่ token ปัจจุบันไม่ได้ป้องกันไฟล์เหล่านี้ตามที่ผู้ติดตั้งอาจเข้าใจ

**แนวทางแก้:** แยก public image assets ออกจาก metadata ภายใน และหากภาพเป็นข้อมูลจำกัดสิทธิ์ด้วย ให้ใช้การยืนยันตัวตนที่ครอบคลุม asset requests เช่น session cookie หรือ URL ที่ลงนาม ไม่ใช่ป้องกันเฉพาะ WebSocket

**การทดสอบที่ขาด:** ตรวจว่าไม่มี token แล้วอ่าน metadata/draft ไม่ได้ และหน้าจอที่ผ่านสิทธิ์ยังโหลดภาพได้ครบ

### 8. [P2] คำพูดปกติของผู้ช่วยไม่ได้ถูกบันทึกใน turn log

**ตำแหน่ง:** [assistant_transcript branch](../../app/session.py#L544), [said record](../../app/session.py#L556)

`turnlog.record('said', ...)` ถูกเยื้องอยู่ภายในเงื่อนไขตรวจ silent block ซึ่งต้องมี newline อย่างน้อยสองครั้งและความยาวอย่างน้อย 40 ตัวอักษร ดังนั้นข้อความพูดปกติที่ทยอยส่งเป็น chunk จะส่งให้ UI แต่ไม่ลง log

**ยืนยัน:** ป้อน `ProviderEvent(kind='assistant_transcript', text='ordinary spoken review fixture')` ผ่าน pump จริง โดยดักการเรียก record พบว่าไม่มี event ถูกบันทึก

**ผลกระทบ:** เวลาตรวจว่า Emma พูดอะไรผิดหรือพูดเกินข้อมูล หลักฐานปกติฝั่งผู้ช่วยจะหาย แม้ยังมีคำพูดของผู้ใช้และชื่อเครื่องมือ ทำให้รายงานจาก log ไม่สมบูรณ์

**แนวทางแก้:** บันทึก assistant transcript นอกเงื่อนไข silent block และพิจารณารวม chunks เป็น turn พร้อม session ID เพื่ออ่านเหตุการณ์พร้อมกันได้ถูกคน โดยยังเคารพ TURN_LOG และ retention เดิม

**การทดสอบที่ขาด:** normal chunk, หลาย chunks, silent block และ interruption ต้องมีข้อมูลที่คาดหวังโดยไม่ซ้ำ และปิด TURN_LOG แล้วยังไม่เขียนไฟล์

## การตั้งค่าบนเครื่องนี้และความเสี่ยงเพิ่มเติม

ตรวจเฉพาะค่าที่เกี่ยวข้องและสถานะว่ามี secret หรือไม่ ไม่พิมพ์ค่า secret:

| รายการ | ที่พบ | ความหมาย |
|---|---|---|
| Profile | `emma` | เครื่องนี้ใช้โหมดผู้ช่วยส่วนตัว |
| Bind address | `0.0.0.0` | รับการเชื่อมต่อจาก interface เครือข่ายได้; การเข้าถึงจริงยังขึ้นกับ firewall |
| WS_TOKEN | ตั้งค่าแล้ว | ปัญหา default token ว่างไม่ใช่สถานะปัจจุบันของเครื่องนี้ |
| MULTI_SESSION | ปิด | ปัญหาโหมดแชร์จะมีผลเมื่อเปิดโหมดนี้; การเลือก profile จาก URL เป็นอีกเส้นทางที่ต้องพิจารณา |
| ROBOT_TOKEN | ยังไม่ตั้ง | ยังไม่พร้อมยืนยันตัวแอปหุ่นยนต์ผ่าน robot_ready |
| FACE_ENABLED | เปิด | กล้องเป็นส่วนหนึ่งของเส้นทางปลุกบนเครื่องนี้ |
| FACE_REQUIRE_CONSENT | ปิด | โค้ดยอมเรียกชื่อคนที่ยังไม่มี consent record ได้ ไม่ได้สรุปจากค่านี้ว่าการปฏิบัติงานจริงมีหรือไม่มีความยินยอม |
| TURN_LOG | เปิด | คำพูดผู้ใช้สามารถถูกเก็บลงดิสก์; ควรกำหนดผู้เข้าถึงและรอบการลบให้ตรงการใช้งาน |
| EMBED_PROVIDER | `local` | ควรมี smoke test สำหรับโมเดลและ dependencies ของเส้นทางนี้บนเครื่องติดตั้งใหม่ |

ความเสี่ยงที่ควรจัดการเพิ่มเติม แต่ยังไม่ได้จัดเป็นบั๊กจำลองยืนยันใน 8 ข้อข้างต้น:

- **ค่าเริ่มต้นการติดตั้งเปิดกว้าง:** `HOST=0.0.0.0` และ `WS_TOKEN=''` ใน config เปิดให้เครื่องในเครือข่ายเริ่มเซสชันโดยไม่ยืนยันตัวตน มี warning แต่ไม่ป้องกัน ควรเริ่มด้วย loopback หรือบังคับมี credential ก่อน bind ภายนอก ทั้งนี้เครื่องที่ตรวจมี WS_TOKEN แล้ว
- **ติดตั้งซ้ำให้เหมือนเดิมได้ยาก:** requirements ใช้ `>=` เกือบทั้งหมด ไม่มี lock/constraints ที่ตรึงชุดที่ผ่านทดสอบไว้ และรวม runtime, testing และงานเสริมไว้ด้วยกัน ควรบันทึก Python/dependency versions ที่รองรับ แยก optional dependency groups และทดสอบการติดตั้งใหม่
- **เอกสารตามโค้ดไม่ทัน:** README ระบุ 495 tests แต่ปัจจุบันรันได้ 1,064 tests และบางส่วนยังบอกว่า wake word/authentication ไม่ได้ทำ ทั้งที่มี implementation แล้ว ควรปรับ readiness checklist จากพฤติกรรมปัจจุบัน
- **ไม่มีหลักฐานคุณภาพบนอุปกรณ์จาก test suite รอบนี้:** fixture ตั้งใจปิดกล้องจริง TTS จริง การเปิด browser และ semantic encoder บางเส้นทาง เพื่อให้ unit tests ปลอดภัยและทำซ้ำได้ ต้องมีชุดทดสอบการติดตั้งและการใช้งานจริงอีกชั้น
- **ไฟล์หลักรับผิดชอบมาก:** แยก browser audio lifecycle, transcript UI และ screen renderers ออกจาก HTML ไฟล์เดียว และแยก session transport, announcement และ presentation orchestration เมื่อมี test ครอบคลุมแล้ว ไม่จำเป็นต้องรีไรต์ทั้งระบบ
- **ความคงทนของข้อมูล:** memory/consent บางเส้นทางเขียน JSON ทับโดยตรง ควรเพิ่ม atomic replace และการจัดการ writer หลายตัวตามวิธีใช้งานจริง รวมถึงแผนสำรอง/กู้คืนข้อมูล ไม่ควรใช้ log เป็นฐานข้อมูลหลัก

## ลำดับการแก้ที่แนะนำ

1. **ปิดช่องข้อมูลและสิทธิ์ก่อน:** บังคับ allowed tools ที่ schema+dispatch, จำกัด profile/memory, แก้ approved_script และจำกัดการเผยแพร่ metadata
2. **ทำให้เสียงไม่สะดุดจากเครื่องมือ:** ย้าย blocking I/O และทดสอบ timeout/การยกเลิก โดยเฉพาะ printer, inventory, web search
3. **แยกข้อมูลระหว่างผู้ใช้และทำผลอุปกรณ์ให้ตรงจริง:** reset/session-scope ของ ROI และ presentation, แก้ robot send failure
4. **ทำให้ตรวจเหตุย้อนหลังได้:** คืน log คำพูดผู้ช่วย เพิ่ม session ID และทดสอบเหตุการณ์พร้อมกัน
5. **ยืนยันการติดตั้ง:** dependency constraints, README ที่ตรงระบบ, clean-install smoke test และทดสอบด้วยเสียง/กล้อง/อุปกรณ์จริงที่มีคนดูแล

เกณฑ์ก่อนเปิดใช้งานหลายผู้ใช้ควรเป็นการพิสูจน์ว่าไม่มี private memory ข้ามคน ไม่มี forbidden tools หลุดจาก import ไม่มีข้อมูลคำนวณค้าง และการค้นของคนหนึ่งไม่เปลี่ยนจอหรือสถานะของอีกคน ส่วนเกณฑ์ก่อนต่อหุ่นยนต์จริงต้องพิสูจน์เพิ่มเติมว่าการส่งคำสั่งล้มเหลวไม่รายงานสำเร็จ และมีพฤติกรรมหยุดที่ตรวจสอบได้เมื่อการเชื่อมต่อขาด

รีวิวนี้ยังไม่ได้แก้ข้อค้นพบข้างต้น ไฟล์ระบบยังคงเดิม โดยเพิ่มเฉพาะรายงานนี้เป็นผลส่งมอบ
