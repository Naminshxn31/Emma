## ข้อค้นพบใหม่ เรียงตามความสำคัญ

### 1. [P1] ประตูอนุมัติถูกติดตั้งครบ แต่ไม่มีเครื่องมือให้ผ่าน และยังไม่มีอะไรผ่านเลย

**ตำแหน่ง:** [evaluate_claim](../../app/knowledge_policy.py#L45), [_render_facts](../../app/prompts.py#L195), [knowledge._entry](../../app/tools/knowledge.py#L75), [approve_narration.py](../../scripts/approve_narration.py)

นโยบาย `customer_claim_v1` ต้องการฟิลด์ครบหกตัว (`approval_status`, `approved_by`,
`approved_at`, `effective_at`, `disclosure_scope`, `content_state`) ก่อนปล่อยข้อความใดๆ
ให้ลูกค้า ออกแบบถูกแล้ว — แต่**ไม่มีโค้ดบรรทัดไหนในระบบเขียนฟิลด์เหล่านี้**

ค้นทั้งรีโป `approval_status` ปรากฏใน 14 ไฟล์: 3 ไฟล์เป็นตัวอ่าน
(`knowledge_policy.py`, `prompts.py`, `slide_search.py`) ที่เหลือ 11 ไฟล์เป็นเทสต์
`scripts/approve_narration.py` ซึ่งเป็นสคริปต์อนุมัติตัวเดียวที่มี เขียนเฉพาะ
`script_approved`/`script_approved_by` ของสคีมาเดิม ไม่แตะฟิลด์ของนโยบายใหม่เลย

**วัดสถานะจริงบนเครื่องนี้:**

```
สไลด์  135 รายการ  →  ฟิลด์นโยบายทั้งหกตัว = ไม่มีเลย ครบทั้ง 135
facts            →  approval_status='draft'  disclosure_scope='internal'
                     approved_by=''  approved_at=None  effective_at=None
```

รันนโยบายกับข้อมูลชุดนี้จริง:

```
display allowed:    135 / 135     (ภาพยังขึ้นจอได้)
model_text allowed:   0 / 135     (ไม่มีบทให้โมเดลสักหน้า)
```

เรียก `search_condo_info(query="สระว่ายน้ำอยู่ชั้นไหน")` ใน process จริง:

```json
{"ok": true, "found": false, "results": [],
 "policy_trace": [{"reason": "missing_metadata", ...}],
 "instruction": "ไม่พบข้อมูลนี้ ให้บอกลูกค้าตรงๆ ว่าไม่มีข้อมูล..."}
```

และ `_render_facts()` คืน `FALLBACK_FACTS` ทำให้ system prompt ทุกเทิร์นมีแค่
"ยังโหลดข้อมูลโครงการไม่ได้ ให้บอกลูกค้าตรงๆ ว่ายังไม่มีข้อมูล"

**ยืนยันกับเซสชันจริง** `data/logs/2026-09-23.jsonl` เวลา 09:07:14 ลูกค้าถาม Emma ตอบว่า
"Embassy World คือโครงการคอนโดมิเนียมของเราค่ะ แต่ตอนนี้ดิฉันยังไม่มีข้อมูลรายละเอียด
ของโครงการนะคะ ต้องขอรบกวนให้คุณติดต่อสอบถามเพิ่มเติมกับทีมฝ่ายขายโดยตรงค่ะ"
— นั่นคือการทำตามพรอมป์ตอย่างถูกต้อง ไม่ใช่โมเดลลืมข้อมูล

**ข้อสังเกตที่ต้องแยกให้ชัด:** สไลด์ยัง**แสดงภาพได้ครบ 135 หน้า** สิ่งที่ถูกกั้นคือ
*ถ้อยคำ* เท่านั้น `presentation_policy.authorize_slide()` แยกสองสิทธิ์นี้ออกจากกัน
โดยตั้งใจ และนั่นเป็นการตัดสินใจที่ถูก — ภาพที่ตรวจ checksum แล้วคือหลักฐานที่แสดงได้
ส่วนคำบรรยายคือ claim ที่ต้องมีคนเซ็น

**ผลกระทบ:** ห้องขายที่เปิดเครื่องวันนี้ได้หุ่นยนต์ที่ทักทายได้ โชว์สไลด์ได้ แต่ตอบ
คำถามเกี่ยวกับโครงการไม่ได้เลยสักข้อ และไม่มีเส้นทางที่ไม่ใช่การแก้ JSON ด้วยมือ
ที่จะเปลี่ยนสถานะนี้ได้

**แนวทางแก้ (ต้องให้เจ้าของตัดสิน ไม่ใช่โค้ด):** ต้องมีสองอย่างแยกกัน —
(ก) *เครื่องมือ* บันทึกการอนุมัติ: ขยาย `approve_narration.py` หรือเขียนสคริปต์ใหม่ที่
เขียนฟิลด์ครบหกตัว รับ `--by` และ `--content-state` บังคับ และ**ปฏิเสธการอนุมัติหมู่
โดยไม่ระบุคน** (ข) *การอนุมัติจริง*: คนอ่านเนื้อหาแล้วเซ็น ซึ่งไม่ใช่งานของโค้ดและ
ไม่ใช่งานของผู้ช่วย ตาม `AGENTS.md` ห้ามเปลี่ยน draft เป็น approved เอง

**การทดสอบที่ขาด:** เทสต์ที่ยืนยันว่ามี *เส้นทางเขียน* ที่ทำให้รายการหนึ่งผ่านนโยบายได้
ตอนนี้เทสต์ทั้งหมดใช้ fixture สังเคราะห์ (`tests/approval_fixture.py`) จึงพิสูจน์แต่ตัวอ่าน
ไม่เคยพิสูจน์ว่าข้อมูลจริงมีทางผ่านได้ — เป็นสาเหตุที่ "ประตูไม่มีทางผ่าน" รอดสายตามาถึงวันนี้

### 2. [P1] ไมค์ตายกลางสาย ระบบวินิจฉัยถูก แต่ไม่มีใครทำอะไรต่อ

**ตำแหน่ง:** [_mic_report](../../app/session.py#L340-L378)

`_mic_report` ตรวจ "ทุกตัวอย่างเป็นศูนย์เป๊ะ" แล้วเขียนคำวินิจฉัยที่ถูกต้องและละเอียด
(ให้ไปรัน `check-mic.cmd`, บอกว่าไม่มี reload หรือ setting ไหนช่วยได้) ลง log —
แล้ว**จบแค่นั้น** ไม่มีการแจ้งหน้าจอ ไม่มีการปิดสาย ไม่มีการพยายามขอไมค์ใหม่

**หลักฐานจากเซสชันจริง 23 ก.ย.** (`data/logs/2026-09-23.jsonl`):

```
09:07:25  avg 0.0138  peak 0.0915  zero 0/204    vad_segments 1   speech level reached
09:07:30  avg 0.0023  peak 0.1992  zero 126/251  vad_segments 1   speech level reached
09:07:35  avg 0.0000  peak 0.0000  zero 250/250  vad_segments 1   DIGITAL SILENCE
   ... ซ้ำแบบเดียวกันทุก 5 วินาที ...
09:09:15  avg 0.0000  peak 0.0000  zero 251/251  vad_segments 1   DIGITAL SILENCE
09:09:18  idle_timeout quiet_s=125
```

เฟรมศูนย์เริ่มปนตั้งแต่ 09:07:30 (126 จาก 251) แล้วเป็นศูนย์ล้วนตั้งแต่ 09:07:35
รวม **103 วินาทีที่สายยังเปิดอยู่โดยหูดับสนิท** จนหมดเวลา idle

**ผลกระทบ:** ลูกค้าที่ยืนอยู่หน้าหุ่นเห็นหุ่นที่ตอบคำถามแรกแล้วเงียบไปสองนาที
อาการนี้แยกจาก "โมเดลช้า" หรือ "ไม่ได้ยินเพราะพูดเบา" ไม่ได้เลยจากฝั่งผู้ใช้ ทั้งที่
เซิร์ฟเวอร์รู้คำตอบที่แน่ชัดอยู่แล้วตั้งแต่วินาทีที่ 33 — ข้อมูลที่จำเป็นมีครบ แต่ไม่ได้
ถูกส่งไปถึงคนที่ต้องใช้มัน

**แนวทางแก้:** เมื่อ `zero == n` ติดกันเกินหนึ่งรอบรายงาน ให้ส่งสถานะขึ้นหน้าเว็บ
(หน้าคุย/kiosk มีแถบสถานะอยู่แล้ว) และพิจารณาปิดสายแทนการปล่อยให้นับถอยหลัง idle —
สายที่รับเสียงไม่ได้ไม่ใช่สายที่ "เงียบ" ระวังไม่ให้กลไกใหม่นี้ไปชนกับ
`releaseCallHardware()`/`goToSleep()` ที่มีอยู่ (ประวัติของไฟล์นี้คือกลไกใหม่ชนกลไกเก่า)

**การทดสอบที่ขาด:** ป้อนเฟรมศูนย์ล้วนต่อเนื่องเข้า `_mic_report` แล้วยืนยันว่ามีการ
แจ้งออกไปจริง ไม่ใช่แค่มีบรรทัด log

### 3. [P1] พื้น VAD เป็นค่าเดียวของทั้ง process แต่ต้องรับใช้ไมค์สองแบบ

**ตำแหน่ง:** [vad_min_rms](../../app/config.py#L861), [make_gate](../../app/vad_gate.py#L260-L276), [VadGate._min_rms](../../app/vad_gate.py#L159-L162)

`VadGate` ถูกสร้างต่อเซสชันอย่างถูกต้อง (คอมเมนต์อธิบายไว้ดี: decoder state ห้ามแชร์)
แต่ค่า `min_rms` มาจาก `settings.vad_min_rms` ซึ่งเป็นค่าระดับ process ตัวเดียว
ไม่มีพารามิเตอร์ต่อการเชื่อมต่อ

เซิร์ฟเวอร์ตัวเดียวนี้รับได้ทั้งจอหุ่น (`/?kiosk=1` ไมค์อาเรย์ + เอคโค่ลำโพง) และ
หน้าเว็บบนเครื่อง (ไมค์เดสก์ท็อป ไม่มีเอคโค่) ซึ่งเป็น chain คนละเรือนกันโดยสิ้นเชิง
คอมเมนต์ใน `.env` บันทึกไว้เองว่าค่านี้ถูกยกจาก 0.01 เป็น 0.03 แล้ว 0.04 เมื่อ 14 ก.ย.
เพราะ**บนหุ่น** เสียงรบกวน/เอคโค่ทะลุ 0.01 (วัดได้ 0.0238–0.0250) แล้วทำให้ Gemini
หลอนเป็น ja/ko ส่วนเสียงพูดจริงเข้าหุ่นวัดได้ 0.06+

นั่นเป็นการวัดที่ถูกต้องสำหรับหุ่น แต่มันกลายเป็นค่าเดียวกันที่บังคับใช้กับไมค์เดสก์ท็อปด้วย

**แก้ข้อสรุปของผมเองเมื่อเช้า:** ผมเคยเสนอให้ลด `VAD_MIN_RMS` เหลือ ~0.010 โดยเทียบ
`avg=0.0138` กับ `floor=0.04` — **เทียบผิดสถิติ** `VadGate` เทียบพื้นกับ RMS ของ
*ชังก์ตอนเปิดช่วงพูด* ไม่ใช่ค่าเฉลี่ยทั้งหน้าต่าง (`vad_gate.py:159-161`) ในเซสชันเดียวกัน
peak ขึ้นถึง 0.0915 และ 0.1992 และ `vad_segments=1` คือช่วงพูดเปิดได้จริง
มี `vad_floor` rejection **ครั้งเดียว** ทั้งเซสชัน (rms 0.0179) ดังนั้นการลดพื้นตามที่ผมเสนอ
จะรื้อการวัดของ 14 ก.ย. ทิ้งเพื่อแก้อาการที่ไม่ได้เกิดจากพื้น — **อย่าทำตามข้อเสนอนั้น**

**ผลกระทบ:** ตอนนี้ยังไม่ใช่บั๊กที่ทำให้เสียงหาย แต่เป็นหนี้เชิงโครงสร้าง: ทุกครั้งที่จูนค่านี้
ให้ไมค์ตัวหนึ่ง อีกตัวจะแย่ลงโดยไม่มีอาการชี้กลับมา และเป็นกับดักเดียวกับที่คอมเมนต์
ใน `config.py` เตือนไว้เอง ("the scale depends on the mic chain in front of it")

**แนวทางแก้:** ให้ไคลเอนต์ประกาศ chain ของตัวเอง (หุ่น/เดสก์ท็อป) แล้วเลือกพื้นจากชุด

ที่ให้เลือกจากรายการ ไม่ใช่ส่งค่า) ถ้ายังไม่ทำ อย่างน้อยควรบันทึกใน `.env` ว่าค่าปัจจุบัน

### 4. [P2] `FALLBACK_FACTS` บอกว่า "โหลดไม่ได้" ทั้งที่ความจริงคือ "ยังไม่อนุมัติ"

**ตำแหน่ง:** [FALLBACK_FACTS](../../app/prompts.py#L176-L181), [_render_facts](../../app/prompts.py#L195-L198)

คอมเมนต์เหนือ `FALLBACK_FACTS` เขียนไว้ชัดว่า "Used when the file is missing or
unreadable" แต่บรรทัด 198 เอาข้อความเดียวกันมาใช้กับกรณีนโยบายปฏิเสธ ซึ่งเป็นคนละเรื่อง
กันคนละขั้ว: กรณีหนึ่งคือไฟล์พัง อีกกรณีคือไฟล์สมบูรณ์แต่ยังไม่มีคนเซ็น

**ผลกระทบ:** คนที่มาไล่ปัญหาจะไปหาไฟล์ที่หาย ทั้งที่ต้องไปหาคนเซ็น — ผมเองเดินเข้า
กับดักนี้เมื่อเช้าวันเดียวกันนี้ และรายงานครั้งแรกออกมาว่า "ข้อมูลหาย" ก่อนจะพบว่าข้อมูล
อยู่ครบ ส่วนพรอมป์ตที่โมเดลได้รับก็ผิดเช่นกัน: Emma พูดกับลูกค้าว่า "ยังไม่มีข้อมูล"
ทั้งที่ข้อเท็จจริงคือ "มีข้อมูลแต่ยังไม่อนุมัติให้เผยแพร่" (`logger.info("knowledge policy %s")`
บันทึกเหตุผลจริงไว้ถูกต้องแล้ว แต่ไม่มีใครอ่าน log ตอนยืนอยู่หน้าหุ่น)

**แนวทางแก้:** แยกข้อความสองกรณีออกจากกัน ข้อความที่ส่งให้*โมเดล*ยังควรเหมือนเดิม
(ลูกค้าไม่ต้องรู้เรื่องสถานะอนุมัติภายใน) แต่ข้อความที่ส่งให้*คนดูแลเครื่อง* —
บรรทัด boot banner หรือ log ระดับ warning — ต้องบอกตรงๆ ว่ามีกี่รายการถูกกั้นด้วยเหตุใด

### 5. [P2] รายการล่าสุดใน CHANGELOG.md เสียหาย อักษรไทยกลายเป็น `?` ทั้งย่อหน้า

**ตำแหน่ง:** `CHANGELOG.md` บรรทัด 3–8 (อยู่ใน working tree ยังไม่ commit)

```
## 2026-09-22 ? ???? Emma ???????????????????? (Form Study 03)
- ??????: `scripts/build-emma-3d-lab.py`, ????????? `scripts/emma_sculpt_body.py` ...
```

ตรวจไบต์จริงแล้ว: ไฟล์เป็น UTF-8 ที่ถูกต้อง และไบต์ในบรรทัดเหล่านั้น**คืออักษร `?` จริงๆ**
ไม่ใช่การอ่านผิด encoding — แปลว่าเนื้อหาไทยถูกแทนที่ตอน*เขียน* ผ่าน codec ที่แทนภาษาไทย
ไม่ได้ (cp874/cp1252) **ข้อความต้นฉบับหายถาวร** กู้จากไฟล์ไม่ได้

สแกนทั้งรีโปแล้วพบเฉพาะรายการนี้รายการเดียว ไฟล์อื่นสะอาด

นี่คือกับดักที่ `CLAUDE.md` เตือนไว้เองในหัวข้อ "subprocess ที่ส่งข้อความไทยต้องระบุ
`encoding='utf-8'`" — ครั้งนี้มันไปโผล่ที่การเขียนไฟล์ ไม่ใช่ที่ subprocess

**แนวทางแก้:** เขียนรายการนั้นใหม่จากงานที่ทำจริง (สคริปต์และ asset ของ Form Study 03
ยังอยู่ครบใน working tree) และตรวจว่าเครื่องมือที่ใช้เขียนไฟล์ระบุ `encoding="utf-8"`
ทุกจุด ก่อน commit ควรมีด่านง่ายๆ ที่ปฏิเสธ `?{4,}` ในไฟล์ `.md` ของโปรเจกต์

## สิ่งที่ตรวจแล้วไม่พบปัญหา

- **`data_sources.py`** ปิดทั้ง path traversal, drive letter, absolute path และ
  ตรวจ `is_relative_to(ROOT)` หลัง resolve · `require_project_payload()` fail-closed
- **`slide_assets.py`** ปฏิเสธ path ที่มีไดเรกทอรี, จำกัดนามสกุลภาพ, ตรวจ token ด้วย
  `compare_digest`, และยังต้องอยู่ใน asset manifest ที่ลงทะเบียน — สามชั้น ไม่ใช่ชั้นเดียว
- **`_same_origin_loopback_websocket()`** ต้องตรงกันทั้ง TCP peer, `Origin` และ `Host`
  และทั้งสามต้องเป็น loopback หน้าเว็บจากอินเทอร์เน็ตที่สั่งเบราว์เซอร์ยิง localhost
  จะมี Origin ไม่ตรงและถูกปฏิเสธ · LAN และ client ที่ไม่ใช่เบราว์เซอร์ยังต้องใช้ token
- **`tool_io.on_loop()`** จัดการกรณี tool ที่ถูกยกเลิกแล้วยังพยายามเขียนจอได้ถูกต้อง
  (ตรวจ `abandoned` ทั้งก่อนคิวและใน callback)
- **`.env` ไม่เคยถูก commit** (`git log --all -- .env` ว่าง, `.gitignore:1`)
  service-role key ของ Supabase อยู่ในไฟล์ที่ไม่เข้า Git
