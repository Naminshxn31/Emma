# แอป "Emma บนหุ่น" — พิมพ์เขียวรุ่น 0.1

**ต่อยอด `apps/emma-robot-android` (`com.emma.robot.control`) ให้เป็นแอปเดียวที่ยืนในห้องขายเองได้** —
เซิร์ฟเวอร์ (Emma) เป็นคนขับแทนคนถือจอย พร้อมชั้นความปลอดภัยในเครื่อง
ตัดสินโครงสร้างกับเจ้าของแล้ว 25 ก.ย. 2026: **ไม่ทำแอปที่ 3 แยก** และ **จอเริ่มต้นคือหน้า Emma
ส่วนตัวบังคับ Xbox ซ่อนไว้เป็น override ของสตาฟ ไม่โผล่ให้ลูกค้าเห็น**

## ที่มา — ทำไมยังไม่มีตัวไหนยืนเองได้

มีสองแอปอยู่แล้ว แต่ตั้งใจแยกหน้าที่กัน และไม่มีตัวไหนเป็นหุ่นต้อนรับอัตโนมัติ:

- **`emma-ai-voice`** (`com.emma.ai.voice`) — WebView ของ `/preview?app=1` มีปากไม่มีตัว
  (ขอเฉพาะ INTERNET+ไมค์ ไม่แตะแขน/ฐานล้อ/กล้อง โดยตั้งใจ — เรื่องความปลอดภัยของมันคือ "ขยับอะไรไม่ได้")
- **`emma-robot-android`** (`com.emma.robot.control`) — คุมด้วย Xbox ขับแชสซี Slamtec ผ่าน
  **SDK พอร์ต 1445** และแขนผ่านบอร์ด CH340 มีตัวแต่คนขับ ไม่มีเซิร์ฟเวอร์/AI ในเส้นทาง
  (เรื่องความปลอดภัยของมันคือ "ไม่มีเน็ตสั่งได้")

ตัวโปรดักชันต้องมีทั้งสองอย่างในโปรเซสเดียว — และนั่นคือเหตุผลที่ต้องระวัง เพราะแอปที่เซิร์ฟเวอร์
คุยได้ กลายเป็นแอปที่ขยับแขนได้ ชั้นความปลอดภัยกับ allow-list ของท่าจึงเป็นแกนของงานนี้ ไม่ใช่ของแถม

**ทำไมต่อยอดไม่ใช่ทำใหม่:** `emma-robot-android` ผ่านการทดสอบกับหุ่นจริงมาหนักแล้ว — ขับล้อออกจาก
dock ได้ (action 50 เดิน 0.164 ม.), รู้เรื่อง E-stop หลัง, force-stop `com.aobo.robot.ai3` เพื่อยึด
การเชื่อมต่อ, deadman คืนก้านกลาง, ต่อแขน CH340 `1a86:7523` ที่ 115200 เล่นกลุ่มท่าได้ ถ้าแยกแอปที่ 3
เท่ากับมีตัว/แชสซี/safety/force-stop-Aobo สองชุดที่จะเพี้ยนออกจากกัน — เหตุผลเดียวกับกฎ "ไม่ fork" ของโปรเจกต์

## สองโหมดในแอปเดียว

| | โหมดลูกค้า (default) | โหมดสตาฟ (ซ่อน) |
|---|---|---|
| จอ | WebView `/preview?app=1` เต็มจอ — หน้า Emma พูด/ขยับปาก | แผง Xbox + แขน + เซอร์โว + ขับเอง (ของเดิมทั้งชุด) |
| ปุ่มคุม | ไม่มีให้เห็น | มีครบ |
| เข้าได้ยังไง | เปิดแอปมาก็เจอ | ท่าซ่อน — กดค้างมุมจอ ~3 วิ หรือปุ่มลับบนจอย (สตาฟรู้) |

เจ้าของสั่ง "ตัวบังคับไม่ต้องเอาขึ้นมา" — โหมดสตาฟจึงยัง**อยู่ในโค้ด**เป็น override ของเจ้าหน้าที่
(ยึดล้อ/หยุด/แก้ท่า) แค่ไม่ใช่จอเริ่มต้น ปุ่ม **B** ของจอยยังหยุด+ล็อกได้เสมอแม้อยู่โหมดลูกค้า

## สิ่งที่เติมเข้าไป (v0.1)

### 1. จอเสียง — ยกจาก emma-ai-voice ไม่เขียนใหม่
WebView shell ของ `/preview?app=1` + permission ไมค์ (`RECORD_AUDIO`, `MODIFY_AUDIO_SETTINGS`) +
`network_security_config` (release = HTTPS เท่านั้น, debug อนุญาต localhost/10.0.2.2) เก็บ server URL
กับ `WS_TOKEN` ใน SharedPreferences เส้นทางเสียงชุดเดียวกับเว็บที่พิสูจน์แล้ว ไม่ทำใหม่

### 2. สะพานหุ่น → เซิร์ฟเวอร์ (native, แยกซ็อกเก็ตจากเสียง)
Native เปิด WebSocket ไป `/ws` ของตัวเอง แล้วทำตามโปรโตคอลใน `docs/ต่อกับหุ่นยนต์ Astronaut.md`:
ส่ง `robot_ready` (พร้อม `places` + **`ROBOT_TOKEN`** คนละตัวกับ `WS_TOKEN`) / รับ `{"type":"robot","action":…}`

**ทำไมแยกจากซ็อกเก็ตเสียงของ WebView:** ชั้นความปลอดภัยและการคุมตัว **ห้ามผูกกับ lifecycle ของหน้าเว็บ** —
ไมค์/เสียงเป็นของ WebView, คำสั่งตัว/telemetry/หยุด เป็นของ native หน้าเว็บรีโหลดไม่ควรทำให้แขนหลุดการคุม

### 3. ท่าทางตามที่เซิร์ฟเวอร์สั่ง → บอร์ดแขน CH340
`{"type":"robot","action":"gesture","args":{"name":"wave"}}` → map ชื่อ→เลขกลุ่มด้วย **allow-list**
→ `ArmController.playGroup(group)` ที่มีอยู่แล้ว (`#<group>GC<loops>`) `cancel_gesture` → `stopAll()` (`#STOP`)

- **หลักฐานที่มี:** กลุ่ม 3 = ยกแขน/งอศอก (ยืนยันด้วยกล้อง) กลุ่มอื่นเพิ่มเข้า allow-list **เมื่อมีหลักฐานกล้อง**เท่านั้น
  — เลขกลุ่มที่ยังไม่รู้ว่าเป็นท่าอะไร = เครื่องมือที่โมเดลใช้ไม่เป็น (กฎเดียวกับที่ `gesture()` ฝั่ง server ยังไม่ทำ)
- แขน CH340 เป็น**คนละบอร์ดกับแชสซี** สั่งท่าไม่ชนการเดิน จึงทำได้เลยใน v0.1 โดยไม่แตะสถาปัตยกรรมล้อ

### 4. ความปลอดภัยในเครื่อง — v0.1
- **E-stop กายภาพหลังหุ่น** (มีอยู่) — การหยุดชนิดเดียวที่ล้มเหลวไม่ได้ เป็นด่านหลัก
- **Watchdog:** WS หลุด หรือไม่มี heartbeat เกิน N วิ = `stopAll()` + cancel แชสซี (native รู้ว่า "ไม่รู้แล้ว" จึงหยุด ไม่ใช่เดินต่อ)
- **ปุ่ม B** ของ operator = หยุด+ล็อกทันที ทุกโหมด
- **แบตต่ำ/บอร์ดแขนไม่ต่อ = ปฏิเสธ** คำสั่งท่าทาง แล้วรายงานกลับ (ไม่แกล้งทำ)
- **ยังไม่ทำ voice-KWS "หยุด" ในเครื่องใน v0.1** — เพราะ**ไมค์มีเจ้าของคนเดียว** WebView ถือไมค์ไว้ให้ Gemini อยู่
  เปิด KWS ซ้อนบนไมค์ตัวเดียวกัน = บั๊ก "ไมค์สองเจ้าของ" ที่โปรเจกต์จ่ายค่าเรียนมาแล้ว ต้องเคลียร์กับผู้ขายก่อนว่า
  เปิดอาเรย์ USB 8 ช่องอ่านซ้อนได้ไหม และช่องไหนคือเสียง post-AEC (คำถามข้อ 1 ในหัวข้อ "เสียง" ของ doc หุ่น)

### 5. Mock honesty
ท่าทาง/สถานะทุกอันติด `hardware` = `ok`/`mock`/`failed` แขนไม่ต่อ = `mock` แล้วบอกโมเดลตรงๆ ว่ายังทำท่าไม่ได้
(กฎเดียวกับ IR/robot เดิม: หุ่นยืนข้างลูกค้า ประกาศว่าทำท่าแล้วทั้งที่ไม่ขยับ = ดังกว่าจอผิดรูปเยอะ)

### 6. Kiosk แข็งแรง (แก้ Chrome kiosk พังตอนรีบูต)
`BOOT_COMPLETED` auto-launch, `FLAG_KEEP_SCREEN_ON`, immersive ซ่อนแถบนำทาง, ล็อก portrait 1080×1920,
force-stop `com.aobo.robot.ai3` ตอน resume (มีแล้ว — คงไว้ Aobo ยึดการเชื่อมต่อพร้อมกันไม่ได้) token ฝังถาวร
เป็น native ได้ครบโดยไม่ต้องพึ่ง Chrome first-run/cert/orientation ที่รีเซ็ตทุกบูต

## เจ้าของล้อมีคนเดียว — เรื่องใหญ่ที่ **อยู่นอกขอบ v0.1**

แชสซีเดินได้สองทางไปมอเตอร์เดียวกัน: **เซิร์ฟเวอร์ REST 1448** (`app/robot_chassis.py`) กับ
**แอป SDK 1445** (`SlamwareCorePlatform`, พิสูจน์แล้วว่าขับล้อจริง) — สองเจ้าของ = นาฬิกาสองเรือน
บั๊กที่โปรเจกต์จ่ายค่าไปสามรอบ

- v0.1 **ไม่แตะการเดิน** ทำแค่ แขน/หัว (คนละบอร์ด ไม่ชน) + เสียง + safety + kiosk
- การเดินอัตโนมัติ (server สั่ง app เดินผ่าน `move_to_point`) เป็นงานแยก และต้อง**เลือกเจ้าของล้อก่อน**
  ข้อเสนอ: ให้ **แอปเป็นเจ้าของล้อ** (SDK 1445 พิสูจน์แล้ว + force-stop Aobo อยู่แล้ว) ส่วนเซิร์ฟเวอร์ใช้ 1448
  **อ่านสถานะ/lidar read-only เท่านั้น** (ไม่ขยับมอเตอร์ ไม่ชน) — กลับมาใช้สะพาน `move_to_point` ตามโปรโตคอลเดิม
  แทน server-direct REST ที่ POST เดินจริงยัง "ไม่เคยส่งสักครั้ง" ส่วน Xbox ขับเอง = operator ยึดล้อชั่วคราว
  mutually exclusive กับการเดินอัตโนมัติ

## ฝั่งเซิร์ฟเวอร์เติมนิดเดียว

- **tool `gesture()`** กลุ่ม `robot` → ส่ง `{"type":"robot","action":"gesture","args":{"name":…}}`
  allow-list ชื่อท่า (wave/nod/point…), ผลติด `hardware`, description บอกโมเดลว่าใช้ตอนไหน (ทักทาย/ชี้จุด/พยักรับ)
  handler รับ `robot_arrived`/telemetry ของท่ากลับถ้าจะยืนยัน ok — ทดสอบ mock ก่อน (เหมือน `tests/test_robot.py`)
