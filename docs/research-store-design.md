# ออกแบบที่เก็บข้อมูลของ agent

**ร่างวันที่ 25 ส.ค. 2569 · ยังไม่ลงมือเขียนโค้ด ให้อ่านและค้านก่อน**

คำถามที่เอกสารนี้ตอบ: *agent ที่ไปหาข้อมูลมา ต้องเก็บยังไงให้หุ่นใช้ได้จริง โดยไม่มีวันพูดตัวเลขที่ไม่มีใครรับผิดชอบ*

---

## หลักการเดียวที่ทุกอย่างในเอกสารนี้งอกออกมา

> **agent ไม่มีสิทธิ์อนุมัติงานของตัวเอง**

ทุกการตัดสินใจข้างล่างคือการทำให้ประโยคนี้เป็นจริงในระดับ*โครงสร้าง* ไม่ใช่ระดับ*ความตั้งใจ* — เพราะกฎที่บังคับใช้ด้วยความตั้งใจ จะถูกลืมในวันที่คนกำลังรีบ

ในโค้ดตอนนี้มีหลักการนี้อยู่แล้วสองที่: `condo_facts.json` มีช่อง `approved_by` และสคริปต์บรรยายสไลด์มี `script_approved_by` — ของใหม่ไม่ประดิษฐ์อะไรเพิ่ม แค่ขยายกฎเดิม

---

## 1. โครงสร้างโฟลเดอร์ — แยกทางกายภาพ ไม่ใช่แยกด้วยฟิลด์

```
data/research/
├── inbox/                    ← agent เขียนที่นี่ที่เดียว เขียนแล้วห้ามแก้
│   ├── legal-2026-09-01.json
│   ├── finance-2026-09-01.json
│   └── reputation-2026-09-01.json
├── legal.json                ← คลังที่อนุมัติแล้ว หุ่นอ่านที่นี่ที่เดียว
├── finance.json
├── market.json
├── reputation.json
├── competitors.json
└── rejected.json             ← ของที่คนดูแล้วไม่เอา + เหตุผล
```

**ทำไมต้องแยกโฟลเดอร์ ไม่ใช้ฟิลด์ `approved: true/false` ในไฟล์เดียว**

เพราะถ้าอยู่ไฟล์เดียวกัน วันหนึ่งจะมีคนเขียนโค้ดที่ลืมกรอง แล้วข้อมูลที่ยังไม่อนุมัติจะหลุดเข้าไปในดัชนีค้นหา การแยกโฟลเดอร์ทำให้ **path ที่หุ่นอ่านกับ path ที่ agent เขียน ไม่ใช่ที่เดียวกันตั้งแต่ต้น** — ลืมกรองไม่ได้ เพราะไม่มีอะไรให้ลืมกรอง

`inbox/` **เขียนแล้วห้ามแก้** ด้วย เพื่อให้ย้อนดูได้เสมอว่า agent พูดอะไรจริงๆ ก่อนที่คนจะแก้ไข — ถ้าวันหนึ่งข้อมูลผิดหลุดออกไป เราต้องแยกให้ออกว่าเป็นความผิดของ agent ที่หามาผิด หรือของคนที่อนุมัติผิด

**ทำไมแยกไฟล์ตามหัวข้อ ไม่รวมไฟล์เดียว**
คนอนุมัติคนละคนกัน — กฎหมายกับการเงินคนละคนเซ็น และเวลาเปิดดูจะได้ไม่ต้องเลื่อนผ่านของที่ไม่ใช่เรื่องตัวเอง

## 2. หน้าตาของหนึ่ง record

```json
{
  "id": "ltv-ceiling",
  "topic": "finance",
  "claim_th": "ธปท. ผ่อนคลายเพดาน LTV เป็น 100% สำหรับสัญญากู้ที่ทำระหว่าง 1 ก.ค. 2569 – 30 มิ.ย. 2570",
  "detail_th": "หลักประกันต่ำกว่า 10 ล้านบาทใช้กับสัญญาที่ 2 เป็นต้นไป · ตั้งแต่ 10 ล้านบาทขึ้นไปใช้ได้ตั้งแต่สัญญาแรก · เป็นเพดานที่ ธปท. อนุญาต ไม่ได้แปลว่าธนาคารจะอนุมัติให้ต่างชาติ",
  "value": { "number": 100, "unit": "percent", "of": "LTV ceiling" },
  "sources": [
    {
      "url": "https://www.bot.or.th/th/news-and-media/news/news-20260514.html",
      "publisher": "ธนาคารแห่งประเทศไทย",
      "tier": "gov",
      "published_at": "2026-05-14",
      "fetched_at": "2026-08-25"
    }
  ],
  "confidence": "confirmed",
  "conflicts_with": [],
  "effective_from": "2026-07-01",
  "expires_on": "2027-06-30",
  "review_by": "2027-05-01",
  "approved_by": "",
  "approved_at": null,
  "supersedes": null,
  "language_note": "ตัวเลขนี้เกี่ยวกับเงิน ต้องผ่านด่าน commercial gate"
}
```

### ทำไมแต่ละฟิลด์ถึงต้องมี

**`id` ที่เสถียร** — หัวใจของทั้งระบบ ถ้าไม่มี id คงที่ รอบหน้า agent จะมองว่าทุกอย่างเป็นของใหม่หมด แล้วคนต้องอ่านซ้ำทั้งฉบับทุกเดือน (ซึ่งแปลว่าเดือนที่สามจะไม่มีใครอ่าน) มี id แล้วถึงจะพูดได้ว่า *"3 รายการเปลี่ยน"*

**`claim_th` ต้องเป็นประโยคเดียว ไม่ใช่ย่อหน้า** — สองเหตุผล: (1) หุ่นพูด ไม่ได้อ่านเอกสารออกเสียง (2) การอนุมัติเกิดทีละ claim — ย่อหน้าที่มีสามข้อเท็จจริงจะอนุมัติครึ่งเดียวไม่ได้ ถ้าเนื้อหาต้องแยกเป็น 3 ประโยค ก็ต้องเป็น 3 record

**`sources[]` ต้องมีทั้ง `published_at` และ `fetched_at`** — คนละความหมาย: "ข่าวนี้ลงเมื่อไหร่" กับ "เราไปอ่านเมื่อไหร่" ข่าวเก่าที่เพิ่งอ่านเจอ กับข่าวใหม่ที่อ่านนานแล้ว มีความน่าเชื่อถือคนละแบบ

**`tier`** — `gov` / `institution` / `media` / `broker` เก็บเป็นข้อมูล ไม่ใช่แค่ป้ายสวยงาม เพราะจะใช้ตัดสินได้ว่า record ไหนควรให้หุ่นพูด (เช่น ตั้งกฎว่าตัวเลขการเงินต้อง tier `gov` หรือ `institution` เท่านั้น)

**`confidence` ต้องมี 4 ค่า ไม่ใช่ 2**

| ค่า | เมื่อไหร่ | ตัวอย่างจริงจากงานรอบนี้ |
|---|---|---|
| `confirmed` | ≥2 แหล่งตรงกัน หรือ 1 แหล่งราชการ | เพดาน LTV 100% |
| `single_source` | มีแหล่งเดียว ไม่ใช่ราชการ | ค่าส่วนกลาง 65-100 บาท/ตร.ม. |
| `conflicting` | แหล่งขัดกันเอง | LTV ของ UOB (40-50% vs 50-70% vs 70%) |
| `not_found` | ค้นแล้วไม่มี | โครงการ "Prime One" |

**`not_found` ต้องเก็บเป็น record ด้วย ไม่ใช่แค่เว้นว่าง** — เพราะ "ค้นแล้วไม่เจอ" คือคำตอบที่มีค่า และถ้าไม่เก็บไว้ agent รอบหน้าจะไปค้นซ้ำเรื่องเดิม แล้วคนก็จะอ่านซ้ำเรื่องเดิม

**`expires_on` บังคับกรอกทุก record** — ไม่มีคำว่า "ไม่หมดอายุ" ยกเว้นตัวบทกฎหมายที่ยังใช้อยู่ (เช่น โควตา 49%) ซึ่งใส่ `null` ได้แต่ต้องเขียนเหตุผลกำกับ
ตัวเลขที่ไม่มีวันหมดอายุ คือตัวเลขที่จะกลายเป็นข้อมูลผิดโดยไม่มีใครรู้ตัว

**`supersedes`** — เวลาข้อมูลเปลี่ยน ไม่ทับของเดิม แต่สร้าง record ใหม่ที่ชี้กลับไปหาของเดิม ทำให้ตอบคำถาม *"เดือนที่แล้วหุ่นบอกลูกค้าว่าอะไร"* ได้ ซึ่งเป็นคำถามที่จะถูกถามจริงในวันที่มีปัญหา

## 3. หุ่นเห็นอะไร — สามสถานะ ไม่ใช่สอง

ตัวโหลดคำนวณ `robot_may_speak` เอง **ห้ามให้ใครกรอกมือ**:

```
approved_by ว่าง                         → ห้ามพูด (ไม่ต้องสนใจอย่างอื่น)
วันนี้ > expires_on                      → ห้ามพูด
วันนี้ > review_by แต่ยังไม่ถึง expires  → พูดได้ + ต้องพ่วงวันที่
อื่นๆ                                    → พูดได้ปกติ
```

หุ่นพูดยังไงในแต่ละสถานะ:

| สถานะ | หุ่นตอบว่า |
|---|---|
| สด | "เพดาน LTV ตอนนี้อยู่ที่ 100% ค่ะ" |
| ใกล้หมดอายุ | "ข้อมูลที่ฉันมี ณ วันที่ 14 พ.ค. 2569 คือเพดาน LTV 100% ค่ะ แนะนำให้ยืนยันกับฝ่ายขายอีกครั้งนะคะ" |
| หมดอายุ / ยังไม่อนุมัติ | "เรื่องนี้ฉันยังไม่มีข้อมูลที่ยืนยันได้ค่ะ ขอให้ฝ่ายขายตอบให้นะคะ" |

**ช่องสุดท้ายสำคัญที่สุด** — หุ่นที่พูดข้อมูลเก่าอย่างมั่นใจ อันตรายกว่าหุ่นที่บอกว่าไม่รู้

### ด่านที่ต้องต่อเพิ่ม

คลังนี้จะมีตัวเลขการเงินอยู่เยอะ (LTV, ดอกเบี้ย, ค่าโอน, yield) ซึ่งเป็นหมวดที่ `_is_commercial()` ใน `knowledge.py` กันไว้อยู่แล้ว — แต่ด่านนั้นดักเฉพาะ `search_condo_info` **ต้องขยายให้ครอบเครื่องมือค้นคลังวิจัยด้วย** ไม่งั้นเปิดคลังนี้เท่ากับเปิดประตูหลังให้คำถามเรื่องเงินทั้งหมด

## 4. รอบการทำงานของ agent — โหมด diff ตั้งแต่รอบที่สอง

```
รอบแรก (bootstrap)          รอบที่ 2 เป็นต้นไป
─────────────────           ────────────────────────────────
ค้นทุกหัวข้อ                 1. โหลด <topic>.json ที่อนุมัติแล้ว
เขียนลง inbox/               2. ส่ง id + claim + expires_on เข้า prompt
คนอนุมัติทีเดียว 1-2 ชม.        เป็น "สิ่งที่เรารู้แล้ว"
                            3. agent ค้นเฉพาะเพื่อตอบ 5 คำถาม
                            4. เขียนลง inbox/ เฉพาะที่ไม่ใช่ still_true
                            5. รายงานสรุปให้คนที่รับผิดชอบหัวข้อนั้น
```

**ห้าคำถามที่ agent ตอบได้เท่านั้น** — จำกัดรูปแบบผลลัพธ์ไว้ ไม่ให้เขียนอะไรก็ได้:

| ผลลัพธ์ | หมายถึง | ต้องแนบ |
|---|---|---|
| `still_true` | ยังเหมือนเดิม | แหล่งที่ไปเช็คมา |
| `changed` | เปลี่ยนแล้ว | claim ใหม่ + แหล่ง + `supersedes` |
| `new` | เรื่องใหม่ที่ยังไม่เคยเก็บ | record เต็ม |
| `expiring` | ใกล้ถึง `review_by` | เตือน + ผลการเช็คล่าสุด |
| `could_not_verify` | เข้าแหล่งไม่ได้ / ขัดกัน | บอกว่าค้นด้วยอะไรไปแล้วบ้าง |

**ข้อบังคับที่โค้ดต้องบังคับ ไม่ใช่ขอความร่วมมือ:** record ที่ไม่มี `sources[]` **ตัวเขียนไฟล์ต้องปฏิเสธ** ตั้งแต่ตอนเขียน ไม่ใช่ไปจับตอนคนอ่าน

`still_true` ก็ต้องบันทึกด้วย — เพราะ "เช็คแล้วเมื่อ 1 ก.ย. ยังเหมือนเดิม" เป็นข้อมูลที่ต่อ `review_by` ออกไปได้ และเป็นหลักฐานว่า agent ทำงานจริง ไม่ได้เงียบเพราะพัง

## 5. รายงานที่คนได้อ่าน — หนึ่งหน้า ไม่เกินนั้น

```
คลังกฎหมาย · รอบ 1 ก.ย. 2569 · ผู้รับผิดชอบ: [ชื่อ]

เปลี่ยน 1 · ใหม่ 2 · ใกล้หมดอายุ 1 · เช็คแล้วเหมือนเดิม 14 · เข้าไม่ถึง 1

▸ เปลี่ยน — ltv-ceiling
  เดิม: เพดาน LTV 100% ถึง 30 มิ.ย. 2570
  ใหม่: ธปท. ประกาศ 20 ส.ค. 2569 ปรับเงื่อนไข…
  แหล่ง: bot.or.th (ราชการ) 20 ส.ค. 2569
  [ อนุมัติ ] [ ไม่เอา ] [ ขอให้หาเพิ่ม ]

▸ ใกล้หมดอายุ — transfer-fee-reduction
  ครบกำหนดทบทวน 1 ต.ค. 2569 · เช็คแล้วยังไม่มีประกาศใหม่
  [ ต่ออายุ 6 เดือน ] [ ให้หมดอายุ ]

▸ เข้าไม่ถึง — sbt-late-delivery-penalty
  ดึง PDF ราชกิจจานุเบกษาไม่สำเร็จ 3 รอบติด
  → ต้องใช้คน ส่งให้ทนายบริษัทดึงตัวบท
```

ของที่ `still_true` **ไม่แสดง** แค่บอกจำนวน — คนที่เปิดอ่านต้องเห็นเฉพาะสิ่งที่ต้องตัดสินใจ

## 6. ช่องทางอนุมัติ — ใช้แพตเทิร์นที่รีโปนี้มีอยู่แล้ว

ในรีโปมี `scripts/add_narration.py` กับ `scripts/approve_narration.py` อยู่แล้ว ของใหม่เดินตามรอยเดิม:

```
scripts/research_run.py      รัน agent → เขียน inbox/ → พิมพ์รายงาน
scripts/research_approve.py  เปิดรายงาน ติ๊กทีละรายการ → ย้ายเข้าคลัง
```

ตอนอนุมัติ **ต้องพิมพ์ชื่อคนอนุมัติ** ไม่มีค่า default ไม่มี `--yes-all` — ความฝืดตรงนี้คือฟีเจอร์ ไม่ใช่บั๊ก

พอนิสัยการตรวจอยู่ตัวแล้วค่อยทำหน้าเว็บ ตอนนั้นจะรู้ว่าหน้าเว็บต้องมีอะไรจริงๆ

## 7. โหมดพังที่ออกแบบเผื่อไว้แล้ว

| อาการ | ผลถ้าไม่กัน | ตัวกัน |
|---|---|---|
| agent พัง เงียบไป 3 เดือน | คลังเก่าโดยไม่มีใครรู้ | ทุกไฟล์มี `last_run_at` · เกิน 2 รอบไม่รัน = แจ้งเตือน |
| ไม่มีใครอนุมัติ | inbox บวม คลังไม่ขยับ | รายงานขึ้นหัวว่า "ค้างอนุมัติ N รายการ เก่าสุด X วัน" |
| agent หลอน แต่งแหล่ง | ข้อมูลปลอมเข้าคลัง | ตัวเขียนไฟล์ปฏิเสธ record ที่ไม่มี `sources[]` · ตอนอนุมัติแสดง URL ให้กดเปิดจริง |
| ข้อมูลทดสอบหลุด | หุ่นพูดเลขที่มั่วขึ้นมา | `approved_by` ที่ขึ้นต้นด้วย `TEST` → `robot_may_speak = false` เสมอ + มีเทสต์ยืนยัน |
| ตัวเลขในคลังขัดกับ `condo_facts.json` | หุ่นพูดสองอย่างในเซสชันเดียว | ตอนโหลดเช็คชนกัน · ถ้าชน **`condo_facts` ชนะเสมอ** (ข้อมูลบริษัทเหนือข้อมูลตลาด) แล้วขึ้นเตือน |
| ลูกค้าถามเรื่องที่ไม่มีในคลัง | หุ่นเดา | กฎเดิม: ไม่มีข้อมูล = บอกตรงๆ **ไม่มีการค้นเว็บสดเป็น fallback** |

## 8. สิ่งที่ยังไม่ตัดสินใจ — ขอความเห็น

1. **ใครเซ็นหัวข้อไหน** — กฎหมาย/การเงินควรเป็นผู้จัดการขายหรือฝ่ายกฎหมาย? ชื่อเสียงบริษัทควรเป็นการตลาด? ต้องมีชื่อคนจริงก่อนเริ่ม ไม่งั้นระบบจะไม่มีใครดัน
2. **รอบการรัน** — ผมเสนอกฎหมาย/การเงิน/ชื่อเสียง เดือนละครั้ง · คู่แข่ง เดือนละครั้ง · โครงสร้างพื้นฐาน ไตรมาสละครั้ง — เร็วไปหรือช้าไป?
3. **`still_true` เก็บทุกรอบไหม** — เก็บหมดไฟล์จะบวม แต่ตัดทิ้งจะเสียหลักฐาน ผมเสนอเก็บแค่รอบล่าสุด (เขียนทับ `last_verified_at`) แต่ inbox เก็บครบตลอด
4. **หุ่นห้องขายควรเห็นคลังทั้งหมดไหม** — ผมคิดว่า `reputation` (เรื่องที่ลูกค้าเสิร์ชเจอ) ควรเป็นข้อมูลสำหรับ*เซลส์อ่านเตรียมตัว* ไม่ใช่ให้หุ่นพูดกับลูกค้าเอง — เห็นด้วยไหม
5. **ภาษา** — เก็บ claim ภาษาไทยอย่างเดียว แล้วให้โมเดลแปลตอนพูด หรือเก็บสองภาษา? (สไลด์เก็บสองภาษา แต่ที่นั่นเป็นคีย์เวิร์ดสำหรับค้นหา ไม่ใช่คำที่ต้องพูดเป๊ะ)
